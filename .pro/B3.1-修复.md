### 1.1 真 bug：resolve 的新判断 id 与同秒旧判断相撞，被 `put_judgment` 静默丢掉

E3 v2 第 6 步原始输出（`.pro\out\e3.after.txt:71-88`）：

```
$ jw resolve file:c.txt --verdict held --by pro --why 人工核对：文件仍在
  resolved: file:c.txt -> held by pro（旧判断过期 1 条）      ← 打印成功
$ jw ask file:c.txt
  conflict: file:c.txt                                       ← 仍是冲突
[resolve 后] file:c.txt judgments:
  held    at=1792904188 exp=1792904189
  refuted at=1792904189 exp=None                             ← 没有第三条！
```

原因（T1，能对上每一行）：
1. `judgment_id = repo:j:<kind>:<at>:<hash(subject)>`，**at 只到秒**；
2. `resolve_conflict` 用 `now`（=1792904189）当新判断的 at，而夹具里本来就有一条 `at=1792904189` 的 refuted 判断 → **id 完全相同**；
3. `put_judgment` 是 `ON CONFLICT(id) DO NOTHING` → 新判断**没写进去，也不报错**；
4. 紧接着 evidence 挂到 `j.id`（=那条 refuted 的 id）上 → 它同时有 contradicts（夹具）和 supports（resolve）→ 冲突；
5. `expire_older_than(subject, Some(&j.id), now)` 过期的是**另一条**（held at=4188）→ 于是 ask 仍是 conflict，且"旧判断过期 1 条"（本该 2 条）。

**同一个坑在 verify 也埋着**：同一秒内连跑两次 `verify`，第二次的新 id 与第一次相同 → 静默 no-op，看起来"重验了"其实没写新观测。

## 2. B3.1 修复（必须，约 15 分钟）

### 2.1 让新判断的 at 严格大于该 subject 现有的最大 at

`store.rs`（放在 `set_expiry` 后，现 374-380 之后）：

```rust
/// 某 subject 现有判断的最大 `at`（没有 → None）。
///
/// verify/resolve 写新判断前必须用它把 `at` 推到 `max(at)+1`：`judgment_id`
/// 只精确到秒，同秒会撞 id，而 `put_judgment` 是 DO NOTHING → 静默丢判断。
pub fn max_at(&self, subject: &str) -> Result<Option<i64>> {
    let v: Option<i64> = self.conn.query_row(
        "SELECT max(at) FROM judgment WHERE subject = ?1",
        params![subject],
        |r| r.get(0),
    )?;
    Ok(v)
}
```

`main.rs::cmd_verify`（现 444-505）：找到 `old` 之后加一行，后续全用 `at`：

```rust
let at = store.max_at(subject)?.map_or(now, |m| now.max(m + 1));
let j = judgment_row(&repo, subject, &old.kind, v, at, 1, 1, old.scope.clone());
// Source.time = at；premise = format!("recheck:{at}:{subject}")；expire_older_than(..., at)
```

`store.rs::resolve_conflict`（现 431-486）：`latest` 拿到后：
