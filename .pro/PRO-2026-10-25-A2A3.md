## A2. 「人工记录」落到模型哪个概念、怎么落

**结论：不新增基本概念。落点是 `judgment(kind=decision)` + `judgment(kind=hypothesis)` + `alternative_of` + `source(instrument=record)`；`decision` 挂在已有 `rationale` 之下（kind_registry.parent），不叫 rationale 本体。**

为什么不是 rationale 本体：`rationale` 已登记为 human 层"为什么"（`store.rs:439`），它是一类**判断片段**；一条完整的决策记录有状态、有替代项、有验收——比 rationale 多一层结构。用 kind_registry 的 parent 表达"decision 是 rationale 的具体化"，不动 12 概念（MODEL-v0.1 变更规则 3：先试关系/字段编码）。

## A3. 冲突 resolve 流程现在做不做

**结论：做，和 `verify` 一起做（B3），且规则必须写死；不做"自动仲裁"。**

现在必须做的理由是 E3（T1）：`verify` 一条 contradicts 就能造出冲突，而**冲突一旦产生就永久 uncertain**——`ask` 不看 `conflict` 表、只看证据极性（`compose.rs:39-41`），过期/标记都不改结论（`e3.txt` 分支 A/B/C）。也就是说：不做 resolve，B3 把 verify 修好后每次重验都会把 subject 钉死。

### A3 规则（v1，写死，别扩）

| 问题 | 裁决 |
|---|---|
| 谁有权 resolve | 只有人：`jw resolve <subject> --verdict <held\|refuted> --by <name> --why <一句话>`；`--by` 必填且非空，落进 evidence premise。机器（git/tree-sitter/verify/checker）**不许**调用 resolve | 
| 前提 | 该 subject 在 `conflict` 表里有一条 `resolved=0` 的记录，且两端判断都未过期；否则 `no_conflict` 退出码 2 |
| 怎么写 | ① 写**一条新判断** `at=T`、`verdict=赢方`、`coverage=1/1`；② 给新判断写 supports 证据 `resolve:cf:<a>:<b>:<by>:<why>`（instrument=`resolve`）；③ 把该 subject **所有旧判断** `expires_at=T`（不删）；④ `conflict` 行 `resolved=1, resolved_at=T` |
| 证据怎么记 | 输方的 contradicts 证据**保留**（它挂的判断已过期，`ask` 不再计入）；**禁止**删证据、禁止 `UPDATE judgment SET verdict`（`update_verdict` 只保留给迁移，正常路径不许用） |
| 不许做什么 | ① 不许机器自动 resolve（自动冲突标注必须人工复核，skill 规则 18）；② 不许 resolve 覆盖不足的判断（先过覆盖闸）；③ 不许跨 subject resolve（冲突只在同 subject）；④ 不许不写 `--why`；⑤ 不许用"新的赢"当默认规则（E3 分支 A 证明：过期最新那条会退回旧的 held，方向反了） |
| 与过期语义的关系 | resolve 就是"用过期表达输"：`ask` 先剔除过期判断再数证据（`query.rs:29-38`），所以模型层**不需要新表新字段**（E3 分支 C 实测：新判断+旧判断全过期 → `ask` 出 refuted）。缺的只是命令行 |
| 判别力判据 | `conflicts` 报的未解决数必须能降到 0；`ask` 必须从 uncertain(conflict) 变成 held/refuted；旧判断必须还在（`SELECT count(*) … expires_at=T` ≥ 1） |

B3 实现前必须知道的两个坑（T1）：`scan_conflicts` 不跳过已过期判断（`store.rs:285-305`，E3 分支 C 里 resolve 完还报 2 对）；`conflict` 表**没有任何写 `resolved=1` 的路径**（`main.rs:457-466` 只读）。

fn record_at(rid: &str) -> Option<i64> {
    let d = rid.strip_prefix("D-")?.split('-').next()?;
    let y: i64 = d.get(0..4)?.parse().ok()?;
    let m: i64 = d.get(4..6)?.parse().ok()?;
    let day: i64 = d.get(6..8)?.parse().ok()?;
    let y2 = if m <= 2 { y - 1 } else { y };
    let era = y2.div_euclid(400);
    let yoe = y2 - era * 400;
    let doy = (153 * ((m + 9) % 12) + 2) / 5 + day - 1;
    let doe = yoe * 365 + yoe / 4 - yoe / 100 + doy;
    Some((era * 146097 + doe - 719468) * 86400)
}

## D.0 三个重点问题的直接回答

**① scope 的粒度与 objects 口径是否自洽？——不自洽，4 个 kind 有 3 套读法。**

| kind | subject 前缀 | granularity | objects（实测） | 自洽? |
|---|---|---|---|---|
| change | `file:` | file | `[被改文件]` | ✗ kind 说"改动"，subject 说"文件"；`kind_registry` 里 `file` 反而 0 生产者（`e0b_facts.txt` §2/§3） |
| doc | `doc:` | file | `[文档路径]` | ✓（但 kind `doc` 没登记，`e0b_facts.txt` §1） |
| symbol | `symbol:` | symbol | `[所在文件]` | ✓ |
| issue | `issue:` | file（旧）/issue（新） | `[issue:demo#1]`（旧）/`[demo#1]`（新） | ✗ 同一字段在 issue 上是"身份"、在 change/doc 上是"被指向的文件"；且 demo 库与当前代码不一致（`e0c_current.txt` C1） |
| pr | `pr:` | file | `[diff 文件]` | ✗ 与 issue 相反（issue 放身份、pr 放文件）——这是 IMPL-GUIDE 15 与 17 自相矛盾的直接后果 |

裁决口径（B2 起统一）：**subject = 身份的键；objects = 该判断覆盖的实体集合；granularity 声明实体类型**。于是 `issue` 的 objects 放 `[repo#n]`（实体就是 issue）、`pr` 若回来必须 `granularity=pr, objects=[repo#n]`，被改文件交给子概念 `impact`（MODEL 冻结的 impact←change），不许再塞进 pr 的 scope。

**② issue/pr 映射跟 compose 的冲突闸、覆盖闸是否互相打架？——不是打架，是"闸对它们无效"。**

- 覆盖闸：issue 一次状态观测记 1/1，没有"评论总数/分页总数"概念 → 永远满覆盖，闸不触发（E2：coverage_short=0）。`uncertain` 记 0/0 又绕过闸（`0<0` 假）。**结论：issue 的 coverage 是伪满覆盖**（D-17）。
- 矛盾闸：issue/pr 全部写 supports，永远造不出矛盾（E2：conflict=0）。
- 真正跟矛盾闸打架的是 **`verify`**：它把 contradicts 挂到本来就有 supports 的同一条判断上 → 单历史也必 conflict（E3）。这是 D-12，B3 修。

**③ CLI 集成测试是在测真行为还是测自己的字符串？——一半一半。**

- 真行为：退出码 0/1/2 三态映射、判断数 3、依据数 7/14（夹具→期望），这些改实现也会红，算真。
- 自证字符串：`out.contains("scope=issue")`、`"coverage=1/1"`、`"crates/cli/src/cmd_scan.rs:+42/-7"`（`collect.rs:56,62,93`）——改一行输出就红、行为坏了不一定红。而且 `issue#1` 的 `contains("uncertain")` 与退出码 2 一起，**区分不了 no_data**（E2 H2c）。
- 最大的缺口不是"测太细"，是"该测的没测"：`verify`/冲突/resolve/幂等/C-quote 零覆盖（D-26/27）。

### 10.3 裁决：过期基准改为"逻辑时钟"（per subject）

`threshold = as_of.unwrap_or(max(墙钟, 本 subject 最新 at))`。理由：`at` 为躲同秒 id 撞车会被推到 `now+1`，`expires_at >= at` 使其也落在 `now+1`；基准只用墙钟会留 1 秒窗口（E3 v2 第 6 步）。作用域**仅本 subject**，`as_of` 显式给定时不受影响；未来日期的 `at` 会把该 subject 基准推后，属数据异常，不加 cap。
