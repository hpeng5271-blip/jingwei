## 1. 整理

### 1.1 对 9 条读法的核对（改 3 处口径）

| # | 原读法 | 我的核对 |
|---|---|---|
| 1 | 单文件=卡片，可切观测态，从底层到顶层、加工过 | **对**。补一句：「加工过」= 每层都是摘要/结构，不是原样 dump（底层=符号/改动，顶层=判断/决策） |
| 2 | 整项目=大画布，图标待研究 | **对** |
| 3 | 取消"专门图谱页 + 高可操作性" | **对**。准确说：取消的是「一个页面承载全部尺度并支持拉取操作」，不是取消图谱本身 |
| 4 | 主战场=IDE（文件树+内容+LSP 客户端适配）+ 角落卡片（单/多文件，最多一模块） | **对**。补：卡片是**只读**的，编辑仍在编辑器 |
| 5 | 跨模块 → 只能大画布 | **对** |
| 6 | 一统图谱可分化成多个卡片，先做窗口 | **对**，但这是**用户的核心洞察**，不是我的结论；我的判断见 §2.1 |
| 7 | 「主要是变换的自由度」= 不同窗口/观测态可切换 | **改**：不是两个自由度，是**三个**——①选范围（文件/多文件/模块）②选观测态（同一范围的看法）③选形态/位置（缩略、展开、从画布生成）。"变换"指这三个的切换，不是变换代码 |
| 8 | 画布可自由排布、总视图可缩略、框选生成卡片 | **对**。补：画布是**入口与布局**，不是阅读器（细读发生在卡片） |
| 9 | 是不是沙箱隔离？自动生成收缩？ | **保留为"用户自问"，未定**。我的回答见 §2.5：是**视图级隔离**（把一块范围摘出来单独研究），不是执行沙箱；"收缩"= 默认折叠/摘要、按需展开 |

### 1.2 概念表（每个一句定义 + 不做什么）

| 概念 | 定义 | 不做什么 |
|---|---|---|
| **卡片窗口** | 停靠在编辑器角落、只读、可关闭的小窗，展示**一个范围**（单文件/多文件/单模块）的结构摘要 | 不编辑代码；不替代文件树；不承载跨模块 |
| **观测态** | 同一范围的**不同看法**（粒度/时间/证据/呈现），不是缩放 | 不是"更多信息"；每个态必须回答一个具体问题 |
| **大画布** | 跨模块/整项目的唯一场所：模块级节点 + 卡片排布 + 框选生成卡片 | 不做逐行阅读；不承诺自动生成"正确架构图" |
| **变换自由度** | 三个可切换维度：范围（scope）、观测态（view）、形态/位置（placement） | 不是"变换代码"；不是无限组合（每层有禁止项，见 §1.3） |
| **模块边界** | 显式的粗粒度边界（v1 用 crate 或一级目录），**不靠猜** | 不从 subject 前缀猜父子（HANDOFF §7 的教训） |
| **沙箱收缩** | 视图级隔离：把一块范围从大图摘出来单独研究；非关注部分默认折叠成摘要 | 不是进程/执行沙箱；不是删代码；不自动改代码 |

### 1.3 层级图（每层允许什么、禁止什么、为什么）

```
L0 单文件 ──► L1 多文件（同模块） ──► L2 单模块 ──► L3 跨模块/整项目
   卡  片        卡  片（并置）          卡  片            大 画 布
```

| 层 | 范围 | 允许 | 禁止 | 为什么 |
|---|---|---|---|---|
| **L0 单文件** | 1 个文件 | 结构（符号清单/数量/最近改动/作者/文档/判断状态）、观测态切换 | 跨文件调用图、依赖图 | 一屏放得下；一屏放不下的东西不该塞卡片 |
| **L1 多文件** | 2–N 个文件（**同一模块内**） | 并置对比（改动/符号/判断）、共享符号、差异 | 跨模块；超过 ~7 个文件 | 多文件的价值是"对比"，不是"更多" |
| **L2 单模块** | 一个 crate/一级目录 | 模块内文件清单、入口/出口、符号总数、模块级判断 | 跨模块；逐符号铺开 | 到这一层，卡片只给"目录级摘要 + 展开入口" |
| **L3 跨模块/整项目** | 全仓 | 大画布：模块级节点、卡片排布、框选→生成卡片、缩略 | 逐行细节、全量符号 | 复杂度跃迁：必须换载体（画布），否则卡片退化成信息堆砌 |

**跨层规则**：每层只回答该层能回答的问题；越层问题给"去上一层的入口"（如 L2 卡片里的"在画布中打开"），不硬答。

### 1.4 与 core 的映射（哪些字段喂卡片，哪些现在没有）

| core | 喂卡片哪一块 | 现状 |
|---|---|---|
| `judgment.verdict` | 卡片顶部"状态"（held/refuted/uncertain + reason） | ✅ 有（`ask`） |
| `judgment.kind` | 决定卡片区块：file/doc/symbol/decision | ✅ 有 |
| `judgment.scope` | 卡片标题的范围（objects/granularity/env） | ✅ 有；但 `time_window` 永远空 |
| `evidence.premise` | "为什么"的 2–3 条依据（commit/def/doc/record） | ✅ 有；**行号只能从 premise 解析**（`def:path:line:kind:at`） |
| `evidence.polarity` | 支持/反驳（红/绿点缀） | ✅ 有 |
| `alternative_of` | 决策卡片里的"考虑过的方案" | ✅ 有（仅 record 导入的 15 条） |
| `change` 表 | 改动次数、最近提交、作者 | ✅ 有（1921 条） |
| **符号间关系**（调用/引用） | 卡片里的"小结构图" | ❌ **没有**：symbol 判断只有"存在"证据，没有 edge 表 |
| **文件级依赖**（import） | 多文件卡片的连线 | ❌ **没有** |
| **符号 kind 分布**（fn/struct/…） | 卡片"符号 30（fn 18 / struct 6）" | ⚠️ 能凑：从 `def:…:<kind>` 依据解析，但脆弱 |
| **文档↔符号**关联（文档提到某符号） | "相关文档" | ❌ 没有：只有同路径 `doc:X` 与 `file:X` |
| **决策↔改动**（这条决策改了哪些文件） | 决策卡片的"影响面" | ❌ 没有：record 只按"提及路径"进 `scope.objects`，不绑 commit |
| **符号/文档历史** | 时间观测态 | ❌ 没有：`at` 是 mtime 快照，不是历史（见 B7 的诚实标注） |
| **LSP 实时语义**（类型/引用/诊断） | "实时"观测态 | ❌ 完全没有 |

> 缺口结论：**第一版卡片只能是"清单 + 状态 + 依据"，不能是"小图"**。画结构图需要 edge 数据，现在没有；硬画就是假图。

## 2. 思考

### 2.1 卡片路线能不能真的把一统图谱的难度分化掉？

**判断：能分化「读」的难度，不能分化「关系」的难度。**

- 一统图谱有两块难：①**数据**（符号/文件/模块之间的关系，我们只有"存在"没有"边"）；②**呈现与操作**（全量、布局、缩放、导航）。
- 卡片把 ② 降下来了（一次只看一个范围、只读、可关），但 ① 一点没解决——卡片若要画"结构"，照样得有边。所以：
  - **第一版卡片 = 清单/状态/依据**（无图），先把"读"跑通；
  - 图留给以后有 edge 数据时再做（LSP 的 references 是最现实的边来源）。
- **退化条件（什么情况下卡片会变成信息堆砌）**——四条，都是可判的：
  1. 单卡超过 ~7 个符号或 >3 层嵌套 → 没人读，等于把文件树竖过来；
  2. 打开 5 个卡片后每次查询 >200ms（每卡独立查询/刷新）→ 用户会关掉它们；
  3. 卡片之间没有同一坐标（不同 scope/时间口径混着看）→ 对比失真，等于没对比；
  4. 卡片只答"有什么"、不答"为什么/算不算数"→ 退化成"美化版文件树"，那用户不如用 IDE 自带 Outline。
- **反例**：如果用户真正想要的是"看清一个陌生项目的模块依赖"，卡片帮不上——那必须画布 + 边数据；卡片只能给"这个模块有多少文件/多少符号/最近动过什么"。

### 2.2 先例（凭已有知识，**T3 推断，未联网核实**）

- **IDE 的 Structure/Outline 工具窗**（IntelliJ Structure、VS Code Outline）：单文件结构卡片的最直接先例，成熟且被日常使用。
- **Minimap / Breadcrumbs**：证明"不占视野的角落"可行——它们只占一条边，且可关。
- **调试器的 Watch / Inline values、Jupyter inspector**：按需、单对象、只读、悬浮——与卡片同型。
- **代码评审的侧栏**（GitHub/GitLab 的文件树 + outline + diff）：在多文件层面用"并置"而不是"图"。
- **JetBrains 的 Diagrams、Sourcegraph 的面板**：有图但操作弱；它们的教训是"图好看但不常开"。
- 经验规律：**活得久的是"按需、单范围、只读、可关闭"**；死掉的是"一次性全量、不可操作、不更新"的一统图谱。
- 我不确定的部分：有没有产品把"卡片+画布"做成两级并在同一工具里长期共存（我印象里没有成熟先例，这条是猜测）。

### 2.3 「观测态」该定义成什么维度

**结论：观测态 = 同一范围的"看法"，由 4 个正交维度里**选 1–2 个**组合，不是一个大枚举。**

| 排序 | 维度 | 取值（v1） | 为什么这个顺序 |
|---|---|---|---|
| 1 | **粒度** | 文件 → 符号 → 行/块 | 最常用；数据全有（文件/符号/行号在 premise） |
| 2 | **时间** | 当前 / 最近 N 天 / 某次提交 / 决策日期 | `change.at`、`judgment.at` 全有；这是"过程动态"的落点 |
| 3 | **证据/可信度** | 只看 held / 含 uncertain / 展开依据链 | **本产品独有的差异点**（别家 Outline 没有"算不算数"） |
| 4 | **呈现** | 清单 / 摘要 / 决策叙事 | 是"样式"不是"维度"；放最后，避免把样式当观测态 |
| 5 | 角色/入口 | 入口函数 / 最近改动 / 有决策 | 需要关系数据（谁调谁），**暂缺**，第一版不做 |

排序理由：前两个有数据；第三个是差异化；第四个是表现层；第五个缺数据。**不要**把"缩放"叫观测态——缩放只是同一种看法的尺寸变化。

### 2.4 LSP：做客户端还是服务端

**裁决：做客户端（消费别人的 LSP），不做服务端。**

- 服务端要重造 rust-analyzer 级别的语义，必败；我们的差异化在"判断/证据/历史"，不在语言语义。
- 客户端能拿到：`textDocument/documentSymbol`（结构）、`definition`/`references`（**边的来源**）、`hover`（类型/文档）、`diagnostics`（错误）。这正好补 §1.4 的两个大缺口（符号关系、文件依赖）。
- 但 LSP 是**实时、无历史**的：只能给"现在"。所以 LSP 数据必须作为**一个观测态（"实时"）**，与 DB 的"历史"并列，并在卡片上标来源（`lsp` vs `db`）。**不许把 LSP 的"现在"混进判断的历史链**。
- 现实风险：rust-analyzer 启动慢、内存高（大型仓 1GB+）；第一版**不接**，只在 `explain --json` 里留 `lsp: null` 的位置，等卡片跑通再谈。

### 2.5 沙箱与收缩（回答用户的自问）

- **是视图级沙箱，不是执行沙箱**：框选一块范围 → 生成卡片 = 把这块从大图里"摘出来"单独研究，主画布保持全貌；不隔离进程、不改代码。
- **"向内收缩的编码部分自动生成收缩"**：读作"默认折叠 + 摘要，按需展开"——这与"加工过的观测态"是同一件事：每层给摘要，展开才见细节。
- 风险：如果"收缩"是自动推断（比如自动摘要代码），会引入"猜"；v1 只做**结构折叠**（按符号/目录折叠），不做语义摘要。

## 3. 最小切片（两周内能看见东西）

### 3.1 输入 / 输出

**输入**：一个文件路径 + 一份 `.jingwei` 库（现有）。**输出**：一个 5 行的只读卡片（终端 ANSI）。

```
crates/cli/src/main.rs                          held · 改动 14 次
符号 30（31 处定义：fn 20 / const 9 / static 2）  最近 2026-10-23 · hp
文档 无                                          依据 3 条
  commit:417009a1  def:crates/cli/src/main.rs:13:fn  ...
[t] 时间态  [s] 符号  [d] 决策  [q] 关闭
```

字段（3–6 行）：
1. 路径 + 状态（`ask` 的三值 + reason）；
2. 改动次数 + 最近一次（时间/作者）；
3. 符号数 + kind 分布（从 `def:…:<kind>` 依据解析）；
4. 文档状态（`doc:` 判断有无/verdict）；
5. 依据 2–3 条（commit/def/doc，可跳转的文本）；
6. 键位提示（切换观测态/展开/关闭）。

### 3.2 数据从哪来（现有命令/表；缺什么）

| 字段 | 来源 | 缺什么 |
|---|---|---|
| 状态 | `ask <path>`（compose） | — |
| 改动次数/最近/作者 | `change` 表（`changes_for`） | — |
| 符号数/kind | `judgment` symbol + `evidence.premise` 解析 `def:path:line:kind` | 没有独立的符号表/kind 字段；解析是**临时手段** |
| 文档 | `find_judgment("doc:<path>")` | 只能同路径，不能"文档提到这个符号" |
| 依据 | `evidence_for` | — |
| 时间态 | `change.at` / `judgment.at` | 符号/文档没有历史（mtime 快照） |

### 3.3 载体：两个方案与取舍

| 方案 | 做法 | 优点 | 缺点 | 裁决 |
|---|---|---|---|---|
| **A 终端卡片**（`jw card <path>`，纯 ANSI，无新依赖） | 5 行文本 + 键位；读一次库 | 两周内可见；零依赖；跨编辑器；可脚本化 | 不能真"角落"（只能分屏/浮动终端）；无鼠标；不跟随光标 | **第一版做这个** |
| **B 编辑器插件**（VS Code / RustRover 侧栏 WebView） | 插件读 `explain --json` 渲染卡片；能贴角落、跟随光标 | 体验真正"不占视野"；能接 LSP | 每个编辑器各写一份；发布/签名成本；两周只能做一个编辑器 | **第二版**，等 A 验证数据够用 |

> 折中不做：HTML 单页（`file://` 或本地 server）——能复用渲染，但嵌不进编辑器角落，且引入 server 生命周期问题；等插件方案时一起考虑。

### 3.4 验收（在 demo 上看到什么）

```
$ jw card crates/cli/src/main.rs
crates/cli/src/main.rs                    held · 改动 14 次
符号 30（31 处定义：fn 20 / const 9 / static 2）  最近 2026-10-23 · hp
文档 无                                    依据 3 条
  commit:417009a1  def:…:13:fn  …
[t] 时间态  [s] 符号  [d] 决策  [q] 关闭
```
> 真实数据（demo，T1）：`main.rs` 有 **30 条 symbol 判断、31 处定义**（一个重名：`setup_console` 两处定义）；kind 分布从 `def:…:<kind>` 依据解析。**卡片必须标注口径**（判断数 30 / 定义数 31），否则"符号 30"会被误解成 30 个定义。
- 同一命令在 `nope/x.rs` 上：`uncertain(no_data)`，不崩、exit 2；
- `jw card docs/README.md`：`文档 held`；
- `jw card "crates/cli/src/cmd_clean.rs#cmd_scan"`：状态 held + 符号 ≥1（修好的 `subject_path`）。

## 4. 第一版明确不做（砍掉清单）

| 不做 | 为什么 |
|---|---|
| 大画布 / 图标体系 | 复杂度跃迁，先把卡片跑通；图标要美术研究 |
| 多卡片联动 / 同步滚动 | 需要"多卡订阅 + 共享坐标"，第一版单卡 |
| LSP 接入（哪怕 references） | 启动/内存/生命周期成本高；先用 DB 数据验证卡片价值 |
| 符号依赖图 | **没有 edge 数据**；硬画画的是假图 |
| 时间轴动画 / 播放 | 时间态先用"最近 N 天"静态切 |
| 跨模块卡片 | 用户原话：最多一个模块；跨模块走画布（v2） |
| 编辑 / 改代码 / 执行 | 卡片只读；编辑留在编辑器 |
| 自动语义摘要 | 会引入"猜"；只做结构折叠 |

## 5. 与 B7 的关系

`explain / timeline / find` 是卡片的**数据底座**；卡片是它们的**视图**：
- `explain --json` = 单文件卡片的数据契约（B7.1 已排期）；
- `timeline --json` = 时间观测态的数据契约（B7.2）；
- `find` = 卡片里"跳转/展开"的检索入口（B7.3）。
所以 B7 照旧做，**卡片（`jw card`）排在 B7 之后**，作为 B8 的第一块。
