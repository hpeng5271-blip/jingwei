# D-20261022-01 · 测试失败怎么定位到行

**背景**：行号旁的诊断标记已经在吃编译器诊断（`check_project`）。测试失败也要能定位，
但测试输出是**自由文本**，不像编译器那样有稳定的 `file:line:col` 结构。

**决定**（2026-10-22，自己拍的，不等人确认）：

1. **只在能证明位置时才标行**：输出行里出现形如 `src/a.rs:12:3` 的片段，且该路径能对上
   项目里的真实文件（按后缀匹配），才在那一行打标记。
2. **对不上就不标**：路径认不出、或文件不在项目里 → 只保留原来的输出文本，**绝不猜行号**。
   宁可少一条标记，不许把人指到错的行。
3. **覆盖范围**：测试一跑就把上一轮测试的标记清掉（同一类结果互相覆盖）；编译器诊断不动。
4. **点击行为**与编译器标记一致：跳到该文件该行。

**为什么不做"更聪明的解析"**（比如解析 pytest / cargo test 的每种格式）：那要按框架各写一套，
而且框架一升级就错；`path:line` 是多种框架都认的子集，先把它做对。

**代价**：有些测试框架只在汇总里说"3 failed"，不打印位置——那种情况我们只给摘要，不给行号。
这是**诚实的缺失**，不是 bug。

**验收**：`tools/uitest.mjs` 里两条断言——认识的路径会出标记、不认识的路径不出标记。
