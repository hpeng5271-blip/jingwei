# 第一部分 · 它是什么，以及为什么是它

## 1.1 一句话

**终端与 IDE 之间的理解层。** 它不替你写代码，也不替你装环境；
它把「这个项目现在到底是什么状态」讲清楚，并且**在你需要的时候才讲**。

## 1.2 它填的那个空档

新手卡住的地方，通常不是"不会写代码"：

| 卡住的地方 | 谁该回答 | 为什么没人回答 |
|---|---|---|
| 这台机器上装了什么，够不够跑这个项目 | 环境探测 | IDE 假定你已经装好了 |
| 报错一屏，**先修哪一个** | 信息过滤 | 终端一律平铺，不分主次 |
| 改了代码，说不清改了什么、影响了什么 | 变更与图谱 | 版本控制管"文件变了"，不管"关系变了" |
| 环境越装越乱，磁盘越来越满，不敢删 | 清理 | 清理教程不区分"能删"和"别碰" |
| 忙了两天，说不清做了什么 | 记录 | 没有一个地方替你留痕 |

IDE 和终端不是不会这些，是它们**不负责筛**：所有信息一律平铺，新手只能被淹没。

**这个工具的全部价值就是两个字：过滤。以及紧跟着的反馈。**

## 1.3 四条不许破的线

这四条写进代码（类型、构造入口、断言），不是写在文档里靠自觉：

| 线 | 实现里的抓手 | 守它的测试 |
|---|---|---|
| **数据正确优先**（先于速度、延迟、首屏） | `store::apply_file_update` 的四步事务 | `a_bad_row_rolls_back_the_whole_batch` |
| **不生成修复命令** | `fix.rs` 只做"补一行忽略规则"这种答案唯一且可逆的事 | `fix` 6 条 |
| **无自查不报错** | `Conclusion` **字段私有** + 唯一构造入口（内含三道闸） | `an_error_without_a_self_check_is_downgraded` |
| **关系必有来源** | `Edge::new` 的 `source` 是必填参数——没来源的关系**造不出来** | `illegal_node_pairs_cannot_be_constructed` |

## 1.4 三态：最核心的一条线

`Verdict<T>` 分 **是 / 不是 / 查不了**。它不是体验优化，是**事实表述的准确度**：

> 「没找到 Python」和「机器上没装 Python」不是一句话。
> 前者是**我们的结论**，后者是**对世界的断言**——而后者我们无权给出。

这条线从内到外贯通三个层次，任何一层断了，纪律就退化成"希望大家记得"：

```
model::Verdict          类型层：三态是类型，不是布尔
      ↓
Envelope{state,reason,data}   外壳层：yes / no / unknown
      ↓
unpack() → 按 state 分三支    界面层：unknown 绝不显示成"没有"
```

判据一句话：**这是"用户的空白"，还是"我们的失败"？**
用户自己创建的东西（配置档、笔记）空 = 正常（`yes` + 空数组）；
系统里本该存在的东西（Python、编辑器、硬件）空 = 异常（`unknown` + 为什么）。

## 1.5 边界：永久不做，与暂时不做

**永久不做**（写进设计 §1.1）：编辑器内核 / 编译器 / 包管理器 / 版本控制 / 调试器内核 /
一键修复 / 插件系统 / 远程 API / 多租户 / 云同步 / 全量索引 / 通用知识图谱。

其中内置编辑器有一条**说死的上限**：

> 只做「打开 → 看 → 改 → 存 → 能回滚」这五件事，不再往补全、跳转、重构、调试上投一分钱。
> 要"成熟"就**外跳**（`open_in` 交给用户自己的 IDEA / VSCode）。
> 判据：**它的功能上限是"让用户不必为了看一眼而开 IDEA"。**

**暂时不做**（每条带触发条件，**没有无条件的 TODO**）：

| 暂不做 | 触发条件 |
|---|---|
| LSP 集成 | M1–M6 完成且 tree-sitter 管线稳定（判据：连续 3 次 `cargo test --workspace` 全绿，且 `collect_facts` 采到的"解析不完整符号数"= 0） |
| 第二种语言 | 第一门做通之后；**判据是"加一门语言只许改 `lang.rs` 一处"**（实测现在是 5 个文件 8 处分支，这条债记在账上） |
| 跨项目知识库 | 单项目图谱连续三个月自己每天在用 |
| AI 集成 | 图谱本身已经能被人类读懂（人读不懂，AI 更读不懂） |

> 为什么"加语言只许改一处"这条判据重要：它**可判定**。
> 原来写的是"不需要改 engine"——那是一句无法判定的口号，所以它一直是假的（P8 实测抓出来的）。

# 第二部分 · 架构与实现

## 2.1 依赖方向：靠编译器，不靠自觉

```
cli / src-tauri  --→  engine  --→  model
                        -
                        ---→  tools/schema.sql（编译期 include_str!，DDL 唯一真源）
```

**实测双向依赖 0 对**。而且不是靠转发假装单向——拆的时候**调用点全部改成了指向下层**
（Q6 抓出 3 对真循环：`probe↔ccpp`、`probe↔jvm`、`project↔rules`，
根因是"工具与类型混在了编排文件里"，拆法是把 `which`/`run_cmd` 下沉到 `winutil`、
把 `Finding`/`Severity` 上移到 `model`）。

## 2.2 engine 的分层（L0–L6，七层；分层进了代码结构，不只写在文档里）

```
L0 util     纯工具，不懂业务      winutil · dlog · textfile · parallel · scan · jobobj
L1 sys      机器与系统           machine · mem · native · clean
L2 detect   探测（拿事实）        probe · jvm · ccpp · deps · editors · envsetup · profiles · lang
L3 understand 项目理解（出结论）   project · projects · contract · rules · diag · fix
L4 graph    图谱（存与查）        store · parse · index · resolve · imports · envelope
L5 state    项目状态（可回滚）     changes · snapshot · workcopy · runs · notes · scaffold · watch
L6          launch（编排）
```

**箭头只许从上层指向下层。** 层名用"这一层在干什么"（detect / understand），
模块名用"它是什么"（probe / project）——**因为层名与模块名撞在一起过**
（层叫 project、模块也叫 project.rs，于是 `crate::project::scan` 指不清是谁）。

**这条分层原来只写在《复审记录》里，没进代码结构**（R2 记的"没兑现"之一）。
重建时把它落成了目录：**光看文件在哪，就知道它该依赖谁。**

## 2.3 一次调用的完整数据流

前端最常走的那条（`inspect`）：

```
前端 invoke('inspect', { root })
  -- src-tauri::inspect_payload
       -- notes::migrate_legacy    旧 jsonl 搬成笔记（不搬的话老项目显示"一篇都没有"——那是假象）
       -- snapshot::load_latest    上一次的快照（用来比"变了什么"）
       -- probe::make_facts        采事实（内含 lang 探测 → jvm / ccpp / web 探测）
       -- deps::rust_tree / web_tree   传递依赖树（只读一份 lock，很便宜）
       -- rules::run_all           出结论（三态 + 抑制 + 聚合都在这里）
     → 组装 JSON 回前端
```

图谱那条支线：

```
目录 → collect_rust_files（过 should_skip 那道闸）
     → 三级检测（大小+时间 → 内容哈希）决定重不重解析
     → parse::parse_rust（tree-sitter；错误门控给 complete）
     → store::apply_file_update（一个事务四步：失效旧关系 → 删旧符号 → 写新的 → 记状态）
     → resolve::resolve_file（全局解析：只有唯一命中才连边）
```

## 2.4 领域模型：13 实体 / 16 关系

| 实体 | 说明 |
|---|---|
| `Project` `File` `Module` `Symbol` | 代码的骨架 |
| `Dependency` `Toolchain` | 依赖与工具链 |
| `Diagnostic` `Rule` | 结论，与产生它的规则 |
| `Contract` | 环境契约（一条龙执行的依据） |
| `Note` `Commit` `Snapshot` `Run` | 记录类 |

**关系两端合法矩阵**（`EdgeKind::allows`）是关键：只允许下表出现的组合，
越界的边**在构造时就失败**（返回 `IllegalPair`，里面带着是哪三个值）。

> 没有这张矩阵，一个拼错的组合（比如 `Note -calls-> File`）会安静地进库，
> 然后在某次查询里变成一条读不懂的结果。

| 关系 | 两端 |
|---|---|
| `contains` | Project→File · Module→{Module,File,Symbol} · File→{Symbol,Dependency,Diagnostic} |
| `defines` | File / Module → Symbol |
| `implements` | Symbol → Symbol |
| `calls` / `references` | Symbol → Symbol |
| `depends_on` | Dependency→Dependency · File→Dependency |
| `needs` | Dependency → Toolchain |
| `diagnosed_at` | Diagnostic → {File,Symbol,Module} |
| `reported_by` | Diagnostic → Rule |
| `causes` / `affects` | Diagnostic 相关 |
| `noted_at` | Note → {File,Symbol,Module,Dependency,Diagnostic,Run} |
| `changed_at` | Commit → {File, Symbol} |
| `snapshotted_at` | Snapshot → 任意 |
| **`produced`** | **Run → Diagnostic** |
| `follows` | Run → Contract |

**三条构造规则**：

1. `Edge::new` 强制两端合法——不合法**构造不出来**。
2. `Edge::new` 强制有来源——`source` 是必填参数。
3. **读路径不校验**：`Edge::from_row` 故意不做矩阵校验——历史数据可能写在规则变更之前，
   **读取必须能原样还原**。

### 标识规则：位置不是身份

```
id = "<kind>:<规范化 key>"
symbol:src/lib.rs#Ledger::post      ← impl 里的方法带容器路径
file:src/engine/lib.rs              ← 路径类实体：小写、斜杠统一
```

**规范化只对位置类实体做。** 这条是测试当场抓出来的：原来对任何 key 都跑 `normalize_path`，
而它最后一步是全小写——于是 `Ledger::post` 变成 `ledger::post`。
但 Rust **大小写敏感**，`Ledger` 与 `ledger` 是两个不同的类型；小写化会让它们
**静默地撞成同一个节点**（后者覆盖前者，不报错）。

> 判据：**文件系统大小写不敏感，所以路径小写；语言的标识符大小写敏感，所以原样保留。**

而且 **id 里不含行号**：方法往下挪两行还是同一个符号。
否则每次编辑都会造出一堆"新符号"，图谱就没法和历史比。

# 第三部分 · 数据层（为什么这么设计）

## 3.1 DDL 只有一份，而且是**文件**

```
tools/schema.sql   ← 唯一真源（能跑、能校验、能被 include）
   --- tools/db_probe.py          读它建库压测（数字因此可复跑）
   --- crates/engine/src/graph/store.rs   include_str! 同一份
   --- 数据层设计.md §3            引用它，只解释"为什么"，不贴副本
```

**为什么从文档里搬出来**：贴着的 SQL **既不能被执行也不能被校验**。
实测把三处设计改掉之后，文档里那份副本没跟着改，于是同一份表结构有了
**两个互相矛盾的版本**（Q1 记过这笔账）。

## 3.2 六张表 + 一个视图 + 一张 FTS 表

`meta`（元信息：schema 版本、上次索引时间）· `nodes` · `edges` · `files` · `index_runs` · `query_cache`
（加 FTS5 外部内容表 `nodes_fts`、视图 `live_edges`）

| 决定 | 为什么 |
|---|---|
| `edges` 用 `WITHOUT ROWID` + 复合主键 `(src,dst,kind)` | 点查与浅层遍历最快 |
| 反向索引是**部分索引** `(dst,kind) WHERE expires_at IS NULL` | 失效边不参与查询计划 |
| `kind` / `source` 的取值用 `CHECK` 写死 | 写错一个立刻失败，而不是留下一条"幽灵关系" |
| 时间一律 INTEGER 毫秒 | 排序快、无时区歧义 |
| `nodes.data` 只放该类独有字段 | 核心查询永远走真列，永远可索引 |

**索引是"先枚举访问路径，再配索引"定出来的**（不是拍脑袋）：

| # | 查询 | 走哪个索引 | 实测 |
|---|---|---|---|
| Q1 | 按 id 取节点 | 主键 | 0.00ms |
| Q2 | 列某文件的某类节点 | `(file_path,kind)` | **0.03ms**（只有 `kind` 单列时 24.27ms） |
| Q3 | 某节点的出边 | 主键 | 0.00ms |
| Q4 | 某节点的入边（谁调用了我） | `(dst,kind) WHERE expires_at IS NULL` | 0.00ms |

**被否掉的索引**（想建但明确不建）：`nodes(name)`、`edges(src,confidence)`、
`nodes(updated_at)`、`edges(expires_at)`、`edges(src,kind)`（主键已覆盖）。

## 3.3 四条守漂移的测试

枚举在 Rust 里、取值在 SQL 里——这是"同一事实两个副本"最容易炸的地方，
而且炸的方式特别难受：**不是编译错，是第一次往库里写东西时 CHECK 拒绝，还多半炸在别人机器上。**

| 测试 | 守什么 |
|---|---|
| `ddl_kind_lists_match_the_domain_enums` | DDL 里两处 `kind` 的取值 == `NodeKind::ALL` / `EdgeKind::ALL`（**含顺序**） |
| `ddl_source_lists_match_the_source_enum` | `source` 的取值 == `Source::ALL` |
| `ddl_version_stamp_matches_the_constant` | DDL 末尾写进 `meta` 的版本号 == `store::SCHEMA_VERSION` |
| `ddl_executes_and_live_edges_filters_expired` | DDL 真能建库；失效边被 `live_edges` 挡掉；非法 `kind` 写不进去 |

**它们第一次跑就抓到了漂移**：`edges` 的 CHECK 顺序与 `EdgeKind::ALL` 不一致。
内容相同、顺序不同——CHECK 的行为不受影响，所以**它永远不会以 bug 的形式暴露**。

## 3.4 写入：一个文件的更新是一个事务，四步

```
1. 先把这个文件产生的旧关系标失效（例外：noted_at / changed_at 是历史，不失效）
2. 删掉不再存在的符号（它们带着自己的边一起被外键级联清掉）
3. 写入新的节点与边（UPSERT；命中的旧关系在这一步复活）
4. 记下这次的文件状态（大小、mtime、内容哈希、节点数）
```

**顺序不是随便定的**：

- 少了第 1 步 → "上个月删掉的那次调用"会永远留在图谱里冒充当前状态
  （UPSERT 只复活命中的，**不清理没命中的**）；
- 少了第 2 步 → 改过名的项目会在图谱里越攒越多已经不存在的符号；
- **四步必须在一个事务里** → 半途失败会让图谱停在"旧关系已失效、新关系还没写"，
  看起来像"这个文件什么都没引用了"，**而且不报错**。有测试盯着
  （`a_bad_row_rolls_back_the_whole_batch`）。

## 3.5 失效与历史：关系不删，只标

- **关系不删，只标 `expires_at`**：一条关系"曾经存在过"本身是信息。
- **清理必须显式**，但 `noted_at` / `changed_at` **永不清理**——那是历史，不是派生数据。
  所以清理 SQL 里那条 `NOT IN` **不是可选项**：写成"清掉所有过期的"就等于把笔记和提交记录
  一起删了，**而且不报错**。有测试盯着（`purge_never_touches_notes_or_commits`）。
- **查询只走 `live_edges` 视图**：失效边在**语法上**就查不到，
  不需要每个调用点记得写 `WHERE expires_at IS NULL`。

## 3.6 承载力（实测，不是估的）

```
体积 ≈ 行数 × 185 字节（含索引与 FTS），两个规模点线性、无拐点
10k 文件 / 20 符号 → 410,000 行 → 74.6 MB
20k 文件 / 20 符号 → 820,000 行 → 153.2 MB
"50 万节点 + 200 万边" → 约 460 MB
```

**复跑命令**：`python tools/db_probe.py`（默认 10k 文件）、`--files 20000` 更大。

**两个规模点的对比结论**：查询延迟**不随规模退化**（0.00–0.03ms 量级不变），
体积线性增长。**所以瓶颈不在数据量**，而在（a）递归 CTE 的深度、（b）索引选错、（c）长事务。

# 第四部分 · 解析与图谱（最核心的那部分）

## 4.1 路线：索引期只记事实，解析放到后面

这一条不是自己想的，是**把 GitHub 的 stack-graphs 读完之后**按实际情况落下来的。
别人的原话是：

> "Because we must rely on incremental results, it's important that at index time we look at
> **each file completely in isolation**. Our goal is to extract **facts** about each file...
> and **all possible things that each reference could resolve to**."

**这三句话纠正了原来的做法**。第一版是"在索引期就尝试解析调用"——只能解析同文件里的裸标识符。
那不是"简化版"，是**方向错了**：一旦跨文件就永远做不到，而且每加一种语言都要重写一遍解析逻辑。

| 阶段 | 做什么 | 为什么分在这边 |
|---|---|---|
| **索引期**（每文件独立） | 只记**事实**：这里有个定义、这里有个引用，引用的是**名字** | 为了**增量**——文件之间不许互相依赖，否则改一个文件要重算一片 |
| **解析期**（全局） | 把"名字引用"解析成"确定的关系" | 只有这一步才需要看到全图；它可以慢慢做、可以缓存、可以只做查得到的那部分 |

**"所有可能解析到的候选"这一条，正好接上三态**：

| 解析结果 | 落成什么 |
|---|---|
| 唯一命中 | `calls` 边，置信度语法层（0.85） |
| **命中多个** | **不猜**——记 `ambiguous`（名字 + 位置），由界面决定要不要显示 |
| **一个都没有** | **外部符号**（标准库、别的 crate）——**不是错误** |

> **一条假边比一条缺边糟得多：缺了只是图不全，错了是图在骗人。**

## 4.2 作用域是**栈**，不是"当前在哪个函数"

第一版 `RefFact` 只记了"在哪个函数里"。**那不够**——真实的作用域是**嵌套**的
（函数 > 块 > 闭包），而且有**遮蔽**（内层同名遮蔽外层）。

stack-graphs 的把这件事编码成"图上的 push/pop 节点 + 搜索时维护符号栈"。
我们抄它的**形状**：

| 它的做法 | 我们的简化版 |
|---|---|
| 索引期建"作用域图"（push/pop 节点） | 索引期给引用记一条**作用域链**（从内到外） |
| 查询期路径搜索 + 符号栈保证遮蔽正确 | 解析期**从内往外找第一个匹配**——这就是遮蔽规则的直接实现 |
| 明确记"might resolve to"（候选） | 同样：解析不出来时**记候选，不猜** |

**还有一条必须抄的是它的"诚实"**：它连"这个仓库里确实有那个文件"都说了，
但**仍然坚持在索引期忽略它**——因为一旦偷看，增量就破了。

## 4.3 错误门控：不是理论，是必须做的

**实测过**：源码里有一个写坏的函数（`fn broken( { }`）时，`has_error = true`，
而符号抽取**照样把 `broken` 抽了出来**。

所以"能不能建关系"**只能看 `complete`，不能看抽到几个符号**。
不这么做的后果很具体：图谱里会出现一个"存在但根本编译不过"的符号，
然后"这个函数在哪定义"给出一个不存在的答案。

## 4.4 闭包也是符号（学 SCIP 的 `Descriptor.Suffix.Local`）

`let has = |s| ...` 之后那句 `has("x")` 是个**调用**，而它指向的东西在图谱里根本不存在
——于是解析期只能说"拿不准"。实测里 `launch.rs` 一口气贡献了七条这样的"拿不准"，全是同一个闭包。

**建成**：新增 `collect_closures`——**只收闭包不收普通 `let`**。
要回答的是"谁调用了谁"，而能被调用的局部绑定只有闭包；把每个 `let x = 5` 都塞进图谱，
只会让图变胖而不解决任何问题。

**效果**：拿不准 **45 → 11**，符号 1088 → 1128（+40 个闭包），边 1623 → 1694。

## 4.5 两条把"拿不准"清零的关键修复

**① 路径的参照系不同（藏得很深）**

符号 id 里的路径是相对**索引根**的（`crates/engine/src/util/winutil.rs`），
而 `use` 推出来的路径是相对 **crate 根**的（`util/winutil.rs`）——**两个路径的参照系不同**，
全等比对永远对不上。

**而每一步单看都是对的**：use 抽对了（单测过）、逻辑对（单测过）、接线对（查过），
所以光看代码找不出来。**改成后缀匹配**（按整段路径比，不做宽松包含），
并且**多个命中就不猜**。

**② crate 根的模块文件叫 `main.rs` / `lib.rs`，不叫 `mod.rs`**

这一条是**图谱自己抓出来的**：把 CLI 外壳按领域拆成 `cmd_*.rs` 之后，
那些文件里写的 `use super::{c, pad, ...}` 全部报"没接上"——而 `super` 指的正是 crate 根。

**这条的价值不在"11 变成 0"，而在于：缺口是工具自己报出来的，
不是靠人逐个去读那些文件看出来的。**

## 4.6 "自己的漏接"不许伪装成"外部符号"

`external` 涨到 4155 个时，那个数字**没法判断图是不是真的全**——
因为它把"标准库"和"我们漏了"加在了一起。

**改法**：分成两类独立出口：

- `unmapped_imports`：**写了 `use` 却没接上**——这是**我们自己的漏接**，不许伪装成"外部"；
- `namespace_mismatch`：名字在图谱里、但不在值命名空间——调用点写错了，或者命名空间判断没跟上。

**建完立刻见效**：自己索引自己时报出 6 处，全是真问题（`super::` 3 处、裸路径 1 处、
crate 名路径 2 处）；补上相对路径解析之后 **6 → 0**，连上 18 → 24。

## 4.7 命名空间是白捡的确定性

《Rust Reference》说"名字被分进不同的命名空间，让不同命名空间里的实体可以同名而不冲突"。

所以 `foo()` 这个**调用**只该在**值命名空间**里解析——同名的 struct / trait / mod 根本不该进候选。
**少了这一条，拿不准里有相当一部分是白白拿不准的**（不是真的分不清，是压根没看名字的种类）。

**值命名空间 = `value` + `local`**（闭包是能被调用的局部绑定）。

## 4.8 图谱可视化：先验证渲染栈，再动手

**验证什么**：canvas 到底画不画得动那张图。这是唯一一个"做不到就真的做不到"的瓶颈。

**怎么验的**：把**经纬索引自己**的真实图谱导出来，用 canvas 画它，在真浏览器里量帧率。

| 规模 | 帧率 | 布局 | 绘制 |
|---|---|---|---|
| 1054 点 / 3162 边 | **153 fps** | 3.2ms | 0.2ms |
| 1054 点 / 9486 边 | **149 fps** | 3.0ms | 0.4ms |
| 1054 点 / 25296 边 | **145 fps** | 3.0ms | **0.9ms** |

**三条结论**：

1. **canvas 完全够用**——25000 条边只要 0.9ms。"几千个节点会卡死"是 **DOM 的问题**，
   不是 canvas 的问题：DOM 里每个点每条线都是一个元素，canvas 只有一次。
2. **下一个瓶颈是布局，不是渲染**：朴素 O(n²) 力导向 1000 点 3ms，
   按平方关系 5000 点会到 ~75ms。真要做几千点的全图，布局得换 Barnes-Hut
   或放 Rust 侧算；**邻域图（几十到几百点）完全没问题**。
3. **一条方法论上的坑**：同一份代码在 **headless 浏览器**里只有 5–44 fps，
   有头模式 145–155 fps，**差 30 倍**（软件渲染 + rAF 节流）。
   → **性能验证必须在有头模式下做**，否则量到的是环境的极限，不是代码的。

**为什么这张图不该是首页**：信息密度太高，第一次打开的人看不懂。
首页仍然是"这个项目卡在哪"。**图谱是钻进去看的东西。**

# 第五部分 · 信息管线（产品的价值在这里）

## 5.1 五步，顺序不可换

```
事实(facts) → 规则(rules) → 过滤(七步) → 结论(四要素) → 呈现(分级)
```

## 5.2 过滤七步

| 步 | 判据 | 不许发生 |
|---|---|---|
| ①去重 | `rule_id + 参数指纹` 相同只留一条 | 同一件事报三遍 |
| ②抑制下位 | 上层根因未解 → 下位不出卡 | 根因下面挂 20 条连锁 |
| ③聚合 | 同文件 + 同错误码 → 一簇 | 同一个错刷满屏 |
| ④分级 | 红=挡运行 / 黄=不挡路 / 灰=进度 / 白=静默 | 用颜色装饰 |
| ⑤排序 | 层序 → 严重度 → 位置 | 按时间倒序（会埋掉根因） |
| ⑥容量 | 一行 ≤6 · 一卡 ≤3 · 一屏 1 结论 | 一屏 20 条 |
| ⑦静默 | <0.1s 的操作不出提示 | 点一下就弹通知 |

**过滤系统必须自带两个出口**（P6 抓出来的）：

1. **时间出口**：被压下的东西，根因解决后要**自动浮回来**（不是"永远不再提"）；
2. **位置出口**：任何被隐藏的，都要能在**一个固定位置**查到——
   问题栏底部固定一行「另有 N 条被上层挡住 · 查看」。

> ⚠️ **这两条至今没有实现（2026-10-16 核实）。** 上面写的是**设计要求**，不是现有行为。
> 事实是：**根本没有"抑制下位"这个机制**——`Level::Silent` 在整个仓库里
> **零个构造点**（已删），所以**没有任何东西被压下**，两个出口也就无从谈起。
>
> 这不是"忘了做"，而是**做了一半就停了**：级别枚举里有那个变体、四份文档写了那行字
> （`使用说明.md` / `V0.md` / `复审记录.md` 都提过），而抑制逻辑一次都没写。
> 于是发生的是**同一形状事故的第 5 次**：**决定记在文档上，代码里什么都没发生**——
> 只不过这次反过来，是**文档承诺了一个不存在的界面**，而用户会去找那一行字。
>
> **要真正做它，验收判据是这三条一起**（缺一条就会重演）：
> ① 抑制真的发生（有构造 `Silent` 的地方）；② 被抑制的能在固定位置查到；
> ③ 根因修好后自动浮回来。**在那之前，文档别承诺它。**

> 「信息过滤」这个词本身有陷阱：它听起来是"砍掉多余的"，
> 但真正难的是**砍掉之后怎么让人相信没丢东西**。

## 5.3 四要素：每条结论给四样

```
看到的事实      带数字、带来源（哪个文件 / 哪条命令看出来的）
你自己怎么验证   一条能复制粘贴的命令
什么时候不用管   边界（避免把正常写法当错）
下一步         能自动做的给按钮；要你决定的只给建议；**不生成修复命令**
```

**"无自查命令，不许报 Error"有测试守着**（`no_rule_can_ship_an_unverifiable_error`：
真跑一遍全部规则，不管哪条触发都不许有"没有自查命令的错误"漏出去）。

## 5.4 排查链：九层，顺序就是方法

规则按"层"排，**层序不是排版偏好**（⑨ 是项目卫生那一层，它不属于"跑不起来"的排查链，
但规则表把它接在同一串里，所以这一串是九层）：

```
① 机器扛不扛得住        内存、磁盘够不够——比"东西装没装"更底层
② 东西有没有            这台机器上有没有能干活的那件东西
③ 用的是哪个            东西有好几个，实际被用起来的是哪一个，以及为什么是它
④ 谁在背后改它          环境变量和转发壳会在看不见的地方改变结果
⑤ 项目说要什么          项目自己声明的要求，和实际之间的差
⑥ 缺什么                声明要的东西装没装
⑦ 隔离开了没有          多个项目共用一套环境，迟早互相踩
⑧ 什么时候变的          环境一直在变；只有"之前能跑现在不能跑"时它才是证据
⑨ 项目卫生              和语言无关的日常维护
```

**为什么这个顺序**：环境类问题，答案几乎总落在"实际用的是哪个"和"谁把它设成这样的"这两层里，
而不是"重装一遍试试"。

## 5.5 一条最容易犯的错：把"无法确认"压成"没有"

P3 抓到过一处真的：`deps_status: BTreeMap<String,bool>` 被三处消费
（发给前端 / 规则判断 / 变更比对）。C++ 项目里"查不到"的包，到这两处就变成 `false` = **缺失**；
规则会照着"缺失"报，界面会照着"未安装"显示。

**这就是这套系统最不能犯的错。** 修法是给 `deps_status` 加废弃告警并指向三态的 `deps_detail`。

# 第六部分 · 一条龙与外壳

## 6.1 六个阶段里，只有前四个跟语言有关

| 阶段 | 谁来决定 | 落点 |
|---|---|---|
| 1–4 环境 / 契约 / 依赖 / 运行时 | **按项目语言分家** | `launch/python.rs` · `node.rs` · `java.rs` |
| 5 拉起进程、6 等待就绪 | **只有一处实现** | `launch.rs`（进程树、输出读取、内存采样、就绪判定、运行记录） |

**这条边界是拿一个真事故换来的**：拿 Python 那条路去开一个 Vue 项目，
用户看到的第一句话是「没有可用的 Python，无法启动」——**答非所问比不回答更糟**，
它会把人引到错的方向上。

**用途是四种，不是一个布尔量**：`Run` / `Task`（测试）/ `Build` / `Install`。
这条是修一个真 bug 换来的：把"装依赖"混进"跑个任务"，Node 项目上会让
「补装依赖」那个按钮去跑 test 脚本——**用户点的是安装，跑的是测试**。

## 6.2 就绪判定的两条判据

**① 常驻服务的判据是「输出里出现监听地址，且那个端口真的连得上」**

- **为什么不按框架名单猜**：Vite 打 `Local: http://localhost:5173/`、
  Next 打 `ready - started server on 0.0.0.0:3000`、`python -m http.server` 打
  `Serving HTTP on 0.0.0.0 port 8000`、Spring Boot 打 `Tomcat started on port(s): 8080 (http)`
  ——说法完全不同，而**名单里没有的那个**（用户自己写的服务、刚出的框架）会被判成"没起来"。
- **为什么光看到地址不算**：`Error: connect ECONNREFUSED 127.0.0.1:3000` 里也有地址。
  **把失败报成成功比报成失败糟得多。**

**② 到点了进程还活着但没判出就绪**：Node / JVM 报**注意**（dev server 本来就不退），
Python 报失败（脚本跑不完通常是卡住了）。且措辞分开——
"看到过地址但端口连不上"与"压根没报地址"是两种处境。

## 6.3 外壳：工作区是画布，卡片只用来浮

- **代码区是画布**（无边框无圆角）、**结构树是工具窗**，两者之间一条发丝线；
- 圆角、描边、阴影**只给浮层**：查找栏、提示条、通知、弹窗；
- **绝不用卡片包住工作区**——一旦包住，就在视觉上拒绝了"上面还能叠东西"。

**依赖工具窗按 Maven 读法组织**：工具条（筛选 / 重载 / 补装）→ 分组（未安装 / 已安装，带计数）
→ 每行两列「声明 → 实际」，悬停给来源，行尾给下游数量（可展开传递树）。

**视觉语言六条**（自研，只借 IDEA 的"信息组织"不借它的皮）：
三层面靠明度差分层 · 悬停按下是在原底上叠半透明 · 面里掺一点主色 ·
同心圆角 · 圆角三档（6 / 10 / 14px）· 分隔线能不用就不用。

**动效的三条硬规矩**：

1. 三档时长 `100 / 170 / 260ms`，由设置改写；
2. **不许动会触发 layout 的属性**（`width`/`height`/`top`/`left`/`margin`/`padding`/`font-size`），
   位移一律走 `transform`；**颜色类允许过渡**（只触发重绘）。
   > 这条原来写的是"只动 transform 与 opacity"，而实测有 30 多处颜色过渡。
   > 原话太窄，等于逼着人天天违反它——**规矩要么改准，要么就是橡皮筋。**
3. **跟随系统的"减少动效"**（`prefers-reduced-motion`）——这是无障碍要求，不是偏好
   （前庭功能障碍的人会被位移动画弄晕）。

**反馈分档**：<0.1s 静默 / 0.1–1s 不打断 / >1s 显式进度。

## 6.4 编辑器：冻结在"够用的窗口"

只做「打开 → 看 → 改 → 存 → 能回滚」，**改动先进草稿，点「应用」才落盘**，
应用前那一版留在 `.jingwei/drafts/`。

两条实测出来的性能约束：

- **只给看得见的那几十行上色**：3000 行全文上色 65ms，而它原来挂在每次按键上——
  打一个字卡一下。改成窗口化后，文件多大都是 2–4ms。
- **重活往后排**：打字时只更新脏标记、行列、光标位置；行号重画与重新上色
  延后 110ms 跑一次（`edPaintHeavySoon`）。

**为什么必须有**：看不了文件就断了工作流，用户会被迫在两套工具之间反复横跳，
每横跳一次掉一次上下文。

# 第七部分 · 系统管理

## 7.1 环境探测：写"来源清单"，能问的就不猜

**判据**：**"装了"是用户的事，"我们找到了"是我们的事。**
少列一个来源就是一次误报，而误报是这个项目最不许犯的错。

| 工具链 | 来源 | 判定 |
|---|---|---|
| **Python** | 14 条（环境变量双读 / 契约 / 项目内 venv / PATH / `LOCALAPPDATA` 三处 / `C:\Python3xx` / **`py -0p`** / scoop / conda 两处 / pyenv-win / `.local/bin` / 便携目录） | 好 |
| **Java** | 11 条（`JAVA_HOME` / PATH / 六类发行版目录 / `.jdks` / `.sdkman` / 便携目录 / `.java-version` / `~/.m2/toolchains.xml`） | 中 |
| **C / C++** | 3 类（PATH / 便携目录 / **`vswhere`**） | 中 |
| **Web / Node** | 随 `web.rs` 补上（`package.json` / 锁文件 / `packageManager` 字段 / `node_modules` 布局 / `.nvmrc` / `engines`） | 中 |

**三条规矩**：

1. **有官方查询命令的，一律去问，不许猜路径**：`py -0p`、`vswhere.exe`、`node -v`。
2. **"故意不进 PATH"的安装方式必须单独列**：pyenv-win 的 versions、IDEA 的 `.jdks`、
   VS 的 MSVC、便携版 SDK 目录——**"装了却说没装"的高发区**。
3. 找不到时说"我在这些地方都没找到"，**而不是"没装"**。

**一个具体的教训**（写在这里因为它是一类问题的通用形状）：

> 一个**字段**装不下，不等于**这个来源**装不下。
> 当时为此绕道写了 `DeviceIoControl`，结果在那台机器上被系统拒了（err=5）；
> 而同一棵注册树里就有 `FriendlyName`，21 个字符一个不少。
> **别急着换更重的路子，先看完这棵树。**

## 7.2 机器清单：多源印证，不许挑顺眼的

一个事实**带来源**；来源对不上时**把分歧摆出来**：

```rust
pub struct Fact { pub key: String, pub value: String, pub sources: Vec<String> }
```

| 纪律 | 怎么来的 |
|---|---|
| CPU 型号读**两个来源**（注册表 + CPUID 品牌串） | 注册表那份是 Windows 抄的，CPUID 是 CPU 自己报的；对得上才敢说"就是它" |
| 内存走 **SMBIOS**，不走 WMI | WMI 在这台机器上要 **20 秒**一次 |
| 硬盘型号走**设备描述符**，不走注册表 `Prod_` | 那是 SCSI 产品标识、**固定 16 字节**：`UMIS RPEYJ1T24MKN2QWY` 被截成 `UMIS RPEYJ1T24MK`。**这种"看起来完全正常"的截断，光靠自己发现不了** |
| 系统设置**只挑影响开发的几项** | 不读 VC++ 运行库（缺了别的程序会自己报错）、不读 Defender 排除项（那是安全决定，不是性能决定） |

**实时采样与清单是两件事**：`spec_report()` 回答"这台机器**是什么**"（读一次可以慢，要准）；
`Sampler` 回答"此刻**在忙什么**"（差分求瞬时值，要快）。状态栏只显示后者，且字段刻意少而准。

**明确不读的**：性能跑分、温度、风扇转速——那些要装驱动或提权，
而"这台机器跑不跑得动这个项目"不需要它们也能回答。

## 7.3 清理：先探后删，只列不替人决定

| 区分 | 做法 | 为什么必须 |
|---|---|---|
| **能删 / 要权限 / 别碰** | 三区，界面照这个分组 | 混在一起就是"一键全清"——灾难的入口 |
| **回收站 / 永久** | 默认走回收站（`FOF_ALLOWUNDO`） | 误删可恢复是底线 |
| **建议删 / 只列出来** | 日志、空目录**只列不建议** | **留不留只有项目自己知道** |

**"先探后删"是 Windows 逼出来的**：删一个正被占用着的东西，Windows 上不是干脆失败，
而是**部分成功**——目录删了一半，剩下的是夹生饭。

> 探测本身还有个坑：不能用 `OpenOptions::new().write(true)` 去试——
> Rust 的 std 打开文件时**默认带 `FILE_SHARE_READ | FILE_SHARE_WRITE`**，
> 于是"再打开一次"永远成功，**探测等于没探**。这里要求独占（`dwShareMode = 0`）。

**安全闸**：盘根、系统关键目录、`.git`、`.jingwei`、用户目录本体，一律不放行。

## 7.4 笔记：是记录，不是文档编辑器

- **给固定的几类，不给空白框**（新手最缺的不是自由格式，是"我该记什么"的提示）；
- **一篇坏了不许毁掉整本**（读不了的跳过，别的照常）；
- **删除只是搬进 `.trash/`**——自己写的字不该被一次误点抹掉；
- **文件是给人看的**：一篇一个 Markdown、文件名带日期、中文留着。
  **换来**能被任何编辑器打开、能用 git 管、能在文件管理器里找到。

**老格式的迁移**：早期把记录塞在一个 `jsonl` 里，第一次打开时搬过来，
然后把旧文件改名成 `.migrated`——**不删**。搬不完、搬重了都有痕迹可查。

| 次 | 记下了什么 | 而门禁上什么都没发生 |
|---|---|---|
| P3 | "已修：打开 `let_underscore_must_use`" | 那个 lint 只在一个 crate 里生效，engine 里 22 处吞 Result 一处都没被拦 |

**所以留下的最值钱的东西不是那几十条修正，是这条规矩**：

> **每一条安全类与正确性类决定，必须同时留下一个"能失败的东西"——**
> 一条测试、一条 lint、或门禁脚本里的一条断言。

> 这和"引用级数字不许当预算"是同一类错——**把"我以为它在那儿"当成了"它在那儿"**。

## 8.4 三处"描述了一个不存在的机制"

注释描述不存在的机制，**比没有注释更糟**：读的人会以为自己改一处就够了。

1. `model` 的测试注释写着"DDL 的 CHECK 子句由 `ALL` 生成"——**那个机制不存在**，

2. 设计 §3.3 的验收标准写着"加第三种语言时如果 engine 一行都不用改"——**实测要改 5 个文件 8 处分支**。

3. 设计 §11 写着"`std::fs::rename` 不是原子操作，一律走 `MoveFileExW`"——

# 第九部分 · 工程规矩（决定它活多久）

## 9.1 工具怎么用：PowerShell 只负责"跑"，不负责"写"

这一条是**拿五次真事故换来的，全发生在一天之内，全是同一个来源**：拿 PowerShell 当文件编辑器用。

| 踩的坑 | 症状 | 为什么 |
|---|---|---|
| `` .Replace("...`r`n...") `` | 文件里出现**字面量** `` `r`n `` | 反引号转义只在双引号里解析 |
| `[IO.File]::ReadAllText('相对路径')` | 找不到文件 | .NET 用**进程工作目录**，不是 PowerShell `cd` 之后的目录 |
| `git show HEAD:path > file` | 写出 **UTF-16** | PowerShell 的 `>` 默认 UTF-16 |
| 脚本按"第一个 `}`"找函数结尾 | 把下一个函数也切走了 | 嵌套 `match` 里全是大括号，**不能靠数括号** |
| 没有 BOM 的 `.ps1` 里写中文 | 中文连同引号一起烂掉，脚本变成语法错误 | PowerShell 5.1 按 ANSI 读没有 BOM 的 `.ps1` |

**规矩三条**：

1. **改文件用补丁工具**——它按行匹配，不经过 shell 的转义层；
2. **要写多行脚本，就先写一个脚本文件**，再让 PowerShell **只运行它**；
3. **脚本本身保持纯 ASCII**，中文全部放进 UTF-8 数据文件（`tools/gates.json` 的注释里写着这条）。

> **一句话**：PowerShell 是"跑命令"的通道，不是"写文件"的编辑器。

## 9.2 动 git 之前先看 `git status`

这一条是拿**两次真丢工作**换来的：

> 用 `git checkout -- <file>` 当"撤销上一次改动"用——它撤销的是**这个文件上所有未提交的改动**。

更值钱的一次是**一笔提交其实是不完整的**：`git add crates/engine/src/launch`
只加上了 `launch/` 目录，`launch.rs` 本体没进去——于是 `mod java;` 不在，
**`launch/java.rs` 根本没被编译**，而提交信息里写着"实测 6 阶段全过"。

> 这是**「看起来对、其实没生效」**那一类坏数据，比"错的"更难发现。

## 9.3 那三条元规矩

1. **同一事实只允许有一个可编辑副本。**
2. **引用级与估算级数字不许当预算**（指标必须带出处）。
3. **每条安全类与正确性类决定，必须留下一个"能失败的东西"。**

**这句话目前还没有被自动检查**——它是整个系统里唯一一处"元层面的裸奔"。

## 9.4 错误怎么表达（两类，不许混）

| 情形 | 表达方式 |
|---|---|
| **前置条件不成立**（项目不存在、契约不是合法 JSON、命令缺失） | 返回 `Err`（`anyhow` + context） |
| **读到了一部分**（某个文件读不了、某项查不了） | 照常返回结果，把缺口写进结果的字段（三态 `unknown` / 说明文本） |

**判据**：**整件事没做成 → Err；做成了一部分 → 结果里说清缺了哪部分。**
绝不允许出现第三种：**把失败吞掉、让结果看起来是完整的**。
