# 经纬 · 数据层与数据库设计

> 这份文件**取代 `设计.md` 的第 5 节**（存储设计），作为数据层的唯一依据。
> 写法：先枚举访问路径，再定索引；每条决定后面跟着**在本机真 SQLite 上跑出来的数字**。
>
> 实测环境：**SQLite 3.53.4**（Python 标准库自带），WAL + `synchronous=NORMAL`，
> 单库 1,210,000 行（10k 文件 / 200k 符号 / 200k 边）。每张表的数字都可用本文给的语句重跑复现。

## 0. 三处修正 + 两处新增

在真库上跑了三轮，**被真实约束和真实查询计划各抓了一次**。相对上一版：

| # | 改动 | 是什么逼出来的 |
|---|---|---|
| 修正 1 | **写入必须是 UPSERT**，不是裸 INSERT | 实测：同一条 `(src,dst,kind)` 重复插入直接 `UNIQUE constraint failed`——而增量重跑时重复产出同一条边是常态 |
| 修正 2 | **加复合索引 `(file_path, kind)`** | 实测："列某文件的符号" **24.27ms → 0.03ms（约 800 倍）** |
| 修正 3 | **深度上限从经验值变成实测值** | 实测：稠密菱形图上递归 CTE 按路径数膨胀（3 跳 40 行 / 6 跳 1,093 行 / 8 跳 9,841 行）→ 4 跳以上走 Rust BFS |
| 新增 1 | `nodes.checksum` + `files` 表 | 抽样校验要"上次算出的哈希"当基准，否则无从比对 |
| 新增 2 | `meta` 的迁移与自检字段 | FTS5 是外部内容表，**它的同步状态必须能被查**，不能假设 |

**技术选型不变**：仍是 SQLite 单文件、扎根项目（理由与实测见 §11）。

## 1. 设计原则（每条都有代价）

1. **先枚举访问路径，再设计索引**。每条索引都要能指名它服务哪个查询。
   代价：写变慢、库变大（我们写少读多，划算）。
2. **约束交给数据库，判断交给代码**：唯一性、外键、非空、枚举取值写进 DDL；
   "这条关系可不可信"由 Rust 类型守。代价：改约束要走迁移。
3. **只增不改，失效标记**：历史必须留得住。
4. **写入幂等**：同一个文件重解析两次，结果必须一样。
5. **"确认不了"必须能表达**：库里允许"值未知"，代码里用三态呈现。

## 2. 标识（ID）规则

**决定**：`id = "<kind>:<规范化 key>"`，例如 `file:src/engine/lib.rs`、
`symbol:src/engine/lib.rs#Ledger::post`、`dependency:cargo:serde`。

> **前提（Q11 补写，原文没写）**：小写化成立于**大小写不敏感的文件系统**，
> 也就是本工具唯一支持的 Windows。换到 Linux/macOS，`Foo.rs` 与 `foo.rs` 是两个不同的文件，
> 小写化会让它们**撞成同一个 id**——而"同一个东西只有一个节点"这条特性会把这件事
> 变成静默的数据丢失（后者覆盖前者），不报错。
> 所以：**要支持跨平台，这里必须先改**（按平台决定是否小写），而不是"反正 Windows 上没事"。

| 规则 | 做法 | 为什么 |
|---|---|---|
| 路径规范化 | 反斜杠→正斜杠、去 `./`、小写 | Windows 大小写不敏感；同一文件的两种写法必须同 id（实测幂等） |
| 符号 key | 相对路径 + `#` + 容器路径 + 名字 | 同名符号在不同文件/不同 impl 里必须区分 |
| 依赖 key | `<生态>:<包名>` | 同一个包在 cargo 与 npm 里是两回事 |
| 不用自增主键 | 全部自然键 | **自增键在重跑索引时会漂**，而反复重跑正是核心玩法 |

**冲突处理**：两个不同实体算出同一 id 时会被主键拦下——**这是特性**（同一个东西只有一个节点）。
真正的冲突靠 key 规则解决（key 必须带容器路径）。

## 3. 物理模型

> **可执行的 DDL 只有一份：`tools/schema.sql`。** 本节讲"为什么这么设计"，不再贴 SQL 副本。
>
> 为什么搬进文件：贴在这里的那份**没法被执行也没法被校验**。实测把三处设计改掉之后，
> 这个副本没跟着改，于是同一份表结构有了两个互相矛盾的版本（Q1 记过这笔账）。
> 现在：`tools/db_probe.py` 读它建库压测，Rust 侧将来 `include_str!` 同一份，
> 本节只负责解释。**改表结构 → 改文件 → 跑探针**，三步固定。

### 3.1 建库（顺序即初始化顺序）

PRAGMA 设定（WAL / `synchronous=NORMAL` / `foreign_keys=ON` / `busy_timeout=5000` /
`wal_autocheckpoint=400` / `cache_size=-2000` / `temp_store=MEMORY`）。

**为什么 `NORMAL` 而不是 `FULL`**：WAL 下 NORMAL 保证**库不会损坏**，
只可能丢"掉电前尚未 checkpoint 的那几笔提交"。而索引数据是可重算的派生数据，丢了下一轮补回来；
真正不可丢的是笔记正文，那条路径单独 `wal_checkpoint(PASSIVE)` 走 FULL 语义。
**代价**：多写一段代码，只服务于"记笔记"。

### 3.2 核心两表

`nodes`（id 主键 / kind / name / file_path / line / language / data / source /
confidence / checksum / created_at / updated_at）

`edges`（src / dst / kind / source / confidence / created_at / expires_at，
主键 `(src,dst,kind)`，`WITHOUT ROWID`）

**四条决定与代价**：

1. **`CHECK` 把枚举写死**（kind 取值、source 取值、confidence 范围、line>0）：
   写错一个 kind 立刻失败，而不是留下一条"幽灵关系"。代价：加关系类型要迁移——这是想要的摩擦。
2. **时间用 INTEGER 毫秒**：排序比较快、无时区歧义。
3. **`edges` 用 `WITHOUT ROWID` + 复合主键**：点查与浅层遍历最快（实测正向 1 跳 0.00ms）。
   代价：按单列 id 查不方便——不需要。
4. **`confidence` 存 REAL，三档语义在 Rust 侧**（`Confidence::{Certain,High,Guessed}`）；
   库里只管范围合法，"估的不许报 Error"由类型守。

### 3.3 三张支持表

| 表 | 作用 | 关键列 |
|---|---|---|
| `files` | 增量检测与校验的落脚点 | path 主键 / size / mtime_ns / content_sha / parsed_at / incomplete |
| `index_runs` | **索引证据**（扫了什么、跳过什么、为什么） | started_at / finished_at / scanned / skipped / incomplete / skip_json |
| `query_cache` | 热点查询物化 | k 主键 / v / created_at / invalidated_at |

## 4. 访问路径 → 索引（这一节是全文最值钱的部分）

**先列出系统里真会跑的查询，再给它配索引。** 实测来自 §0 那套 1.21M 行的库。

| # | 查询（谁在用） | 执行计划要点 | 服务它的索引 | 实测 |
|---|---|---|---|---|
| Q1 | 按 id 取节点（到处） | 主键点查 | `nodes` 主键 | **0.00ms** |
| Q2 | 列某文件的某类节点（结构树、诊断按文件聚合） | `SEARCH nodes USING INDEX idx_nodes_file_kind (file_path=? AND kind=?)` | **`(file_path, kind)`** | **0.03ms**（只有 `kind` 单列时 **24.27ms**） |
| Q3 | 某节点的出边（1 跳正向、调用链起点） | `SEARCH edges USING PRIMARY KEY (src=?)` | `edges` 主键 | **0.00ms** |
| Q4 | 某节点的入边（谁调用了我） | `SEARCH edges USING INDEX idx_edges_dst (dst=? AND kind=?)` | **部分索引 `(dst,kind) WHERE expires_at IS NULL`** | **0.00ms** |
| Q5 | 多跳遍历（≤3 跳） | 递归 CTE，每步走主键 | 同 Q3 | 0.02ms |
| Q6 | 全文搜符号（搜索框） | FTS5 虚表扫描 + 主键回表 | `nodes_fts` | **0.02ms** |
| Q7 | 各 kind 计数（状态栏、统计） | 覆盖索引扫描 | `(kind)` | 11.02ms（20 万行，可接受） |
| Q8 | 打开文件列它所有类型节点 | 同 Q2 的前缀匹配 | `(file_path, kind)` | 0.03ms |

**最终索引清单（多一条都不要）**：

- `idx_nodes_file_kind`：`nodes(file_path, kind)` —— 服务 Q2 / Q8（**实测关键**）
- `idx_nodes_kind`：`nodes(kind)` —— 服务 Q7
- `idx_edges_dst`：`edges(dst, kind) WHERE expires_at IS NULL` —— 服务 Q4 / Q5

**被否掉的索引**（想建但明确不建）：

| 想建的 | 为什么不建 |
|---|---|
| `nodes(name)` | 模糊查走 FTS5、精确查走 id；建了会拖慢每次写 |
| `edges(src, confidence)` | 从没出现过"按置信度筛边"的查询 |
| `nodes(updated_at)` | 时间序需求由 `files` / `index_runs` 承担 |
| `edges(expires_at)` | 失效边占比极低，部分索引已覆盖 |
| `edges(src, kind)` | **主键 `(src,dst,kind)` 已经覆盖它**——上一版多建了这条 |

## 5. 写入路径（幂等是硬要求）

**决定：所有事实写入都是 UPSERT，且包在事务里。**

节点：`INSERT ... ON CONFLICT(id) DO UPDATE SET` 更新可变字段（name/file_path/line/language/
data/source/confidence/checksum/updated_at），**保留 `created_at`**。

边：`INSERT ... ON CONFLICT(src,dst,kind) DO UPDATE SET confidence/source, expires_at=NULL`
——**重跑命中的关系要"复活"，而不是报错**。

**实测**：单事务灌 1.21M 行（含 100 万次边 UPSERT）**12.25s**（≈10 万行/秒）。
**幂等的价值**：我故意用会重复的生成器，边数停在 **200,000** 而不是 1,000,000——重复产出不涨库。

**事务边界三条**：

1. 一个文件的全部节点与边 = **一个事务**（要么整个文件进去，要么完全没进去）
2. 失效标记与新关系插入 = **同一事务**（不许出现"新旧都在"或"新旧都不在"）
3. 全量索引分批提交，**每批 ≤2000 文件**，批间可中断

**并发**：SQLite 是**单写者**——所以**一个写连接 + N 个读连接**，写连接永不查询；
写连接 `busy_timeout=5000`；读连接 `PRAGMA query_only=1`；
**读连接不许开长事务**（长读会把 checkpoint 挡住）。

## 6. 失效与历史

**决定：关系不删除，标 `expires_at`。** 重跑时 UPSERT 把命中的边复活（`expires_at=NULL`），
没被重新产出的边自然留在过期状态。

清理必须显式（否则库一直涨）：每次索引结束后删一次「过期超过 30 天的边」。

```sql
DELETE FROM edges
 WHERE expires_at IS NOT NULL
   AND expires_at < ?1
   AND kind NOT IN ('noted_at', 'changed_at');
```

**代价**：丢掉"曾存在过"的记录。**换来**：库不会无限增长。
**边界**：`noted_at`（笔记附着）与 `changed_at`（提交）**永不清理**——那是历史，不是派生数据。
所以上面 SQL 里那条 `NOT IN` **不是可选项**：它是这条边界唯一的落点。
写成"清所有过期的"就等于把笔记和提交记录一起删了，而且**不报错**。

**实现状态（Q11 核对）**：这段**还没做**——`store` 里目前只有 `expire_edge`。
它属于 M2 收尾（施工第 1 步），触发条件：库第一次被反复重建（也就是 M3 接图谱之后）。

## 7. 全文搜索（FTS5 外部内容表 + 三个触发器）

**决定**：`nodes_fts` 用 `content='nodes'`（外部内容，不重复存文本），同步靠
**AFTER INSERT / AFTER DELETE / AFTER UPDATE 三个触发器**。

**实测**：搜唯一名 0.02ms；删节点后 FTS 自动清干净；`count(nodes_fts) - count(nodes) == 0`。

**两个必须记住的坑**：

1. **外部内容表不会自己同步**。少一个触发器，搜索就会返回"已经不存在的符号"——
   **它不报错，只让用户搜到幽灵**。
2. 删除必须用 `'delete'` 魔法行（`INSERT INTO nodes_fts(nodes_fts, ...) VALUES('delete', ...)`）；
   在外部内容模式下直接 `DELETE FROM nodes_fts` 会报错。

**自检（启动时 + 每次索引后）**：

- `INSERT INTO nodes_fts(nodes_fts) VALUES('integrity-check');`
- `SELECT (SELECT count(*) FROM nodes_fts) - (SELECT count(*) FROM nodes);` —— 必须为 0

**重建**（只在自检失败时）：`INSERT INTO nodes_fts(nodes_fts) VALUES('rebuild');`

**降级边界**（**只在换成动态链接 SQLite 时才可能触发**）：§13 已定用 `rusqlite` + `bundled`，
FTS5 是自带的，正常路径上不会缺。这段守的是方案 ② 那条退路——那时 `winsqlite3.dll`
的版本不确定。真缺了：**禁用搜索并在界面上说明**，不许静默失效
（对应 §7 开头"真实空 vs 缓存空"那条原则）。

## 8. 一致性自检（"数据不错"的落地）

| 检查 | 命令 | 时机 | 不通过怎么办 |
|---|---|---|---|
| 库完整性 | `PRAGMA integrity_check` | 启动、每次索引后 | 从备份恢复；无备份则重建 |
| 外键一致 | `PRAGMA foreign_key_check` | 每次索引后 | 删孤儿边 |
| FTS 同步 | §7 两条 | 每次索引后 | `rebuild` |
| 抽样重算 | 抽 1% 文件重算哈希与节点数 | 每 50 次增量 | 重建受影响子树 |
| 索引证据 | `index_runs` 有本次记录 | 每次索引 | 没记录就不算索引成功 |

**抽样判据**：抽中的文件要同时满足两条——

1. `files.content_sha` 与磁盘当前内容一致；
2. `files.nodes_count` 与「重新解析一遍数出来的节点数」一致。

只比第 1 条的话，检查器会漏掉一整类错：**文件没变，但图谱错了**
（写库时漏了一批、或者上轮崩在commit之前）。第 2 条就是专门抓它的。

**两个不同的东西，别再混成一个**（Q11 更正——原文这里是错的）：

| 字段 | 层级 | 管什么 |
|---|---|---|
| `files.nodes_count` | **文件级** | 这个文件解析出了几个节点 |
| `nodes.checksum` | **行级** | 这个节点自身内容的指纹（种类 + 名称 + 签名）|

原文写的是"新增 `nodes.checksum` 就是为了比对'节点集合'"——那是**拿行级字段当文件级用**，
抽样校验根本落不了地（一行存"整个集合的哈希"？说不通）。
文件级的那一列已经在 `schema.sql` 里补上了。

## 9. 迁移框架

**决定：只允许向后兼容的迁移，且必须可回滚。** `meta.schema_version` 是唯一版本真相源。

| 变更类型 | 做法 | 代价 |
|---|---|---|
| 加列 | `ALTER TABLE ADD COLUMN ... DEFAULT ...` | 旧代码忽略新列，安全 |
| 加表 / 加索引 | `CREATE ... IF NOT EXISTS` | 幂等，可重复跑 |
| 改 CHECK 取值范围 | **必须重建表**：新建 → 迁数据 → 删旧 → 改名，全程一个事务 | 慢，但只在加关系类型时发生 |
| 删列 | 不允许（先标废弃，两个版本后再删） | 库略大 |

**"重建表"到底怎么写**（Q11 补——原文只有一句话，照着做不出来）：

```sql
PRAGMA foreign_keys = OFF;          -- 改名顺序会被外键挡住，必须先关
BEGIN;
  CREATE TABLE nodes_new ( …新的 CHECK… );
  INSERT INTO nodes_new SELECT … FROM nodes;
  DROP TABLE nodes;
  ALTER TABLE nodes_new RENAME TO nodes;
  -- 索引与触发器**随旧表一起没了**，必须原样重建（这一步最容易漏）
  CREATE INDEX  IF NOT EXISTS idx_nodes_file_kind …;
  CREATE TRIGGER IF NOT EXISTS nodes_fts_ai …;   -- 三个都要
COMMIT;
PRAGMA foreign_keys = ON;
INSERT INTO nodes_fts(nodes_fts) VALUES('rebuild');   -- 不能漏，见下
```

**这里有一个真坑**：`nodes` 一重建，`nodes_fts` 的外部内容指向就断了
（`content_rowid` 指的还是老 rowid）——**而它不报错**，
只是搜出来的是旧的、或者干脆搜不到。所以最后那句 `rebuild` 不是收尾动作，是**必需的一步**。
（这也是"外部内容表不自己同步"这条在 §7 的第二个面。）

**流程**：`VACUUM INTO` 备份 → 开事务 → 按序迁移 → 更新 `schema_version` → 校验 → 提交；
任何一步失败**回滚并保留备份**（实测 1.21M 行导出 73MB，几秒）。

## 10. 增长与保留（不设策略，库只会一直涨）

| 数据 | 增长速度 | 保留策略 | 实现状态（Q11 核对）|
|---|---|---|---|
| `nodes` / `edges` | 1.2M 行 ≈ **77MB**（含索引） | 常驻；文件删除靠 FK 级联 | ✅ 级联在 DDL 里 |
| `edges` 过期行 | 每次大改签名可能留几百条 | 30 天后清（§6，带 `NOT IN` 例外） | ⬜ 待做（M2 收尾）|
| `nodes_fts` | 约为被索引列的 30–40% | 随 nodes 级联 | ✅ 触发器已建 |
| `index_runs` | 每次索引一行 | 保留最近 200 次 | ⬜ 待做（M4，那时才真有索引轮次）|
| `query_cache` | 每种查询模式一行 | 失效即删；上限 500 行 | ⬜ 待做（M2 收尾）|
| **项目里的文件快照** | 每次"应用"前留一版 | 每个文件保留最近 **20** 版 | ✅ `snapshot.rs`（`KEEP = 20`）|
| **运行记录 `runs.jsonl`** | 每次跑一行 | 保留最近 **60** 条 | ✅ `runs.rs`（`KEEP = 60`）|

**两处澄清（Q11 补，原文含糊）**：

1. 原文说的"环境快照 保留最近 30 条"**在代码里找不到对应物**。
   实际存在的是两个不同的东西：**文件快照（20 版，`snapshot.rs`）** 与
   **运行记录（60 条，`runs.rs`）**——它们的数字都不是 30。
   写下真实数字，免得下次有人照着 30 去改代码。
2. **`runs.jsonl` 不在这张表里本该有的位置**——它不在 SQLite 里（是项目内的 jsonl），
   所以它的保留策略谁都不管。这里把它登记进来，是因为**"没有归属的策略 = 没有策略"**。

**容量模型（实测校准过，两点线性，无拐点）**：

用 `tools/db_probe.py` 在两个规模上各测一次（同一套 DDL、同一批查询）：

| 规模 | 行数 | 库体积 | 字节/行 |
|---|---|---|---|
| 10k 文件 / 20 符号每文件 | 410,000 | **74.6 MB** | 182 |
| 20k 文件 / 20 符号每文件 | 820,000 | **153.2 MB** | 187 |

**结论：体积 ≈ 行数 × 185 字节**（含索引与 FTS），线性，没有拐点。
行数 ≈ `文件数 + 符号数 + 边数`。

**体积组成**（820k 行那次实测）：nodes 表 46% · edges 表 22% · 三个索引 19% · FTS5 12%。

**按这个模型换算（边/符号按 4 估算）**：

| 项目 | 行数 | 库体积 |
|---|---|---|
| 小（1k 文件 / 20 符号） | ~101k | ≈ 19 MB |
| 中（10k 文件） | ~410k | ≈ 76 MB |
| 大（20k 文件） | ~820k | ≈ 153 MB |
| **"50 万节点" + 200 万边** | ~2.5M | **≈ 460 MB** |

> ⚠️ **这条修正来自 P4 复验**：上一版写"50 万节点 ≈ 30–40 MB"——**实测比例下差了 4–10 倍**。
> 原估算是按"每 1000 文件 8MB"外推的，而真正决定体积的是**行数**，不是文件数。
> **50 万节点时已是 460MB 量级**：那时该重新审的是页缓存（`cache_size`）、
> `VACUUM` 代价与是否需要把 FTS 拆成独立库——**不是换 SQLite**。

**维护动作**：每次索引后 `wal_checkpoint(PASSIVE)`（实测 `TRUNCATE` 只要 8ms，勤做无妨）；
库内空洞率高时做 `VACUUM`（全库重写，谨慎）。

## 11. 承载力结论（实测）

| 指标 | 实测 |
|---|---|
| 批量 UPSERT（executemany，单事务） | **≈10 万行/秒**（1.21M 行 12.25s） |
| 逐条 UPSERT（每条一次 execute） | ≈1.5 万行/秒（820k 行 56.7s）——**这个数是脚本瓶颈，不是 SQLite 的** |
| 库体积 | 410k 行 **74.6 MB** · 820k 行 **153.2 MB**（≈185 字节/行，线性） |
| 点查 / 1 跳 / FTS | 0.00–0.03 ms（**两个规模点上都一样**，无退化） |
| 复杂遍历（8 跳稠密图） | 9,841 行 / 2.8 ms，**随深度指数涨** |
| `integrity_check` | ok |
| FK 级联 | 删 1 个符号 → 相关边立即消失（孤儿边不可能存在） |
| `VACUUM INTO` 备份 | 74.6 MB → **0.29s** · 153.2 MB → **0.49s** |
| `wal_checkpoint(TRUNCATE)` | 8–11 ms |

**两个规模点的对比结论**：查询延迟**不随规模退化**（0.00–0.03ms 量级不变），
体积**线性增长**（≈185 字节/行）。**所以瓶颈不在数据量，而在**（a）递归 CTE 的深度、
（b）索引选错、（c）长事务——这与 §4（先枚举访问路径再配索引）和 §7（按跳数分工）的判断一致，
而且现在有两个规模点撑着，不再是单点外推。
**复现方式**：`python tools/db_probe.py`（默认 10k 文件）、
`python tools/db_probe.py --files 20000`（大一点）。
脚本只用系统自带 Python + 标准库，不装任何东西。
**建库语句读的是 `tools/schema.sql`**（Q3 起）——所以"脚本与设计同源"这件事
不再是靠人记得同步，而是**同一份文件**：改表结构 → 改 `schema.sql` → 探针自动跟上。
唯一还需要人守的是：**改完要跑一次探针**，确认数字没坏。

**结论**：这套模型在 **50 万节点内是宽裕的**。真正的瓶颈不在 SQLite，而在
（a）递归 CTE 的深度，（b）索引选错，（c）长事务——三者都已在设计里给出对策。

## 12. 不做（免得以后有人再加回来）

- **不换图数据库**：50 万节点内 SQLite 更快、更小、更绿，且图库破坏"单文件扎根项目"
- **不做跨库 JOIN / 联邦查询**：一个项目一个库，边界写清
- **不做分布式 / 云同步**：隐私与复杂度双重代价
- **不给 `nodes.data` 建索引**：一旦需要按它查，说明该字段该升成真列
- **不允许读连接写库**：读连接一律 `PRAGMA query_only=1`

## 15. 实体与类型的充分性审计（能不能当地基）

**方法**：不看清单看能力。把系统**承诺过的每一条能力**拿出来，逐个问
**"用初版那 9 种实体 / 10 种关系，能不能表达出来"**。表达不出来，就是缺口。

### 15.1 逐条核对

| # | 系统承诺的能力 | 现有模型能否表达 | 结论 |
|---|---|---|---|
| 1 | 扫盘、列文件、按文件看节点 | `Project` + `File` + `contains` | ✅ |
| 2 | 符号级结构（函数/结构体/trait/impl） | `Symbol` + `defines` + `contains` | ✅ |
| 3 | **多层级下钻：项目 → 模块 → 文件 → 符号** | ❌ **没有"模块"这个实体** | **缺口 1** |
| 4 | 调用链、谁调用了谁 | `calls` + `references` | ✅ |
| 5 | **"这个符号实现了哪个 trait"** | ❌ `calls`/`references` 表达不了 | **缺口 2（关系）** |
| 6 | 依赖：声明 → 实际、传递树、运行时/开发期 | `Dependency` + `depends_on` | ✅（`depends_on` 两端都允许 `Dependency`） |
| 7 | **M/D/U 三表里的 M：机器上有什么工具链** | ❌ 工具链不是实体，只是 engine 里的 facts | **缺口 3** |
| 8 | **七窍玲珑：环境事实 × 语义事实交叉归因** | ❌ 环境侧无节点，交叉无从建边 | 由缺口 3 引起 |
| 9 | 真实编译错误进图谱、按文件聚合 | `Diagnostic` + `diagnosed_at` | ✅ |
| 10 | **诊断要能追溯到"哪条规则判的"** | ❌ **没有 `Rule` 实体**（规则表是可自定义的知识资产） | **缺口 4** |
| 11 | 根因与影响面 | `causes` + `affects` | ✅ |
| 12 | **契约（env.contract.json）：一条龙执行的依据、人改过要保住** | ❌ **契约不是实体** | **缺口 5** |
| 13 | 运行记录、退出码、症结 | `Run` | ✅ |
| 14 | 运行的进程树（Job Object 管的那棵树） | 用 `Run.data` 存 JSON 摘要即可 | ⚠️ 有意不进图谱（进程是瞬时的，不是资产） |
| 15 | 变更：某次提交改了哪些文件 | `Commit` + `changed_at`（Commit→File） | ✅ |
| 16 | **某次提交里"某个符号"被改了** | 关系类型够（`changed_at` 两端允许 Commit→Symbol），但**没有写明允许** | 需补"两端合法矩阵" |
| 17 | 笔记挂在结构节点上 | `Note` + `noted_at`（→ File/Symbol/Module…） | ✅（但依赖缺口 1 才能挂到模块） |
| 18 | **快照对比两次差异** | ❌ 十关系里**丢了 `snapshotted_at`**，快照指不回对象 | **缺口 6（关系）** |
| 19 | 全文搜符号 | FTS5 | ✅ |
| 20 | 生态（跨项目：同一个包在三个项目里都有问题） | 现在**明确不做**；但 `dependency:cargo:serde` 这种**生态级 key 已经为将来留好了门** | ⚠️ 有意留白 |

### 15.2 缺口清单（按"不补会怎样"排）

| 缺口 | 是什么 | 不补的后果 | 怎么补 | 代价 |
|---|---|---|---|---|
| **1. `Module`** | 逻辑模块（≠目录） | 多层级下钻断一层；笔记挂不到模块 | 加实体 `Module`；由 tree-sitter 的 `mod`/目录惯例 + LSP 共同识别 | 需要"模块边界识别"规则（已在空架构里列过） |
| **2. `implements`** | Symbol → Symbol(trait) | Rust 的结构性关系缺一块；"谁实现了这个 trait"答不出 | 加关系 `implements` | 迁移要重建 `edges`（改 CHECK） |
| **3. `Toolchain`** | 机器上的工具链（路径/版本/来源） | 七窍玲珑少一半；"这个依赖需要哪个工具链"建不了边 | 加实体 `Toolchain`；`Dependency`—`需 要`→`Toolchain` | 工具链随机器变，要定 TTL（放进 `expires_at`） |
| **4. `Rule`** | 判定规则（可自定义） | 诊断无法追溯到规则；"规则表管理"没有落点；用户改了规则图谱不知道 | 加实体 `Rule` + 关系 `reported_by`（Diagnostic→Rule） | 规则条目要稳定 ID（`rule:no-cargo-in-path@v1`） |
| **5. `Contract`** | 契约声明（含 manual 名单） | 一条龙执行在图谱里不可见；"人改过的字段"飘在图外 | 加实体 `Contract` + 关系 `follows`（Run→Contract） | 契约是单例，每个项目一个节点 |
| **6. `snapshotted_at`** | Snapshot → 任意实体 | 快照只是文件，没法按对象对比差异 | 补回这条关系 | 无（本来就在旧版里） |

### 15.3 修正后的最终清单

**实体 13 种**（原 9 + 4）：

1. `Project` 2. `File` 3. **`Module`** 4. `Symbol` 5. `Dependency`
6. **`Toolchain`** 7. `Diagnostic` 8. **`Rule`** 9. **`Contract`**
10. `Note` 11. `Commit` 12. `Snapshot` 13. `Run`

**关系 17 种**（原 10 + 5 + 2）：

1. `contains` 2. `defines` 3. **`implements`** 4. `calls` 5. `references`
6. `depends_on` 7. **`needs`**（Dependency→Toolchain） 8. `diagnosed_at`
9. **`reported_by`**（Diagnostic→Rule） 10. `causes` 11. `affects`
12. `noted_at` 13. `changed_at` 14. **`snapshotted_at`** 15. **`follows`**（Run→Contract）
16. `produced`（Run→Diagnostic） 17. **`registers`**（File→Symbol，装饰器注册，2026-10-19 D-02）

**一条纪律**：这份清单的每一次增长都必须经过 §15.1 那种"能力 → 能不能表达"的核对，
不许因为"顺手"而加。**加得越容易，模型糊得越快**——所以下面是硬矩阵。

### 15.4 关系两端合法矩阵（防模型糊掉的关键）

只允许下表出现的组合；不在表里的组合**编译期就不该构造得出来**（`Edge::new` 做类型检查）。

| 关系 | 允许的 src → dst |
|---|---|
| `contains` | Project→File · Module→Module · Module→File · Module→Symbol · File→Symbol · File→Dependency · File→Diagnostic |
| `defines` | File→Symbol · Module→Symbol |
| `implements` | Symbol→Symbol（trait） |
| `calls` | Symbol→Symbol · **File→Symbol**（仅 `if __name__ == "__main__"` 块） |
| `registers` | File→Symbol（`@app.route(...)` 这类装饰器，不混进 `calls`） |
| `references` | Symbol→Symbol |
| `depends_on` | Dependency→Dependency · File→Dependency |
| `needs` | Dependency→Toolchain |
| `diagnosed_at` | Diagnostic→File · Diagnostic→Symbol · Diagnostic→Module |
| `reported_by` | Diagnostic→Rule |
| `causes` | Diagnostic→Diagnostic · Diagnostic→Symbol |
| `affects` | Symbol→Symbol · Diagnostic→Symbol |
| `noted_at` | Note→File · Note→Symbol · Note→Module · Note→Dependency · Note→Diagnostic · Note→Run |
| `changed_at` | Commit→File · Commit→Symbol |
| `snapshotted_at` | Snapshot→任意实体 |
| `follows` | Run→Contract |

**为什么必须有这张矩阵**：没有它，"什么能连什么"只存在于人的脑子里；
一个拼错的组合（比如 `Note -calls-> File`）会安静地进库，然后在某次查询里
变成一条读不懂的结果。**有了它，越界的边在构造时就失败。**

### 15.5 明确不进图谱的（免得以后有人硬塞）

| 不进 | 为什么 | 改用什么 |
|---|---|---|
| 进程 / 线程 | 瞬时的，不是资产；图谱是"可回看的结构" | `Run.data` 存进程树摘要 |
| 字节 / 字节区间 | 太小，查询价值低于存储成本 | `File` + `line` 足够定位 |
| 清理项 / 敏感词 / 机器清单明细 | 属于工具功能，不属于"项目的结构" | 各自的功能模块 |
| 用户的每一次点击 | 那是遥测，设计里明确不做 | —— |
| 跨项目生态节点 | 现在不做；但 key 已按生态命名留了门 | 将来加一张共享表即可 |

### 15.6 这次审计暴露的一个更深的问题

缺口 3 与 8 说明：**"环境"这一半在图谱里原本是空的**。
而"七窍玲珑（环境事实 × 语义事实交叉归因）"是设计里三大能力之一——
**能力承诺与数据模型对不上**。补 `Toolchain` 只是把地基建到能承载它；
真正的交叉规则（例如"这个 build 失败是因为 JAVA_HOME 指向 11 而 pom 要 17"）
属于规则层，得在 `Rule` 落地之后单独做。

## 16. 数字来源分级（设计稿自己也得守"可验证"）

这份设计的核心承诺之一是"每条结论都要能自己验证"。**设计稿自己先得做到**——
所以凡出现数字，必须能回答两件事：**哪一级**、**怎么复现**。

| 级别 | 含义 | 在文档里的写法 |
|---|---|---|
| **实测** | 本机跑过，给出可重跑的语句或命令 | 直接写数字 + 复现方式 |
| **引用** | 来自外部资料/他人基准，**本机未复现** | 数字后标注「引用，未复现」 |
| **估算** | 有算法、无测量 | 写出算式，并写明"待校准" |

**当前状态**：

- 本文件 §11 的承载力数字、§4 的查询延迟、§0 的表结构验证 → **实测**
- §13 里提到的 LSP 冷启动、rust-analyzer 内存 → **引用**（与实现无关，等 M7 接上再测）
- §10 的容量模型 → **估算**（等 M4 一次真实全量索引后校准）

**一条纪律**：**引用级与估算级的数字，不许被当成预算用来做取舍**。
想用它做取舍，先在本机测一遍。
