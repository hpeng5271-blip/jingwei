## 0. 这份系统是什么（以及它靠什么活着）

**决定**：经纬是一个**本地优先的"项目理解层"**。它不编辑代码、不编译、不管版本，
它做三件事：**把项目里散落的事实读出来 → 过滤成看得懂的结论 → 让用户能顺着来源验证**。

**它靠什么活着**（一句判据，用来否掉一切新需求）：

> 一个功能只有在"**它让用户看见了原本看不见的东西，并且用户能自己验证它没看错**"时才算数。

**为什么**：你的起点不是"我要做个工具"，是三个具体的痛——COMSOL 吃满内存不知道为什么、
不知道自己改了什么、不知道 AI 干了什么。这三件事的共同点是：**信息存在但不可见、不可验证**。

**代价**：它永远不能像 IDE 那样"顺手"，因为它不替用户动手，只让用户看见。
想让工具更"好用"的人会一直提"加个一键修复"——这条线必须守住。

**被否掉的替代方案**：

- *做成 IDE 插件*：受宿主节奏约束，装不了底层能力（进程树、真编译器诊断、文件占用探测）。
- *做成 AI Agent*：对话式没有状态，回答不可复现、不可追溯——正好是你最想要的反面。

## 1. 边界与非目标

### 1.1 决定：永久不做（写进代码注释，不是写在文档里）

| 不做 | 为什么 |
|---|---|
| 编辑器内核 / 编译器 / 包管理器 / 版本控制 | 调用现成的；自研收益远小于维护代价 |

**内置编辑器的投入就此冻结**（R3 补写，把边界说死）：

只做「**打开 → 看 → 改 → 存 → 能回滚**」这五件事，不再往补全、跳转、重构、调试上投一分钱
——那些是 IDEA 十几年磨出来的东西，自研一万行不如它一行。

**要"成熟"就外跳**：`open_in` 把项目交给用户自己的编辑器（IDEA / VSCode / 记事本都行）。
那是这个工具该有的姿势——**不跟成熟的工具抢活，只负责把它该知道的事说清楚**。

**但不能没有**：看不了文件就断了工作流，用户会被迫在两套工具之间反复横跳，
每横跳一次就掉一次上下文。所以内置编辑器是「**够用的窗口**」，不是「竞争的产品」。
判据一句话：**它的功能上限，是"让用户不必为了看一眼而开 IDEA"**。
| 调试器内核 | 同上，且专业度要求极高 |
| 一键修复、自动改代码 | **AI 无保护地生成破坏性内容是真问题**；工具只给事实与自查命令 |
| 插件系统 / 远程 API / 多租户 / 云同步 | 每个扩展点都是一份长期维护负担，且破坏"本地优先" |
| 全量索引（整库符号表） | 太重、太慢，与"按需"冲突 |
| 通用知识图谱（什么领域都装） | 只有框在计算机领域，关系才是确定的 |

### 1.2 决定：暂时不做（写进 TODO，带触发条件）

| 暂不做 | 触发条件（满足才做） |
|---|---|
| LSP 集成 | M1–M6 完成且 tree-sitter 管线稳定（判据：连续 3 次 `cargo test --workspace` 全绿，且 `collect_facts` 采到的"解析不完整符号数"= 0） |
| 第二种语言 | **加一门语言，只允许改 `lang.rs` 一处**；改到第二个文件就说明抽象漏了（P8 改写：原来的写法是"不需要改 engine"——那是句无法判定的口号，实测现在要改 5 个文件 8 处分支） |
| 跨项目知识库 | 单项目图谱连续三个月自己每天在用 |
| AI 集成 | 图谱本身已经能被人类读懂（人读不懂，AI 更读不懂） |

**代价**：短期看起来"不够智能"。这是有意的——先把地基做对，再说上层。

### 1.3 决定：**"自动执行"必须有信任机制**（P5 复审新增）

**背景**：`afterAuto` 在默认设置下会对刚打开的项目**自动跑契约里的启动命令**。
而契约随项目走 → **打开一个别人给的项目 = 一次自动的任意程序执行**。

**决定三条**：

1. **自动试运行默认关闭**（`trial` 默认 false）。
2. 对某个项目首次自动执行命令前，必须由人**手动跑过一次**才算点头；那之前自动流程只做只读的事。
   提示里要**原样列出将执行的命令**。
3. **未确认的项目，自动流程只允许只读动作**（扫描、检查、分析构建产物），不跑 `run`。

**P9 更正（这条很要紧）**：初稿写的是"决定记进 `.jingwei/trust.json`（跟项目走）"——**那是错的**。
信任记录一旦跟着项目走，别人发来的压缩包只要自带一份 trust.json，就绕过了"第一次必须由你点一次"
这道闸，而这恰好是本节要防的事。**信任记录必须留在这台机器上**（实现用 localStorage 的
`jingwei.trust`，按项目路径），与项目本身无关。
——顺便记住这一类的形状：**安全机制存错地方，比没有这个机制更糟**，因为它看起来是有的。

**代价**：少了一点"打开就自动跑通"的爽感。**换来**：陌生项目不会在你不注意时执行东西。
**这条不能谈**：它是"数据正确优先"在安全上的同一条线。

### 1.4 决定：改名的尾巴必须一次收干净（P7 复审新增）

改名不是替换字符串，是**引入兼容面**。P7 一次性改掉旧名（`drydock`/`pylaunch`）时
踩到了四处"改了会静默坏事"的地方，全部按"新名字优先、旧名字也认"处理：

| 旧东西 | 新形态 | 为什么不能只认新的 |
|---|---|---|
| `.pylaunch/`、`.drydock/` 数据目录 | `.jingwei/` | 用户那一代名字下攒的笔记与运行记录会原地消失，而用户不会知道 |
| `DRYDOCK_PYTHON` 环境变量 | `JINGWEI_PYTHON`（旧名仍读） | 用户明明设过了却读不到——这种错最难自己想明白 |
| 忽略文件里的 `# added by drydock` 标记 | `# added by jingwei`（旧标记仍认） | 只认新标记就会再盖一遍，用户文件里平白多一行 |
| 清理/扫描的跳过名单 | 三代名字都在名单里 | 漏一代，旧目录就会被当成垃圾列出来给用户删 |

**规矩**：迁移链**只许往后加，不许删**。删一个旧名字 = 删用户的一代记录。

### 1.5 取舍的三道检查（2026-10-20）

架构 = 取舍，而且不只在技术层。每个"要不要做 / 选哪个"的决定，过这三道：

1. **成本必填**：写清开发量、周期、**长期维护复杂度**三维，外加一句"被否掉的选项是什么、为什么否"。
2. **绑定检查**：依赖了外部服务，就问"能不能换"；换不了 → 标"绑定风险"，并加抽象层降级。
   落点：与依赖基线闸（只降不升）同一条线。
3. **先问关心什么**：新功能先写"它优化哪个判据"；写不出判据 = **不做**（三态：判不了就写"查不了"，不许编）。

三条都接现有铁律：判断只在 engine 一份、DB 只存事实、关系必有来源。

## 2. 形态骨架：用户看到什么

**决定**：一屏工作区 + 三个工具窗 + 一条状态栏。**没有门户、没有仪表盘首页。**

```
- 图标条 64 - 项目（全局选中的那个）--------- 依赖（当前项目）-
-           ---------                -
-           - 画布：代码 / 图谱 / 记录（三选一）- 声明→实际      -
-           -                                  - 可展开传递树   -
---------
- 底部工具窗（可拖高，默认收起）：问题 · 终端 · 消息              -
---------
- 状态栏：CPU·内存·系统盘·工具进程 - 问题 N · 终端 · 设置         -
---------
```

**为什么不是"首页 + 多个页面"**：这个工具的价值是"随时能看见"，不是"进去逛一圈"。
多一层导航就多一次注意力切换。所以：**主区永远是工作区，信息按需从边缘浮出来。**

**为什么底部工具窗默认收起**：报错、日志、消息是"出事时看"的东西；
常驻会一直吃掉画布高度（实测踩过：264px 常驻底栏把编辑区压得没法用）。

**代价**：新用户第一次打开不知道点哪 → 用**空状态**解决：没有项目时主区只有一件事
（选目录扫描），扫到项目后卡片流自己流出来。

## 3. 架构：三条不可违反的约束

### 3.1 决定：crate 边界即架构（靠编译器，不靠自觉）

```
crates/                              状态（2026-10-17 核）
--- model/      纯数据：实体、关系、结论、来源。零依赖（只有 serde）
                                     ✅ 有
--- engine/     纯逻辑：解析、图谱、诊断、过滤。依赖 model
                                     ✅ 有
--- store/      SQLite 持久化。实现 engine 定义的 trait
                                     ⚠️ **没有这个 crate**——持久化在 engine 里
                                     （`crates/engine/src/graph/store.rs`）
--- adapters/   外部工具适配：cargo / npm / mvn / cmake / lsp。实现 engine 的 trait
                                     ⚠️ **这一层还没实现**，表是空的
--- cli/        命令行外壳：调 engine，输出人读文本
                                     ✅ 有（crate 名 `jingwei`）
--- src-tauri/  桌面外壳：调 engine，输出给 WebView。允许 unsafe（Win32）
                                     ✅ 有（crate 名 `jingwei-app`）
```

**依赖方向（单向）**：`cli / src-tauri → adapters → engine → model`；`store → engine → model`。
（**实际上**，因为那两个 crate 不存在，现在是 `cli / src-tauri → engine → model` 直连。）

> **为什么加这个"状态"列**（2026-10-17）：这份表原来把 `store` 与 `adapters` 和真存在的
> crate 平铺着写，**读的人会以为六层都在跑**。而事实是两层没有。
> 这与 `框架.md` 记的那条同一个毛病：
> **设计文档 §8.1"过滤七步"表没有状态列 → 核实后只有 ⑤排序是完整的。**
> **不标实现状态，读的人会以为都在跑**——而写的人（我）也会。

**强制方式**：workspace lints 全局 `unsafe_code = "deny"`（仅 `src-tauri` opt-in）；
`model` 的 `Cargo.toml` **不许出现 sqlite / tokio / reqwest**。
谁想违反，`cargo check` 直接失败——**这比 code review 可靠**。

### 3.2 决定：判断只有一份

**怎么判它有没有被破**：同一道检查如果在一条路径上写了、另一条路径上没写，
就是破了。**要么只写一次，要么在每条路径上都验一遍。**
（P10 的真事故：拦网络盘/链接/超长路径的 `should_skip` 只装在"扫项目列表"那一步，
进了项目内部深扫就没人管——而 junction 在 `node_modules` 里遍地都是。）

所有"这是什么、该怎么办"的判断都在 `engine`。外壳（CLI/WebView）**不许出现业务 if**：
它拿到的是已经决定好的结构（结论 + 证据 + 下一步 + 级别），只负责画。

**代价**：加一个 UI 需求时，常常要回 engine 加一个字段。
**换来**：换外壳（CLI → GUI → Web）不需要重写任何判断逻辑。

### 3.3 决定：机制与策略分离

内核提供**机制**（`trait ToolAdapter`：探测、执行、解析输出），
适配器提供**策略**（`CargoAdapter` 怎么调 `cargo metadata`、怎么解析 JSON）。

**验收标准**：加第三种语言时，如果 `engine` 一行都不用改，说明抽象做对了；
否则**先改抽象，再加语言**。

## 4. 领域模型（冻结：十年不变的那一层）

### 4.1 决定：实体清单以《数据层设计》§15.3 为唯一真源

**当前 13 种**：`Project` · `File` · `Module` · `Symbol` · `Dependency` · `Toolchain` ·
`Diagnostic` · `Rule` · `Contract` · `Note` · `Commit` · `Snapshot` · `Run`

> **为什么这里不再抄一份**：清单一旦有两份副本就会漂——本轮复验就抓到了
> （本文档初版写的是 9 种，代码里已经是 13 种）。所以**唯一真源 = `数据层设计.md` §15.3 + `crates/model` 的 `NodeKind::ALL`**，
> 本文档只讲"为什么是这些"，不再复述"有哪些"。

**为什么是这十几样**：任何语言、任何框架的项目，拆到底层都是这几样东西的组合。
**种类有限，组合无限**——这是把"几十种语言"收进一套模型的关键。
**它们的充分性经过了逐条核对**（把每条能力拿出来问"模型能不能表达"），见 §15.1。

### 4.2 决定：关系清单同样以《数据层设计》§15.3 为唯一真源（当前 17 种），每条必须回答三个问题

**最关键的新增是"两端合法矩阵"**（`数据层设计.md` §15.4）：什么关系允许连哪两种实体，
写死在代码里（`EdgeKind::allows`），**越界的组合在构造时就失败**。
没有这张矩阵，一个拼错的组合（比如 `Note -calls-> File`）会安静地进库，
然后在某次查询里变成一条读不懂的结果。

| 字段 | 取值 | 作用 |
|---|---|---|
| `source` | `ts` / `lsp` / `meta` / `user` | **没有来源的关系不许入库** |
| `confidence` | `1.0` / `0.85` / `0.5` | 只有推测才标低；确定的不用标 |
| `expires_at` | 时间戳 / NULL | 失效只标记，不物理删除 |

### 4.3 决定：三态，不用布尔

任何"有没有"的判断一律三态：**有 / 没有 / 无法确认**。

**为什么**：C++ 的包可能来自系统、vcpkg、Conan 或源码树；查不到就必须说"无法确认"。
**一次误报，用户就再也不信这一栏**——比少报一条严重得多。

### 4.4 决定：不搞通用 Object+Relation

**为什么**：领域有限、实体有限、关系有限。为"未来可能扩展"做抽象，等于牺牲现在的清晰。
**天很广大，但承载的东西有限。**

## 5. 存储设计（**已被《数据层设计》取代，本节仅存历史**）

> 本节是初版存储设计。**在真 SQLite 上实测后被修正了三处**（写入改 UPSERT、
> 索引改 `(file_path,kind)`、深度上限给实测依据），并新增两处（`checksum`、自检字段）。
> **唯一真源是 `数据层设计.md`**；本节不再维护，读到时以那份为准。

### 5.1 表结构

**真源在 `数据层设计.md` §3，这里不再重复放 DDL。**

重复过的后果已经出现过一次：实测把三处设计改掉之后，这个副本没跟着改，于是同一份 DDL 有了两个互相矛盾的版本，读到哪份全凭运气。要看表结构就去那一份；本节只留"为什么这么设计"。

**两条关键决定与代价**：

- `edges` 用 `WITHOUT ROWID` + 复合主键 `(src,dst,kind)`：点查与浅层遍历最快。
  **代价**：按单列 `id` 查不方便——我们不需要。
- 反向遍历索引用**部分索引** `WHERE expires_at IS NULL`：失效边不参与查询计划。
  **代价**：失效边不被这个索引覆盖——正是目的。
- `nodes.data` 只放该类独有字段，**不放通用字段**。**代价**：加字段要改 JSON 约定；
  **换来**：核心查询永远走真列，永远可索引。

### 5.2 决定：所有写操作在一个事务里；改文件先写日志

**为什么**：数据错只有三个根源——写入不原子、增量漏更、并发冲突。
事务解决第一个；三级检测（§6.2）解决第二个；单写者 + 读写连接分离解决第三个。

### 5.3 决定：每 50 次增量做一次抽样校验

随机抽 1% 文件重算哈希与节点数，对不上就以存储为基准重建。
**代价**：偶发额外开销。**换来**："图谱悄悄错了"这件事能被自己发现。

### 5.4 决定：schema 迁移只允许向后兼容

加列带默认值、加表用 `IF NOT EXISTS`；**改类型不许原地改**——
新建表 → 迁数据 → 删旧表，且**迁移前备份 `graph.db`**，失败回滚。
`meta.schema_version` 是唯一版本真相源。

## 6. 解析与索引管线

### 6.1 决定：tree-sitter 是主力，LSP 是补充（不是反过来）

**为什么**：tree-sitter 结构化导航的 token 消耗比 LSP 少约 30%（395K vs 567K），
答案完整性相当；而 LSP 冷启动 60–120 秒、多 crate 项目单实例可吃 22–39GB。

**四条解析纪律**（每条都对应过一次误报）：

1. **查询对象复用**（`OnceLock`）· `set_query_ranges` 限范围 · **Parser 每线程独立**（非线程安全）
2. **错误门控**：树里含 `ERROR` / `MISSING` 子树 → 标"解析不完整"，
   **只提顶层符号，不建调用关系**
3. **四个 Rust 边界**：`format!` 是宏不是函数 · 接收者类型要用源码声明的类型推 ·
   `impl other_mod::Trait for Type` 要保留模块路径 · `pub(crate)` 在 crate 外不算公开
4. **语法包按需加载**，缓存在 `.jingwei/grammar/`。
   **P8 更正——"按需"的含义要说准**：动态加载是官方支持的路（`tree-sitter-loader` 用
   `libloading` 加载 .dll/.so/.dylib），但那条路要现场编译，而**目标机器上没有 C 编译器**。
   所以实际可行的只有一种：**预编译好的 .dll 随发行版分发，运行时按需加载**。
   代价两条，写在这里免得后面当成意外：① 发行包变大——**Q8 已实测**：core + 1 个语法 = 1.3 MB，
   每增加一个语法约 1.14 MB，10 个语言 ≈ 11.4 MB（原来那句"5–15MB"是引用级估算，Q8 实测落进区间）；② 语法包与 core 有 ABI 窗口（`LANGUAGE_VERSION 15` /
   `MIN_COMPATIBLE 13`），升级 core 就要重新编译全部语法包。

### 6.2 决定：三级变更检测 + 符号级双哈希

| 级 | 机制 | 代价 |
|---|---|---|
| Tier 0 | 变更日志（watcher 记下本次改动） | 需要 watcher（轻） |
| Tier 1 | mtime + size（不读字节） | mtime 可能被工具改坏 → 靠 Tier 2 兜底 |
| Tier 2 | 内容哈希 blake3 | 要读字节，但只对 Tier 1 判"变了"的文件 |

符号级两个哈希：`content_hash`（种类+名称+签名+主体）、`subtree_hash`（内容 + 子节点）
→ 精确区分 **新增 / 修改 / 仅子节点变化 / 未变 / 删除**。

**脏传播**：签名变了 → 下游调用者的上下文全部标过期并重算。
**代价**：一次改签名可能触发几十个文件的局部重算。**换来**：图谱不会"半新半旧"。

**watcher 的现实**：Windows 用 `ReadDirectoryChangesW`，但 WSL2 / 网络挂载上可能完全不触发
→ **必须挂 `PollWatcher` 兜底**（原生 N 秒无事件就切轮询），并用 debounce 合并同一批改动。

### 6.2.1 决定：**索引期只记事实，解析放到后面**（学 stack-graphs，V0 重建期补）

这一节是"关系抽取"的路线。**不是自己想的**——是把 GitHub 的 stack-graphs 那套
读完之后，按经纬的实际情况落下来的。

**别人是怎么做的**（原文，出自 GitHub 介绍 stack-graphs 的博客）：

> *"Because we must rely on incremental results, it's important that at index time
> we look at **each file completely in isolation**. Our goal is to extract **facts**
> about each file that describe the definitions and references in the file,
> and **all possible things that each reference could resolve to**."*

以及它背后的学术来源：TU Delft 的 **scope graphs**（Eelco Visser 组），
核心是把"名字解析"变成**图上的路径搜索**。

**这三句话纠正了我们原来的做法**：

我们的第一版是"**在索引期就尝试解析调用**"——只能解析同文件里的裸标识符。
那不是"简化版"，是**方向错了**：一旦跨文件就永远做不到，
而且**每加一种语言都要重写一遍解析逻辑**。

**改后的路线，两段分开**：

| 阶段 | 做什么 | 为什么分在这边 |
|---|---|---|
| **索引期**（每文件独立） | 只记**事实**：这里有个定义、这里有个引用，引用的是**名字**（不是"确定的符号"）| 为了**增量**——文件之间不许互相依赖，否则改一个文件要重算一片 |
| **解析期**（全局） | 把"名字引用"在图上解析成"确定的关系" | 只有在这一步才需要看到全图；而它**可以慢慢做、可以缓存、可以只做查得到的那部分** |

**"所有可能解析到的候选"这一条，正好接上我们的三态**：

| 解析结果 | 落成什么 |
|---|---|
| 唯一命中 | `calls` / `references` 边，置信度按语法层（0.85）|
| **命中多个**（同名、多个候选）| **不猜**——记成"有歧义"，边上带 `affects` 那句话：这条关系不确定 |
| **一个都没有** | 那是**外部符号**（标准库、别的 crate）——**不是错误**，如实标成"不在索引范围内"，与"不存在"分开 |

**这条与四条线的关系**：第三条（无自查不报错）在关系层就是——
**解析不出来就说"解析不了"，不许拿一个猜出来的目标凑数**。
一条假边比一条缺边糟得多：缺了只是图不全，**错了是图在骗人**。

**为什么这条现在写得了**：图谱、解析器、增量都已经在了，
而"引用事实"是什么形状（名字 + 位置 + 所在作用域）现在能说清楚——
在 M3 之前写它，只能是空话。

#### 6.2.1.1 再往下一层：作用域是**栈**，不是"当前在哪个函数"

第一版 `RefFact` 只记了"在哪个函数里"。**那不够**——真实的作用域是**嵌套的**：
函数 > 块 > 闭包，而且有**遮蔽**（内层同名遮蔽外层）。

stack-graphs 对这一条的处理值得抄作业：

> **每个 blue 节点压一个符号进栈，每个 red 节点弹一个出来；
> 弹的时候栈顶不匹配，就不许走那条路。**

它把作用域规则编码成"图上的 push/pop 节点"，然后**路径搜索时顺手维护一个符号栈**——
于是"同名遮蔽"这种语言规则，变成了一个机械的匹配过程，不需要为每种语言写一套查找逻辑。

**我们抄不了全套**（它有一整个 Rust 库在做这件事），但能抄它的**形状**：

| 它的做法 | 我们的简化版 |
|---|---|
| 索引期建"作用域图"（push/pop 节点）| 索引期给引用记一条**作用域链**（从内到外）|
| 查询期路径搜索 + 符号栈保证遮蔽正确 | 解析期**从内往外找第一个匹配**——这就是遮蔽规则的直接实现 |
| 明确记"might resolve to"（候选）| 同样：解析不出来时**记候选，不猜** |

**还有一条必须抄的，是它的"诚实"**：

> *"Because we are looking at this file in isolation, **we don't yet know** what the `broil`
> reference resolves to... **it might resolve to** `stove.broil`, defined in some other file
> — but that depends on whether there is a file defining that symbol."*

它连"这个仓库里确实有那个文件"都说了，但**仍然坚持在索引期忽略它**。
——因为一旦偷看，增量就破了。

**这与我们的三态是同一个东西**：索引期那些引用就是 `unknown`
（不是"没有关系"，是"还不知道"），到解析期才变成 `yes` / 仍然 `unknown`。

### 6.3 决定：性能预算写进测试门禁

| 操作 | 预算 | 超标怎么办 |
|---|---|---|
| 单文件解析（≤2000 行） | <5ms | 降级：只提顶层符号 |
| 单次增量更新 | <1s | 排后台队列，UI 不等 |
| 首次全量索引（中型项目） | <120s，**必须有进度** | 分批 + 可中断 |
| UI 查询（点查 / 1 跳） | <30ms | 加缓存；仍超就分页 |
| 3 跳遍历 | <50ms | 改走 Rust BFS |
| **UI 线程阻塞** | **>1s 一律不允许** | 移后台 + 进度条 |

**红线**：30 秒以上无响应 · 数据不同步 · 数据错误。

## 7. 查询与图算法

**决定：按跳数分工，不按偏好分工。**

| 场景 | 用什么 | 为什么 |
|---|---|---|
| 点查、1–3 跳、浅层 | SQLite 递归 CTE + `LIMIT` | 实测 1 跳 <1ms、3 跳 12–18ms |
| 4 跳以上、环状、菱形依赖 | **Rust 层 BFS/DFS + visited 集合** | 递归 CTE 会退化成 O(2^n)（有项目 >120s → 1.6ms） |

**硬限制**：深度上限 **10 跳**；递归 CTE 必须带 `LIMIT`
（否则规划器可能选全索引扫描，实测能占查询时间 70%）。
反向索引 `(dst, kind) WHERE expires_at IS NULL`（也就是 `schema.sql` 里那条 `idx_edges_dst_kind`）能让 CTE 直接 seek 而不是 scan（实测提升 96%）。

**缓存**：热点查询结果物化到 `query_cache` 表（带 `invalidated_at`）；
任何写操作把相关缓存整体失效。**不做细粒度依赖追踪**（代价远大于收益）。

## 8. 信息管线（产品的全部价值在这里）

**决定：所有对外信息走同一条管子，五步，顺序不可换。**

```
事实(facts) → 规则(rules) → 过滤(七步) → 结论(四要素) → 呈现(分级)
```

### 8.1 过滤七步（每步都有判据，不是感觉）

| 步 | 判据 | 不许发生 | **实现状态（2026-10-16 核实）** |
|---|---|---|---|
| ①去重 | `rule_id + 参数指纹` 相同只留一条 | 同一件事报三遍 | ⚠️ **没有显式去重**（`rules.rs` 里零个 `HashSet`/`dedup`）。靠"每条规则对同一件事只报一次"隐含成立，有测试钉着 id 不重复，但**不是机制** |
| ②抑制下位 | 上层根因未解 → 下位不出卡 | 根因下面挂 20 条连锁 | ❌ **未实现**（`Level::Silent` 零构造点，那个变体已删）。见 §8.3 |
| ③聚合 | 同文件 + 同错误码 → 一簇 | 同一个错刷满屏 | ❌ **未实现**。同类问题靠 `group` 分组显示，但**条数不变**——那不是聚合 |
| ④分级 | 红=挡运行 / 黄=不挡路 / 灰=进度 / 白=静默 | 用颜色装饰 | ⚠️ **部分**：`Severity` 只有 `Error`/`Warn`/`Info` 三档，**没有"静默"这一档**（见 §8.3）；界面按 severity 上色是有的 |
| ⑤排序 | 层序（8 层）→ 严重度 → 位置 | 按时间倒序（会埋掉根因） | ✅ **有**：`layer_of()` 给每条定层号并据以排序；测试钉着"资源层排最前" |
| ⑥容量 | 一行 ≤6 · 一卡 ≤3 · 一屏 1 结论 | 一屏 20 条 | ⚠️ **界面侧有取舍**（概览卡只给一条结论），但**没有机器判据** |
| ⑦静默 | <0.1s 的操作不出提示 | 点一下就弹通知 | ⚠️ **有近似实现**：提示音有个"静默"开关（`ui/core.js` 的 `SET.fb`），但那是**用户偏好**，不是"按耗时自动静默" |

> **这张表原来没有状态列**，读的人会以为七步都在跑——**实际上只有 ⑤ 是完整的**。
> 这不是"忘了做"，而是设计走在了实现前面；**但表格里不标出来就等于在骗人**
> （这个仓库为这一类事故记了五次账：决定记在文档上、代码里什么都没发生）。

### 8.2 四要素模板（强制；第四要素不是修复命令）

```
看到的事实      带数字、带来源（哪个文件 / 哪条命令看出来的）
你自己怎么验证   一条能复制粘贴的命令
什么时候不用管   边界（避免把正常写法当错）
下一步         能自动做的给按钮；要你决定的只给建议；不生成修复命令
```

**无自查命令，不许报 Error**——这条有测试守着（`an_error_without_a_self_check_is_downgraded`）。
> ✅ **2026-10-16 补齐**：这句话原来**只对了一条**。完整的判据是三条一起
> （权威来源 / 非推测置信度 / 有自查命令，见 §8.3 第 3 条），
> 而生产里只跑了第三条。现在 `rules::enforce_evidence` 三道齐全。

### 8.3 三条不可退让

1. **隐藏必须可查**：每条被过滤掉的都能问"为什么没显示"——
   `重复` / `被上层抑制` / `同类已聚合` / `低于静默阈值` / `你关掉了这类`
   > ⚠️ **未实现（2026-10-16 核实）**：过滤七步里只有 ⑤ 是完整的，**"隐藏"这件事本身还没发生**，
   > 所以"隐藏必须可查"暂时是**空转的要求**。那五个理由枚举（`SuppressReason`）随
   > `Conclusion` 一起删了——它生产零调用。真要做这一条时，**同一次改动里必须
   > 连"隐藏可查"的入口一起做**，否则就会重演"文档承诺、代码没有"。
2. **区分"真实空"与"缓存空"**：后者必须明说"语义分析暂不可用"，
   **绝不能让用户以为代码没问题**
3. **降级必须标注**：非权威来源的结论标"估的"，**且不给它 Error 级**
   > ✅ **这一条 2026-10-16 之前只做到三分之一**：闸原来只查"有自查命令"，
   > 前两条（权威来源 / 非推测置信度）长在一个**生产零调用**的类型上。
   > 现在 `Finding` 带上了 `source` / `confidence`，`rules::enforce_evidence` 三道闸齐全，
   > 降级原因写进 `boundary`——**用户能看见为什么降级**。

### 8.4 决定：索引证据（每次索引后必须产出）

```json
{"scanned":1280,"skipped":[{"why":"网络盘","n":3},{"why":"联接点","n":11},
 {"why":"超长路径","n":1},{"why":"不在项目范围","n":4}],"incomplete":7,"ms":8420}
```

**为什么**：没有它，图谱就是黑盒；用户无法判断"它到底看见了多少"。

## 9. 外部工具集成与系统管理（这类系统的成败都在这里）

> 标题在 R3 时扩过一次：原来只叫"外部工具集成"，而机器清单、清理、项目生命周期
> 都是"**读这台机器、动这台机器**"的事，塞不进"集成"两个字里，
> 于是它们一直被挂在别的章节边上——最后干脆没有章节（`machine.rs` 1,298 行、
> `clean.rs` 1,448 行都跑着，设计里搜不到）。

### 9.1 决定：LSP 客户端是一台显式状态机

```
NotStarted → Starting → Ready → Degraded → Down
                -          -        -        -
          就绪探测失败   连续3次失败  冷却5分钟  需人工/重启
```

**四条实现纪律**（每条都来自别人踩过的坑）：

1. **非阻塞初始化**：拿不到客户端就返回"未就绪"并在后台启动，**绝不冻结 UI**
2. **分层超时**：进程启动 5s / 初始化 **120s** / 单次请求 10–30s（按语言可配）
3. **就绪探测**：不信 `initialize` 握手，主动发一次 `workspace/symbol`，有有效响应才算就绪
4. **超时是终态**：超时即杀子进程并清理关联，**不重放**（"超时的传输不再可信"）

**降级链**：LSP 不可用 → tree-sitter 保底 → UI 明说"语义分析暂不可用"。

### 9.2 决定：项目成熟度自适应（按规模决定开多少重量功能）

| 阶段 | 判据 | LSP 策略 |
|---|---|---|
| 孵化期 | 文件 <10、依赖极少 | 延迟启动，仅打开文件时启动；禁用 cachePriming |
| 成长期 | 文件 10–100 | 后台启动；先禁 checkOnSave / procMacro，保补全与跳转 |
| 成熟期 | 文件 >100、有 CI | 全功能后台加载；UI 只给角落进度 |

### 9.3 决定：依赖与工具链按 M / D / U 三张表管理

- **M（机器上有什么）**：注册表 / PATH / 各语言自带工具探测，带**路径与版本**
- **D（项目声明了什么）**：读清单（cargo.toml / package.json / pom.xml / CMakeLists / requirements.txt）
- **U（实际用了什么）**：锁文件（Cargo.lock / package-lock.json）或安装目录

**结论只由差集产生**：`D 有 U 无` = 没装；`U 有 D 无` = 多装/传递依赖；`M 无 D 有` = 工具链缺失。
**查不到的一律进"无法确认"**，不进"缺失"。

### 9.4 决定：工具链探测写"来源清单"，能问的就不猜（P8 复审新增）

**判据**：**"装了"是用户的事，"我们找到了"是我们的事。**
少列一个来源，就是一次误报——而误报是这个项目最不许犯的错。所以每种工具链都要能回答
"用户可能把它装在哪"，并且这份清单要**逐条可核对**，而不是散在代码各处的 `join()`。

**三条规矩**：

1. **有官方查询命令的，一律去问，不许猜路径。**
   已经这么做的：`py -0p`（系统登记过的所有解释器）、`java -version`、各编译器的 `--version`。
   P8 补上了 `vswhere.exe`（问 VS 装在哪）。
   **还没跟上的**：`uv python dir`——uv 的 Python 放在 persistent data directory 的
   `python/` 子目录，而且**可被 `UV_PYTHON_INSTALL_DIR` 覆盖**，官方专门提供这条命令回答"到底在哪"。
   硬编码 `%LOCALAPPDATA%\uv\python` 就是猜。
2. **"故意不进 PATH"的安装方式必须单独列**：pyenv-win 的 versions、IDEA 的 `.jdks`、
   VS 的 MSVC、便携版 SDK 目录。这些恰恰是"装了却说没装"的高发区。
3. **每条来源都要在结论里留下"从哪找到的"**（`source` 字段已经在做）。
   找不到时说的是"我在这些地方都没找到"，而不是"没装"——**这两句话不是一回事**。

**当前覆盖度**（P8 实测，作为基线；数字变化时更新这里）：

| 工具链 | 来源 | 判定 |
|---|---|---|
| Python | 14 条（环境变量双读 / 契约 / 项目内 venv / PATH / `LOCALAPPDATA` 三个位置 / `C:\Python3xx` / `py -0p` / scoop / conda 两处 / pyenv-win / `.local/bin` / 便携目录） | **好**——`py -0p` 这条尤其对：问的是系统登记过的解释器，比任何目录猜测都权威 |
| Java | 11 条（`JAVA_HOME` / PATH / 各发行版安装目录 / `.jdks` / `.sdkman` / 便携目录 / `.java-version` / `~/.m2/toolchains.xml`） | 中 |
| C / C++ | 3 类（PATH / 便携目录 / `vswhere`） | 中 |
| **Web / Node** | **0 条** | **缺**：只听 `package.json` 和 `node_modules`，从不探测 node / npm / pnpm 本身。**触发条件：做前端项目（Vue）时必补** |

### 9.5 决定：机器清单要多源印证，**不许挑顺眼的**（R3 补写）

**为什么现在才写**：R3 通审发现这一块是空白的——`machine.rs` 已经 1,298 行在跑，
设计里**零章节**。这是**逆差**（代码比设计多），比反过来更危险：没人知道边界在哪。

**核心决定**：一个事实必须**带来源**；来源对不上时**把分歧摆出来**，而不是挑一个顺眼的。

```rust
pub struct Fact {
    pub key: String,
    pub value: String,
    pub sources: Vec<String>,   // 从哪几个独立来源拿到的
}
```

「可能会读不出来，但是**不能读错**」这句话，落地就靠这个结构：
**单来源的值、和两个来源互相印证的值，可信度不是一回事**；
两个来源打架时，界面上要显示分歧——该怀疑的时候就得怀疑。

**四条来源纪律**（每条都是真踩出来的）：

| 纪律 | 怎么来的 |
|---|---|
| CPU 型号读**两个来源**（注册表 + CPUID 品牌串）| 注册表那份是 Windows 抄的，CPUID 是 CPU 自己报的。对得上才敢说"就是它" |
| 内存走 **SMBIOS**，不走 WMI | WMI 在这台机器上要 **20 秒一次**；SMBIOS 结构直接读，毫秒级 |
| 硬盘型号走**设备描述符**，不走注册表 `Prod_` | 那是 SCSI 产品标识、**固定 16 字节**：`UMIS RPEYJ1T24MKN2QWY` 被截成 `UMIS RPEYJ1T24MK`。拿 CrystalDiskInfo 一对才发现——**这种"看起来完全正常"的截断，光靠自己发现不了** |
| 系统设置**只挑会影响开发的几项** | 刻意不读 VC++ 运行库（缺了别的程序自己会报错，不需要提前防）、不读 Defender 排除项（那是安全决定，不是性能决定）|

**一条教训**（代码里也写着，抄一份到这里，因为它是这一类问题的通用形状）：

> 一个**字段**装不下，不等于**这个来源**装不下。
> 当时为此绕道去写了 `DeviceIoControl`，结果在那台机器上被系统拒了（err=5）；
> 而同一棵注册树里就有 `FriendlyName`，21 个字符一个不少。
> **别急着换更重的路子，先看完这棵树。**

**实时采样与清单是两件事**，别混：

- `spec_report()` 回答"这台机器**是什么**"——读一次可以慢，要准；
- `Sampler` 回答"此刻**在忙什么**"——靠两次累计计数求差（`GetSystemTimes` 给的是开机以来的累计值，
  单看一次只能算出平均占用），要快。

状态栏只显示后者，且**字段刻意少而准**：**多一个数字就多一份噪音**。

**明确不读的**：性能跑分、温度、风扇转速。那些要装驱动或提权，
而"这台机器跑不跑得动这个项目"**不需要它们**也能回答。

### 9.6 决定：清理要"先探后删"，而且**只列不替人决定**（R3 补写）

**同样是逆差**：`clean.rs` 1,448 行在跑，设计里只有零星 3 处提到"清理"，没有章节。

**三个区分，缺一个都会出事故**：

| 区分 | 做法 | 为什么必须 |
|---|---|---|
| **能删 / 要权限 / 别碰** | `Zone` 三区，界面照这个分组 | 混在一起就是"一键全清"——那是灾难的入口 |
| **回收站 / 永久** | 默认走回收站（`FOF_ALLOWUNDO`），永久删要显式点 | 误删可恢复，是底线 |
| **建议删 / 只列出来** | 日志、空目录**只列不建议** | **留不留只有项目自己知道，工具不该替它决定** |

**"先探后删"这条是 Windows 逼出来的**：

删一个**正被别的进程占着**的东西，Windows 上不是干脆失败，而是**部分成功**——
目录删了一半，剩下的是夹生饭。所以不试删，先探一次：**能独占打开，就是没人在用**。

探测本身还有一个坑，代码里原样记着：

> 不能用 `OpenOptions::new().write(true)` 去试——Rust 的 std 打开文件时
> **默认带 `FILE_SHARE_READ | FILE_SHARE_WRITE`**，于是"再打开一次"永远成功，
> 探测等于没探。**第一版就是这么写错的，被测试当场抓住。**
> 这里要求独占（`dwShareMode = 0`）：只要有人拿着任何句柄，就会冲突。

**安全闸**：盘根、系统关键目录、`.git`、`.jingwei`、用户目录本体，一律不放行。
形状与 §9.4 那道"跳过闸"相同——**同一道检查只写一次，别处复用**（§3.2）。

**两份清单不许各写一份**：全局缓存目录总表只有一份，"量体积"与"填清单"都以它为准。
——两边各写一份，迟早会歪；这是 §3.2 那条规矩的具体落点。

**什么算垃圾**：后缀清单**不是拍脑袋定的**——`*.bak / *.tmp / *.swp` 这些
在 **GitHub 官方 .gitignore 模板**里是标配。普遍到需要被集体屏蔽，
说明它们确实是所有人都在忍着的东西。

**虚拟环境**：同一个项目里往往躺着两三个，只有一个真在用。
能**确定**"没在用"的只有两种：名字里写着 bak / 副本，或者项目契约绑的是另一个。
——**其余一律不碰**：猜错一次就是把人的环境删了。

### 9.7 决定：项目生命周期——发现、创建、起草；**移动与删除不做**（R3 补写）

`scaffold.rs`（创建）与 `projects.rs`（发现、起草契约）都在跑，设计里同样是零章节。

**四个动作，做三个，明确不做半个**：

| 动作 | 做不做 | 关键决定 |
|---|---|---|
| **发现** | ✅ | 一个目录本身是项目就**不再往里翻**——不然 `frontend/` 和 `frontend/legacy/` 会各占一张卡，人反而看不清自己有几个东西 |
| **创建** | ✅ | 按语言给**整套**东西，不是换个后缀了事：清单文件、构建命令、忽略规则、目录约定、契约里的三条命令，**每一门都得对**。名字要能当包名（中文名很常见，兜底成 ascii 安全名）|
| **起草契约** | ✅ | 返回 `(契约, 依据)`——依据是"从哪个文件哪一行看出来的"。**看不懂的推导不去猜** |
| **移动 / 删除目录** | ❌ | **工具不该动你的目录**（`fix.rs` 里的原话）|

**这里有一处"用户诉求"与"实现判断"的分歧，摆出来比藏起来好**：

> 用户要的是"**挪动项目位置**【挪动后所有配置项一并对齐】"，
> 而实现的判断是"工具不该动你的目录"。

两者其实**不矛盾**——用户真正要的不是"让工具替我搬文件"，
而是"**我搬完之后，不用手工去修一堆配置**"。所以正确的做法不是加一个移动功能，而是：

**工具不搬，但工具认账。** 目录被用户自己挪走之后，重新扫描时：

- 图谱库跟着项目走（`.jingwei/` 就在项目里，本来就跟）；
- 契约里的绝对路径要重算；
- 变更基线（`watch.json`）里的路径要重算；
- 界面上那张卡的位置刷新（父目录变了）。

→ **记待办**，触发条件：真有用户把项目挪了之后发现配置对不上。
（在那之前这只是推测出来的需求——而"推测出来的需求"不该直接做成功能。）

### 9.8 决定：**一条龙的六个阶段里，只有前四个跟语言有关**（V0 重建期补）

**背景**：六个阶段（检查环境 / 校验契约 / 解析依赖 / 准备运行时 / 拉起进程 / 等待就绪）
原本整套锁死在 Python 上——第 1 阶段就是"找一个能用的解释器"，
找不到直接报「没有可用的 Python，无法启动」。
拿它去开一个 Vue 项目，用户看到的第一句话与他的项目**毫无关系**：
**答非所问比不回答更糟**，它会把人引到错的方向上，还会让他以为机器出了问题。

**决策**：前四阶段按项目语言分家，后两阶段完全共用。

| 阶段 | 谁来决定 | 落点 |
|---|---|---|
| 1–4 环境 / 契约 / 依赖 / 运行时 | 按项目语言 | `launch/python.rs` · `launch/node.rs` · `launch/java.rs` |
| 5 拉起进程、6 等待就绪 | 只有一处实现 | `launch.rs`（进程树、输出读取、内存采样、就绪判定、运行记录） |

两边靠一个 `Prepared` 结构对接：要执行什么、参数、环境变量、人看得懂的命令，
外加**两条只有那一层知道的判据**（下面单说）。走哪条路由"这个项目是什么"决定：
有 `pom.xml` / `build.gradle` → JVM；有 `package.json` → Node；其余走 Python。
复合项目（根目录里两样都有）按 JVM 优先，**顺序写下来是为了两难时答案一致**。

**用途是四种，不是一个布尔量**：`Run` / `Task`（测试）/ `Build` / `Install`。
这一条是修一个真 bug 换来的：把"装依赖"混进"跑个任务"，
Node 项目上会让「补装依赖」那个按钮去跑 test 脚本——用户点的是安装，跑的是测试。
各语言怎么落地：

| 用途 | Node | JVM |
|---|---|---|
| Run | `dev` 优先，其次 `start`（从 `scripts` 里读） | `spring-boot:run` / `bootRun` / `run`（看构建文件里有什么插件） |
| Build | `{包管理器} run build` | `mvn package` / `gradle build` |
| Task | `{包管理器} run test` | `mvn test` / `gradle test` |
| Install | `{包管理器} install`（包管理器自己的子命令，**不是 scripts**） | `mvn dependency:go-offline`；**Gradle 如实说不适用**（依赖是构建时按需解析的，硬编一条只会打印依赖树） |

**"看不出怎么跑"时不猜**：普通 Maven 项目（没有 spring-boot 插件）不给启动命令，
而是如实说"看不出怎么启动"并给出 `jingwei run --run "<你的命令>"`。
硬编一条 `java -jar target/*.jar` 看起来聪明，但那是三个假设叠在一起
（jar 构建过、名字是那个、清单里有主类）——猜错一次，用户就会以为这工具连启动都不会。

**就绪判定的两条判据**（写在 `Prepared` 里，跟语言一起定）：

1. **常驻服务**的判据是「输出里出现监听地址 **且那个端口真的连得上**」。
   - **为什么不按框架名单猜**：Vite 打 `Local: http://localhost:5173/`、
     Next 打 `ready - started server on 0.0.0.0:3000`、`python -m http.server` 打
     `Serving HTTP on 0.0.0.0 port 8000`、Spring Boot 打 `Tomcat started on port(s): 8080 (http)`——
     说法完全不同，而**名单里没有的那个**（用户自己写的服务、刚出的框架）会被判成"没起来"。
     抓 `host:port`、带协议的 IPv4、以及"带 port 和'起来了'的意思"的行，
     认的是**进程自己说出来的话**，与它叫什么名字无关。
   - **为什么光看到地址不算**：`Error: connect ECONNREFUSED 127.0.0.1:3000` 里也有地址。
     所以认到地址之后必须再真连一次端口。**把失败报成成功比报成失败糟得多。**
2. **到点了进程还活着但没判出就绪**：Node / JVM 报**注意**（dev server 本来就不退），
   Python 报失败（脚本跑不完通常是卡住了）。且措辞分开——
   "看到过地址但端口连不上"与"压根没报地址"是两种处境。

**后果**：一个没有契约的 Node 项目现在能直接 `jingwei run` 起来（实测：6 阶段全过、
就绪 251ms，依据是"端口 5173 已监听（输出里出现过 localhost:5173）"）；
Spring Boot 项目按 pom 里那个插件给的启动目标跑。

**被否的替代方案**：给每种框架维护一张"就绪关键词表"。否掉的理由就是上面那条——
表永远不全，而表里没有的那个会被报成失败。

## 10. 外壳设计

### 10.1 决定：工作区是画布，卡片只用来浮

- **代码区是画布**（无边框无圆角）、**结构树是工具窗**（平的一块），两者之间一条发丝线
- 圆角、描边、阴影只给浮层：查找栏、提示条、通知、弹窗
- **绝不用卡片包住工作区**——一旦包住，就在视觉上拒绝了"上面还能叠东西"

### 10.2 决定：依赖工具窗按 Maven 读法组织

工具条（筛选 / 重载 / 补装）→ 分组（未安装 / 已安装，带计数，可折叠）→
每行两列「声明 → 实际」，悬停给来源，行尾给下游数量（可展开传递树）。

### 10.3 决定：视觉语言六条（自研，只借 IDEA 的"信息组织"不借它的皮）

1. 三层面（底板 / 工作面 / 嵌入块）靠**明度差**分层，不靠描边
2. 悬停与按下是**在原底上叠半透明强调色**，不换底色
3. 面里掺一点主色（纯中性灰与暖色主色放一起一定打架）
4. 同心圆角：外圆角 = 内圆角 + 内边距
5. 圆角三档：6px 控件 / 10px 页内卡片 / 14px 浮层
6. 分隔线能不用就不用，分组靠底色与留白

**代码区与结构树**借用 IDEA 的信息组织：多文件标签、面包屑、行号、当前行、缩进参考线、
括号配对、查找与跳行、类型徽标。**语法配色**用 IDEA Light / Darcula 两套色值。

### 10.4 动效与反馈（每条都要回答"发生了什么"）

- 三档时长 **fast 100 / default 170 / slow 260ms**（`--t-fast` / `--t` / `--t-slow`，
  由设置里的"动效"档位改写）。大面用强调曲线
- **不许动会触发 layout 的属性**（`width` / `height` / `top` / `right` / `bottom` / `left` /
  `margin` / `padding` / `font-size`）。位移一律走 `transform`。
  **颜色类（`background` / `color` / `border-color` / `box-shadow`）允许过渡**——
  P9 更正：初稿写的是"只动 `transform` 与 `opacity`"，但实测有 30 多处颜色过渡。
  它们只触发重绘、不触发 layout，代价可以忽略，而且全删掉界面会变僵。
  原话太窄，等于逼着人天天违反它——**规矩要么改准，要么就是橡皮筋**。
  例外要写明理由：通知栏的 `right` 过渡是跟着侧栏开合走的一次性位移，
  换成 `transform` 得反推侧栏宽度差，不划算。
- **跟随系统的"减少动效"**：`prefers-reduced-motion: reduce` 时首次运行默认关掉动效
  （用户自己挑过档位之后不覆盖他的选择）。这是无障碍要求，不是偏好
- 反馈分档：<0.1s 静默 / 0.1–1s 不打断 / >1s 显式进度
- 四角通知最多 2 张，非红 6s / 红 14s 淡出，**历史进"消息"栏**
- 加载态统一文案「正在加载中…」，**骨架位与真实字段一一对应**（避免跳动）

### 10.5 决定：关系图谱怎么展示（R3 补写——**这一节原来根本不存在**）

**背景**：R3 需求通审时发现，"把关系画出来"这个设想在设计里**零命中**。
之前所有章节讲的都是"项目状态怎么展示"，没有一处讲"关系怎么展示"——
而这两件事的负载完全不同：状态是几十行字，关系是几千个点和边。

**先说清它与图谱的依赖方向**：**可视化不是独立功能，它是图谱的一面镜子。**
图画错了，不是画的问题，是图谱的问题。所以下面这些约束**大部分是对图谱提的**：

| 约束 | 为什么 | 落到哪 |
|---|---|---|
| **只画 `live_edges`** | 失效边是历史，画出来就是假的当前状态 | 视图已经保证（查询层只许查它）|
| **未知的关系不许画成实线** | 三态那条线在图上也要活着：实线=确定，虚线=推断，不画=查不了 | 用 `Edge.confidence` 区分线型 |
| **每条边悬停要能说出"哪来的"** | "关系必有来源"这条线在图上不能断 | `Edge.source` 直接显示 |
| **一屏节点数有上限** | 几千个点全画出来既看不清也画不动；超了必须聚合或分页 | 界面上限由成熟度自适应决定（§9.2）|
| **布局算法要有时间预算** | 图布局是 O(n²) 起的东西，不能让它卡住界面 | 预算进 §6.3；超了就退化成"只画 N 跳邻域" |
| **点节点必须能跳到源码** | 图不落到源码上就只是装饰 | 复用已有的"点条目跳到那一行" |

**一个判断**：这张图**不该是首页**。它信息密度太高，第一次打开的人看不懂——

### 10.5.1 渲染栈验证（实测，V0 重建期补）

**验证什么**：canvas 到底画不画得动那张图。这是唯一一个"做不到就真的做不到"的瓶颈
——别的性能问题可以优化，画不动就是画不动。

**怎么验的**：把**经纬索引自己**的真实图谱导出来（47 个文件 / 1006 个符号 / 1054 节点），
用 canvas 画它，在真浏览器里量帧率。**全程真数据，不靠估。**

**结果**：

| 规模 | 帧率 | 布局 | 绘制 |
|---|---|---|---|
| 1054 点 / 3162 边 | **153 fps** | 3.2ms | 0.2ms |
| 1054 点 / 9486 边 | **149 fps** | 3.0ms | 0.4ms |
| 1054 点 / 25296 边 | **145 fps** | 3.0ms | **0.9ms** |

**三条结论**：

1. **canvas 完全够用**——25000 条边只要 **0.9ms**。原来担心的"几千个节点会卡死"
   是 **DOM 的问题，不是 canvas 的问题**：DOM 里每个点每条线都是一个元素，
   几千个就是几千次布局与合成；canvas 只有一次。
2. **下一个瓶颈是布局，不是渲染**：现在是朴素的 O(n²) 力导向，1000 点 3ms；
   按平方关系，**5000 点会到 ~75ms**（13fps）。真要做几千点的全图，
   布局得换 Barnes-Hut，或者**放 Rust 侧算完再把坐标传过去**。
   ——但**邻域图（2 跳、几十到几百点）用现在这套完全没问题**。
3. **一条方法论上的坑**：同一份代码在 **headless 浏览器**里只有 5–44 fps，
   有头模式 145–155 fps，**差 30 倍**。原因是 headless 下 canvas 的栅格化走软件渲染、
   `requestAnimationFrame` 还被节流。
   → **性能验证必须在有头模式下做**，否则量到的是环境的极限，不是代码的。

**留下的东西**：`tools/graphview.html`（能拖能缩的图，双击就开）、
`tools/graphbench.mjs`（可复跑的性能基准）、
`graph::store::dump(limit)`（**天生带闸门**：超了截断并如实说 `truncated: true`
——界面上画不全时必须能区分"只有这么多"和"被截了"）。
首页仍然是"这个项目卡在哪"（§10.1）。图谱是**钻进去看的东西**：
从某条结论、某个符号点进去，看它连着谁。

**为什么这条现在才补**：内核（M2–M5）做完之前，"关系"这一层根本不存在，
那时写它只能是空想。**现在图谱真的有了节点和边，这些约束才是可验证的。**

### 10.6 决定：笔记是**记录**，不是文档编辑器（R3 补写）

`notes.rs` 在跑，设计里零章节。"笔记"这个词在设计里只出现过一次（术语表里）。

**第一条决定：给固定的几类，不给空白框。**

新手最缺的不是自由格式，而是"**我该记什么**"的提示。所以类型是固定的几类
（`KINDS`），每类一个标签——这比一个空 textarea 有用得多。

**第二条决定：一篇坏了，不许毁掉整本。**

读不了的（编码坏、文件被截断）**跳过**，别的照常列出来。
——这与"链路的鲁棒性"是同一条线（§12.2 数据安全那几条）：
**局部坏掉要能局部承受**，不能一处坏了整个界面变空。

**第三条决定：删除只是搬进 `.trash/`。**

**自己写的字，不该被一次误点抹掉。** 这条与清理那边的"默认回收站"是同一个判断，
只是搬到了笔记上——**用户自己产生的内容，默认都要能捞回来**。

**第四条决定：笔记文件是给人看的，不是给数据库看的。**

一篇一个文件、Markdown、文件名带日期前缀、中文留着（只去掉 Windows 非法字符）。
代价：文件名会出现中文（跨系统拷贝时可能乱码）。
**换来**：用户可以直接用任何编辑器打开、可以用 git 管、可以在文件管理器里找到。
——**能被看见、能被搬走、能被别的工具读**，这三件事对一个"记录"来说比"整齐"重要。

**老格式的迁移**：早期版本把记录塞在一个 `jsonl` 里。
第一次打开时搬过来，然后把旧文件改名成 `.migrated`——
**不删**。搬不完、搬重了都有痕迹可查（§1.4 那条"迁移链只许往后加"的同一种做法）。

### 10.7 决定：交付形态是"绿色压缩包"，不是安装器（R3 补写）

**决定**：`pack.ps1` 打出一个 zip，里面两个 exe + `run.cmd` + 使用说明。
**解压就能跑，删掉就是卸载。**

**为什么不装安装器**：这个工具的定位是"想用的时候打开，用完可以扔"。
装安装器意味着写注册表、建开始菜单、留卸载项——**全都是"用户不想用了还得清理"的负担**。
而它的全部资产（项目内的 `.jingwei/`）本来就是**跟着项目走的**，
程序本身丢了也不影响项目。

**包里必须带说明书**——这一条原来没有，`pack.ps1` 是"有就拷、没有就算了"，
结果打出来的那份里没有说明，谁都没发现。
现在缺了会**直接停下来报错**（`throw`），因为"发行版里少一份说明书"不是可以默许的降级。

## 11. 工程规矩（决定它活多久）

### 11.0 工具怎么用：**PowerShell 只负责"跑"，不负责"写"**（V0 重建期立）

这一条是**拿五次真事故换来的**，全发生在一天之内，而且**全是同一个来源**：

> 拿 PowerShell 当文件操作工具用。

| 踩的坑 | 症状 | 为什么 |
|---|---|---|
| `` `.Replace("...`r`n...") `` | 文件里出现**字面量** `` `r`n ``（六个字符），Rust 报 `unknown start of token` | 反引号转义在**双引号里才解析**，在 `.Replace()` 的实参里当普通字符 |
| `[IO.File]::ReadAllText('相对路径')` | 找不到文件 | .NET 用**进程工作目录**，不是 PowerShell `cd` 之后的目录 |
| `git show HEAD:path > file` | 写出 **UTF-16**（首字节 0xFF）| PowerShell 的 `>` 默认 UTF-16，不是 UTF-8 |
| 脚本按"第一个 `}`"找函数结尾 | 把下一个函数也切走了 | 嵌套 `match` 里全是大括号，**不能靠数括号** |
| 用 `-split` 处理多行 | 切不干净 | 同上：字符串层面猜结构，猜错不报错 |

**规矩三条**：

1. **改文件用 `apply_patch`**——它按行匹配，不经过 shell 的转义层。
2. **要写多行脚本，就先写一个脚本文件**（用 `apply_patch` 建），再让 PowerShell **只运行它**。
3. **涉及结构（括号、缩进、路径）的操作，不许用字符串层面猜**——
   用能理解那种结构的工具（Rust/Node/Python 的解析器），或者干脆手工改。

**一句话**：**PowerShell 是"跑命令"的通道，不是"写文件"的编辑器。**
让通道干编辑的活，错误会以"文件内容错了但命令成功了"的形式出现——
而那种错**不报错、只留下坏数据**，正是这个项目一直在防的东西。

#### 11.0.1 同族的第二种：**动 git 之前先看 `git status`**（V0 重建期补）

这一条是拿**两次真丢工作**换来的，形态完全一样：

> 用 `git checkout -- <file>` 当"撤销上一次改动"用。

它撤销的不是"上一次改动"，而是**这个文件上所有未提交的改动**。两次的代价：

- 一次是 `launch.rs` 刚写好的 `has_jvm_build_file`、Java 分支、`port_words` 一起没了；
- 更值钱的一次是**一笔提交其实是不完整的**：`git add crates/engine/src/launch`
  只加上了 `launch/` 目录，`launch.rs` 本体没进去——于是 `mod java;` 不在，
  **`launch/java.rs` 根本没被编译**，而提交信息里写着"实测 6 阶段全过"。

**规矩两条**：

1. **改文件之前先 `git status`**；要保住工作区就先 `git stash`，别用 `checkout` 当撤销。
2. **提交之前先 `git status` 再看一遍**——尤其当你只 `git add` 了某个目录：
   目录和同名的 `.rs` 文件是两回事（`launch/` 与 `launch.rs`）。

**这一条为什么算工程规矩而不是小事**：坏数据的形态有两种，一种是"错的"，
一种是"**看起来对、其实没生效**"。后者更难发现，也更贵——
它的代价不在写错的那一刻，而在**别人（包括三天后的自己）照着它做决定**的时候。

| 项 | 规矩 |
|---|---|
| 错误 | 库层返回 `Result` 或"结果内嵌降级说明"（两类见 §11.1）；边界层 `anyhow` + context；不用 `.unwrap()`；**忽略一个 `Result` 必须有写在旁边的理由**——由 `let_underscore_must_use` 全 crate 生效来守 |
| 命名 | 领域术语统一（契约/诊断/就绪/工具链/工作副本/应用/清理/机器清单/变更集）；函数动词开头、类型名词、trait 描述能力、布尔 `is_`·`has_`·`can_` |
| 规模 | 单文件 ≤1000 行（前端放宽到 4500：没有打包器是有意的架构选择）· 单函数 ≤100 行 · 单结构体 ≤20 字段。**由 `tools/gate.mjs` 守**：超限的新文件直接失败；历史超限的登记在案，**只许降不许升** |
| 注释 | 写"为什么"不写"是什么"；**模块按理解路径组织**；每个 crate 的 `lib.rs` 顶部一句话定位 |
| 日志 | 自研 `dlog`，**不引 `tracing`**：本项目只要"攒着、退出时一次落盘"这一种用法，为它引一个框架不划算。带四位码表（`code_name`，写时只写码）；热路径零分配；只在退出时写盘，被强杀最多丢 2 MB |
| 依赖 | 每加一个先问"能不能不加"；`Cargo.lock` 入库；`resolver="2"`；不用 `*` / `>=1` |
| Lints | **四个 crate 全部继承** workspace lints；`unsafe_op_in_unsafe_fn = deny`；`let_underscore_must_use = warn`；`undocumented_unsafe_blocks = warn`（每个 `unsafe` 块前面必须有 `// SAFETY:`）。`unsafe_code` 只对 `model` 用 crate 属性 deny（它不该碰 FFI），engine/cli 因 Win32 调用必须允许 unsafe——**允许，但要一处一处写清楚凭什么**。**不开 `clippy::pedantic`**：实测 820 条，绝大多数是风格偏好，开了会把真问题淹掉 |
| 决策 | 关键决策写进本文——`### x.y 决定：` 就是 ADR 格式（背景 → 决策 → 后果 → 被否替代方案）。**不另建 `docs/adr/`**：同一份事实只允许有一个可编辑副本 |
| 体积 | `opt-level="s"` + `lto=true` + `codegen-units=1` + `panic=abort` + `strip=true` |

### 11.1 引擎 API 怎么表达失败（两类，不许混）

这条以前写成"库层 `thiserror`；边界层 `anyhow`"，而实现不是那样。按**实际在做的事**重写：

| 情形 | 表达方式 | 为什么 |
|---|---|---|
| **前置条件不成立**（项目不存在、契约不是合法 JSON、命令缺失） | 返回 `Err`（`anyhow` + context） | 这件事根本没做成，调用方必须知道 |
| **读到了一部分**（某个文件读不了、某个外部命令超时、某项查不了） | 照常返回结果，把缺口写进结果的字段（`coverage` / 说明文本 / 三态 `unknown`） | 一个目录读不了不该让整次扫描失败——工具要的是"尽可能说清现状"，而不是"要么全对要么全没有" |

**判据一句话**：**整件事没做成 → Err；做成了一部分 → 结果里说清缺了哪部分。**
绝不允许出现第三种：**把失败吞掉、让结果看起来是完整的**。这正是 `let_underscore_must_use` 要拦的东西。

**平台特例（必须记住的三条 Windows 真坑）**：

1. **`std::fs::rename` 就用标准库的**——它在 Windows 上就是
   `MoveFileExW` 带回退到 `SetFileInformationByHandle`（Win10 1607+ 且文件系统支持时，
   行为与 Unix 一致，也就是真正的原子替换）。**不要自己调 FFI**：
   P10 更正了初版那句话（原写作"它不是原子操作，一律走 `MoveFileExW`"）——
   查官方文档才知道标准库已经这么做，而且更全。
   **定规矩之前先查清"语言是不是已经做了"。**
2. 文件可能被瞬时锁住（杀毒、索引器、编辑器）→ 写前重试。
   **这一条还没做**（P10 实测：代码里没有任何重试）。触发条件：有用户报"保存失败 / 落盘失败"。
3. 文本文件读写**必须按原编码与原换行**（GBK / BOM / CRLF），认不出就只读并说明

### 11.14 状态机：只显式化三处（2026-10-20）

状态机不是越多越好。**只有"转移错了会留下脏数据"的地方**才值得显式化：

| 处 | 状态 | 为什么值得 |
|---|---|---|
| 文件生命周期 | `unseen/unchanged/modified/deleted` | "删了又改""超大后变小"直接决定数据对不对 |
| 索引管线 | `idle/scanning/indexing/committing` | 半提交是最坏事故，回滚不变量要能断言 |
| rename 计划 | `planned/verified/written` | "判不准不发编辑"要机器表达 |

**不显式化**：三态（是/不是/查不了）是**值域**，不是流程；扫描缓存/LSP 已由各自结构管；目标/轮次太浅。

**唯一入口**：`graph::file_life::transition(from, event)`，返回 `Err` = 非法转移，调用方必须报错。
非法例子：`deleted --scan_same--> unchanged`——文件已经没了还报内容没变，说明扫描与库的认知对不上。
兜底：DB `CHECK(file_life IN ...)`；测试：4 状态 × 4 事件**穷举**，删/改一条转移必红。

**与三态的分工**：状态机管"文件处在哪个阶段"，三态管"这个结论可不可信"；两者不混。

### 12.2 必须有的具体用例（按"出事概率"排）

**数据安全（最高）**
- GBK + CRLF 文件：打开→改一行→写回，**编码与换行不变**
- 认不出的编码：**只读**且给出理由，绝不替换
- 保存中途杀进程：重启后文件要么是旧版要么是新版，**不能是半截**
- 关系失效：标记而不删，历史可查

**不误报（第二）**
- 冲突/缺失/估计三种来源的结论分开，**"估的"不许出 Error**
- 检查器没装 → 明说"没装，装它才能查"，**不许报"没问题"**
- 检查没跑成（stderr 有内容）→ 报"没跑完"，**不许报"通过"**
- tree-sitter 遇 `ERROR` 子树 → 不建调用关系

**过滤与呈现（第三）**
- 同类 20 条 → 聚合成 1 条 + "连带 N 处"
- 上层根因存在时，下层不出卡
- 每条被隐藏的都能回答"为什么没显示"

**性能边界（第四）**
- 3000 行文件：**打字路径不得做全文件操作**（实测 126ms → 0.57ms 是不可退化的）
- 环状依赖图的遍历：不得超时（走 Rust BFS）
- 索引期间 UI 查询不被阻塞（读写连接分离）

**靠记得就是迟早会漂。** 现在改成机器守：

- 真源是 `tools/facts.json`，由 `node tools/collect_facts.mjs` **现场采集**（跑 `cargo test --workspace --all-targets`、
  跑外壳测试、数 `tools/gates.json` 的道数、现跑一次图谱自索引、数 `tools/motives.json`）；
  **采不绿就拒绝覆盖**——不绿的跑不许当真值，否则下一步就是"改文档去迁就一个坏掉的跑"。
- 文档里的数字用一对 HTML 注释包起来——本段的 <!-- fact:tests_total -->596<!-- /fact --> 就是这么写的：
  渲染时看不见，但机器能定位到**哪个文件哪一行**。
- `node tools/check_facts.mjs` 逐个比（它还挂在 `gate.mjs` 里，判断只有一份）：对不上就打印
  "哪个文件哪一行、文档写的 X、真值 Y"并非零退出；**一个标记都找不到也报错**（那说明文档被改坏了）。

这道门禁第一次跑就抓出两处真漂移：M1 写着"15 条测试"（真值 16）、M6 写着"23 条外壳测试"（真值 37）。

**为什么门禁要一条命令跑完**：靠人记得跑四条命令，总有一天不跑；而那一天之后的每一笔改动，
都在一条没人验证过的基线上做。**门禁的代价是几分钟，不跑门禁的代价是返工。**

## 13. 迭代规矩（防止"设计漂移"）

这三条是硬的，破例要写进 ADR：

1. **一轮只做一件事，且必须留下一个可验证的产物**（能跑的命令 / 能看的界面 / 能跑的测试）。
   不接受"只写了文档"作为一个迭代。
2. **每加一条设计，必须同时做掉一件事**：要么实现它，要么删掉一条旧设计。
   否则设计只会单向膨胀（这是已经发生过的：61 万字设计 vs 2.6MB 工具）。
3. **任何"未做"都要带触发条件**（§1.2 那种写法），不许留无条件的 TODO。
4. **每一条安全类与正确性类决定，必须同时留下一个"能失败的东西"**——
   一条测试、一条 lint、或门禁脚本里的一条断言。
   做不到，就说明这条决定**还没做**，只是被记下来了。

   **这条是拿两次真事故换来的**（P3 与 P9 各一次，形态完全相同）：
   P3 记下"已修：打开 `let_underscore_must_use`"，而那个 lint 只在一个 crate 里生效，
   engine 里 22 处吞 Result 一处都没被拦；P5 记下"已写进设计：自动执行要有信任机制"，
   而代码里 `trust` **零命中**——打开陌生项目照样自动执行它的命令。
   两次都是**决定记在文档上、门禁上什么都没发生**。

5. **动机要有落点，而且这件事由门禁守着。**

   `tools/motives.json` 是"用户当初要什么"的清单；`gate.mjs` 检查每一个动机
   要么在设计里指到一段**真实存在**的话，要么带触发条件挂着。

   **这条是拿 R3 的发现换来的**：设计一直跟着"能力"长，不跟着"动机"长——
   做内核时想的是节点和边，做外壳时想的是卡片和通知，
   而"我想看一张能转起来的关系图"这个**动机**正好掉进两者的缝里，
   设计里搜"可视化"**零命中**。

   而 R3 之前，四轮复审里没有一次问过"用户当初为什么要这个"。
   现在这个问题有了机器来问。

   判据：**想让一个动机消失，必须改清单，不能靠遗忘。**

**每轮的固定动作**：

```
选一个小目标（来自里程碑，不是来自灵感）
  → 写失败的测试（或写清验收命令）
  → 实现
  → 跑门禁（§12.3）
  → 写 A D R（如果做了取舍）
  → 记一条"这一轮留下了什么"（可验证的）
```

# 附录 A · 判据与分工（原《设计哲学》+《架构与权重》并入，2026-10-16）

> **为什么并进这里**：这两份讲的都是「**每个决定为什么这么定**」——与《设计》正文同一件事，
> 只是更靠近「判据」那一端。分成两个文件的实际后果是**三处各写一遍优先级**，而它们必然漂移。
> 正文是「决定是什么」，本附录是「**凭什么这么决定**」与「**谁负责哪一段**」。

## A.1 判据（原《设计哲学》）

### 一、这个系统是什么（一句话，且不许膨胀）

**它把「一个项目现在到底是什么状态」变成可信的信息，并且按人此刻该看的顺序摆出来。**

不是：构建工具、包管理器、编辑器、IDE 的替代品。
不是：替你写代码、替你装环境、替你改项目。

**唯一的产出是"理解"。** 一切代码、界面、命令，都只是把理解送到人眼前的手段。

判据（任何新功能都过这一关）：
> **它让哪一句话变得更可信、更准时、更好懂？** 答不上来就不做。

---

### 二、核心与外围（权重，不许偏科）

```
                    --------- 核心：一条链，四段 ---------
  项目（不可信的原始世界）
        -
   ①  采集 --- 可靠途径优先：用成熟工具的**官方输出**（cargo/pip/node/git/系统 API）
        -        自研规则只填**工具不回答、而我们能确定**的那些空白
        -        铁律：**采集阶段只记事实，不做判断**
        ▼
   ②  加工 --- 去重 → 交叉印证 → 定级 → 归因 → 排序
        -        每一步都要有判据；学外界（见 §五），不发明
        ▼
   ③  判定 --- 三态：是 / 不是 / **查不了**
        -        每条结论必须带：凭什么（来源）+ 怎么反驳（自查命令）
        ▼
   ④  呈现 --- 分级：该大的大、该小的小、该藏的藏（可查）、按层级现
                    ---------
        外围（服务这条链，权重更低，但不许拖后腿）
        CLI · 外壳 · 门禁 · 文档 · 打包 · 演示
```

**权重（先做哪个、一个阶段里怎么分精力）**

| 段 | 权重 | 为什么 |
|---|---|---|
| ① 采集 | **最高** | 事实错了，后面全错。而且**采集成本最高**（要碰真机器、真项目） |
| ③ 判定 | **高** | 这是"可信"这个词的落点。三态压扁一次，整个系统就不可信了 |
| ④ 呈现 | **高**（与③同级） | 用户明确要求过：**外形与核心同等投入**。信息在人眼前排错序 = 没做 |
| ② 加工 | 中高 | 它决定"信息量"，但**它的正确性由③暴露**；没有③的加工是自娱 |
| 外围 | 低但**不许欠债** | 门禁/文档/打包坏了会让人**误信**核心是好的（已经发生过 6 次） |

**偏科的判据**：如果连续几轮只有外围在动（文档、门禁、账本），那就是偏科——
**这一类消耗在账本里已经占了大头，是实测出来的教训，不是猜的。**

---

### 三、可信（第一铁律，压过一切）

### 3.1 三态不可压扁

任何"有没有"的问题，答案有三种：**是 / 不是 / 查不了**。

- `查不了` **永远不许**显示成 `没有`。
- 判据：**这是"用户的空白"，还是"我们的失败"？**
  - 用户的项目确实没装 → 是"不是"
  - 我们没查到（工具没输出、权限不够、语言不支持） → 是"查不了"
  - **这两个的界面文案必须不一样。**

### 3.2 每条结论都有来源，且来源要分级

来源分档（**只有权威来源才配得上"错误"级别**）：

| 档 | 例子 | 能报什么 |
|---|---|---|
| 权威 | 编译器诊断、包管理器输出、文件系统事实 | 错误 / 警告 / 提示 |
| 推断（高） | 语法树结构、清单文件的内容 | 警告 / 提示 |
| 推测 | "看起来像"、"可能" | **只许提示**，且必须标"估的" |

机器强制方式：结论类型上带 `source` 与 `confidence` 字段，
**默认值取最保守的那一档**——这样"忘了标"不会意外升级成错误。

### 3.3 每条结论都能被反驳

一条错误级结论必须能给出**用户可以自己敲的命令**去证伪它。

> 给不出自查命令的结论，用户只剩"照做"或"怀疑工具"两条路——**那就降级**。

### 3.4 关系的来源必须记下来

图谱里每一条边都要写清"**凭什么认为这两个东西有关系**"。
没有来源的边 = 假边，而**假边比没有边糟得多**（人会照着错的关系去改代码）。

---

### 四、加工（严谨 + 复杂，但不是玄学）

四段加工，每段都要**能说出它比不做时多知道了什么**：

1. **去重** —— 同一件事只报一次。判据：`规则 id + 参数指纹` 相同即同一条。
   （不做去重的后果：用户以为是两个问题。）
2. **交叉印证** —— 两条独立路径得出同一个事实时，可信度提升；
   结论冲突时**两个都报，并说明冲突**（不许挑一个当答案）。
3. **定级** —— 见 §三.2 的来源分档。
4. **归因与排序** —— 见 §六。

**"复杂"的正确含义**：加工步骤多、彼此有依赖、每步都有判据。
**错误的含义**：代码绕、抽象多、层级深。**复杂度要花在判据上，不是花在架构装饰上。**

---

### 五、学外界（没有哪一部分例外）

**每一个部分都要先问：这个问题别人已经解决过吗？**

| 我们的部分 | 已经解决它的东西（要学的） | 学什么 |
|---|---|---|
| 符号与引用 | **stack-graphs**（GitHub）、**SCIP**（Sourcegraph）、tree-sitter | "索引期只出候选、解析期才定论"的分层；描述符命名空间 |
| 关系图谱布局 | **力导向**（Fruchterman-Reingold / ForceAtlas2）、graphviz | 斥力-引力-阻尼的参数与收敛；**分组而不是逐个铺** |
| 大图可读性 | **degree threshold / k-core** 骨架、渐进披露 | "先给骨架、按需展开"是标准做法，不是偷懒 |
| 信息分级呈现 | **渐进披露**（Nielsen）、**Shneiderman 的"先概览、缩放与过滤、按需细节"** | "一屏 1 结论"的理论依据 |
| 诊断与去重 | **编译器诊断格式**（GCC/Clang/rustc JSON）、LSP diagnostics | 位置、严重度、错误码的通用形状 |
| 增量索引 | **增量构建**（Ninja/Bazel）、mtime+哈希三级检测 | "便宜的先查、贵的后查"的分级 |
| 修复建议 | **rustfix / clang-tidy --fix**、ESLint fix | **只做答案唯一且可逆的**——不要发明"智能修复" |
| 事实与文档一致 | **docs-as-code + 断言式文档测试**（Rust doctest、Sphinx doctest） | 文档里的数字/枚举由机器核对 |

**判据**：动手前先写一行「**这一处学的是谁、学它的哪一点**」。
写不出来，说明要么我在发明，要么我没做功课——**两种都不许开工**。

---

### 六、呈现（分级，不是罗列）

这是"最小可信操作系统"里 **"操作系统"** 三个字的落点：它是**信息的管理者**，不是清单打印器。

### 6.1 一条硬规矩：**排序是工具的责任**

列出 7 条却不排先后的界面，等于把排序工作推回给用户。
**每一次呈现都必须回答：现在最该看的是哪一个？**

### 6.2 分级的四级（Shneiderman 的落法）

| 级 | 什么时候出现 | 例子 |
|---|---|---|
| **一句话结论** | 永远是第一行 | 「现在就能跑」/「卡在：4 个依赖没装」 |
| **依据** | 紧跟结论，1–3 条 | 凭什么这么说 + 一条自查命令 |
| **细节** | 用户点开 / 加 `--more` | 完整清单、原始输出 |
| **全部** | 显式入口（命令或按钮） | 原始 JSON、全图、被过滤掉的那些 |

**"该藏的藏"** 只允许出现在第四级**有显式入口**的前提下——
**没有入口的隐藏就是丢信息**，那是这个项目最反对的一件事。

### 6.3 界面不是另一套逻辑

外壳与 CLI 必须走**同一个内核入口**。两条路各算各的，迟早算得不一样
（这个坑踩过一次：`diag` 两处实现）。

---

### 七、怎么判断一件事做对了（验收铁律）

**任何"改好了"必须同时给出三样**：

1. **门禁/测试的结尾**（不是"我跑过了"）
2. **改动范围**（`git diff --stat`）
3. **改之前它确实坏过的证据**（负向验证的输出）

**缺任一项，就是没做。**

补充三条实测出来的判据：

- **负向测试不红 = 判据不成立**，不管正测多绿。
- **一条几乎什么都放过的判据，比没有判据更坏**——它看起来在守。
- **做不出来的判据要收回去，并把"为什么做不出来"写下来**（否则下一轮会再试同一条路）。

---

### 八、怎么工作（用户的明确要求）

1. **每轮先写任务卡**：任务 / 验收标准 / 停止条件 / 不做什么。
   没有任务卡就不动手——**这是"不知道干到什么程度算完"的根治办法**。
2. **先分配权重**：一轮只攻一个主要目标，但**做到一定程度就让别的部分赶上来一点**，
   不许出现"核心全绿、界面全坏"这种偏科。
3. **失败的判据**：同一件事失败 **2 次**就停下，如实报「未完成，卡在哪」。
   不许"再试一次"超过一次——**反复试探是最贵的浪费**。
4. **不许给自己搭脚手架**：现在要验的东西，用最短的路径验。
   （实测：大量消耗花在"写脚本验证我自己的脚本"上，那是自娱。）
5. **先修坏的**：用户看得见的、已经坏的东西，优先于一切新功能。

---

### 九、这个系统**不做**什么（边界，防膨胀）

- 不生成修复命令（答案唯一且可逆的除外，且必须说明"这一步可逆"）
- 不替用户做决定（给依据与后果，不给"你应该"）
- 不追新功能而放弃"可信"（**宁少说，不说错**）
- 不做"看起来智能"的推断：**猜错了比不收更糟**
- 不为了对称、美观、抽象洁净而增加概念（**每一个概念都要能回答一个问题**）

## A.2 分工与权重（原《架构与权重》）

### 一、一句话架构

```
   不可信的原始世界                --------- 核心：一条链 ---------
   （项目 / 机器 / 工具输出）        -  ①采集 → ②加工 → ③判定 → ④呈现 -
                ---------► ---------
                                             -
                    外围（服务这条链，权重更低）-
                    CLI · 外壳 · 门禁 · 文档 · 打包
```

**核心只有一条链。** 别的东西要么喂它、要么送它出去——**没有第三类**。

---

### 二、模块与权重的真实账（2026-10-16 实测行数）

| 段 | 权重 | 模块 | 现有规模 | 它替核心干什么 |
|---|---|---|---|---|
| **①采集** | **最高** | `detect/`（3695） | 语言/依赖/工具链/Web/Java/CC 探测 | 事实进来的唯一入口 |
| | | `sys/`（4121） | CPU/内存/磁盘/显卡/SMBIOS/注册表/原生调用 | **机器事实**——操作系统已经提供，我们只是转述 |
| | | `parse/`~`graph/parse*.rs`（~1500） | tree-sitter 符号与引用 | 源码事实 |
| **②加工** | 中高 | `graph/`（4543） | 图谱：存、查、解析、增量、envelope | 把事实连成**关系** |
| | | `state/`（2806） | 快照、变更、失效标记、实时层 | 时间维度：**和上次比变了什么** |
| | | `understand/`（5662） | 契约、体检规则、容器判定、`guide` | 把事实变成**判断** |
| **③判定** | **高** | 同上（`understand/rules.rs` 的 `enforce_evidence`、`Verdict<T>`） | 三态 + 三道闸 | "可信"这个词的落点 |
| **④呈现** | **高** | `ui/`（7128） | 七个页签、画布、卡片、分级 | 送到人眼前 |
| | | `cli/`（2993） | 命令、三态退出码、`--json` | 送到脚本/终端 |
| 外围 | 低**但不许欠债** | `src-tauri/`（1366） | 命令桥、自检报告、深链接 | 壳 |
| | | `tools/`（3757） | 4 道门禁、采集真源、打包、造演示 | 守"承诺=事实" |
| | | `model/`（788） | 领域模型（13 实体/16 关系） | 共同语言 |

**这份账说出的三件事**：

1. **`sys` 占引擎 1/6，而它是"转述操作系统"**。它有价值（机器事实是判断的一部分），
   但**它的权重不该与 `understand` 同级**——它没有加工，只有采集。
   → **决定：`sys` 归入①采集，权重与 `detect` 同级；新增功能优先度低于③④。**
2. **`ui` 有 7128 行，比 CLI 多一倍多**。这符合"外形与核心同等投入"的要求——
   但**行数不等于质量**：实测里最坏的缺陷（画布塌成一小块、图乱作一团）都在这一栏。
   → **决定：④呈现的权重定为与③判定同级，"能看见的坏"优先于"新的能"。**
3. **`tools` 有 3757 行**，其中大量是**给流程搭的脚手架**（门禁/账本/真源脚本）。
   它是必要的（它抓出过 6 次"承诺≠事实"），但它**不产生用户价值**。
   → **决定：外围的活儿只在"它拦住了真交付"时才做；不再主动发起。**

---

### 三、权重怎么用（一轮里怎么分精力）

### 3.1 硬比例（每 5 轮为一个大周期）

| 段 | 轮数 | 说明 |
|---|---|---|
| ①采集 + ③判定 | **2 轮** | 可信是根，且这两段是"信息量"的来源 |
| ④呈现 | **2 轮** | 与③同级——**这一栏是过去最欠的** |
| ②加工 | **1 轮** | 它的正确性由③暴露；没有③的加工是自娱 |
| 外围 | **0 轮**（只在被拦住时插入） | 见 3.3 |

### 3.2 不许偏科的判据（可自查）

**连续 3 轮以上只有外围在动 → 判定为偏科，立刻回到①③④。**
（这条是实测出来的：账本类消耗在本项目里曾经占到大头。）

### 3.3 外围的插入条件（只有这两条）

1. **门禁/测试红了**，而且它挡着当前这一轮。
2. **文档承诺与代码事实不一致**，而且用户会看到那个不一致。

**其他情况一律不做。** 包括：整理文档、重命名、重构、加新门禁、写账本。

---

### 四、每条链的"输入 → 输出"契约（防止互相污染）

| 段 | 输入 | 输出 | **不许做的事** |
|---|---|---|---|
| ①采集 | 项目目录、机器 | `Facts`（纯事实） | **不做判断、不下结论、不排优先级** |
| ②加工 | `Facts` | 关系（图谱）/ 变化（快照） | 不许把"猜的"混进"事实"里 |
| ③判定 | `Facts` + 关系 | `Finding`（带来源与自查）/ `Guide`（带排序） | 不许**无来源**、不许**无自查**、不许压三态 |
| ④呈现 | ③的输出 | 界面 / 终端 / JSON | 不许**自己算**（那是内核的事）；不许**藏起来没入口** |

**"不许自己算"这一条踩过坑**：`diag` 曾经两处各算一遍。
现在**同一个内核入口，两份外壳**是硬规矩。

---

### 五、现状：每一段做到哪了、缺什么

| 段 | 有 | **缺**（这就是下一步该做的） |
|---|---|---|
| ①采集 | 语言/依赖/工具链/系统/解析 都在 | 采集的**来源分级**还没有在类型上强制（`Facts` 里没有"这条事实来自哪、多可信"） |
| ②加工 | 图谱能索引 Rust+Python、增量三级检测 | 关系的**语义层**薄：只有 contains/defines/calls，没有"谁依赖谁"的传递闭包 |
| ③判定 | 三态、三道闸、`guide` 的排序 | **"查不了"在多数规则里没有出口**——很多地方只有"报/不报"两支 |
| ④呈现 | 七页、画布、分级文案 | **图谱页刚修一半**（尺寸已修、布局待验）；**信息层级多数页面还是罗列** |

**下一步的优先顺序（按上表"缺"那一列，结合权重）**：
1. ④ 把图谱页收口（**能看见的坏，优先**）
2. ④ 把"罗列"改成"分级"——挑**概览页**先做（它是打开项目第一眼）
3. ③ 给规则补上"查不了"的出口
4. ① 给 `Facts` 的来源分级定类型

### 六、判据速查（放这儿，因为架构决定都靠它）

- 新模块进来前先答：**它替哪一段干活？** 答不上来就别加。
- 新功能进来前先答：**它让哪一句话更可信/更准时/更好懂？**
- 动手前先写：**这一处学的是外界哪一样东西、学它哪一点。**
- 收尾必须给：**门禁结尾 + 改动范围 + 改前确实坏过的证据。**


## 边界（2026-10-20，来自外部观点的吸收，pro 裁）

- **判断只在 engine 一份，DB 只存事实**：图谱是源码的派生投影，不是事实源。
  "把业务逻辑写进数据库"在这里**不成立**——一旦下沉，三态（是/不是/查不了）和来源分级都会被 SQL 抹平。
  但保留它的内核：**最省事 = 最少移动部件**。
- **新依赖是永久成本**：加库要先改 `tools/deps-baseline.json` 并在提交信息写理由（门禁守）。
- **数字要能复现**：性能/规模结论必须带复现命令与对照（`tools/regress.mjs` / `bench/`）。
