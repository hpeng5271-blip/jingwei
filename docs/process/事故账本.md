- **假 Error：Rust + 前端的项目里，每条 npm 依赖都被拿去查 `Cargo.lock`**（2026-10-16 实测抓出，已修）：
  - **现象**：`jingwei guide --root D:\projects\jingwei` 报
    「✗ 现在跑不起来 · 1 个依赖没装：**@tauri-apps/cli**」（退出码 1）。
    而 `package.json` 里明明写着 `"@tauri-apps/cli": "^2"`，
    `node_modules/@tauri-apps/cli/package.json` **实实在在在磁盘上（2454 字节）**。
    **同一个仓库的旧目录 `pylaunch-rs` 报出完全一样的一条**——这才让我去查。
  - **根因**：`detect/deps.rs::installed()` 的第一个分支写的是
    `root.join("Cargo.toml").is_file() && lang != Lang::Python`——
    **判据是"这个目录里有没有 `Cargo.toml`"，而不是"这条依赖属于哪门语言"**。
    Tauri 项目两样都有，于是 `@tauri-apps/cli`（`Lang::Web`）被塞进 Rust 那一支，
    去 `Cargo.lock` 里找 `name = "@tauri-apps/cli"` → 找不到 → `Verdict::No` → 报「没装」。
  - **修法**：判据换成 `matches!(lang, Lang::Rust) ||（Unknown 且 Cargo.toml 在）`。
    依赖的归属由 `Decl.lang` 一路带下来，**这里是它该被用上的地方**。
  - **教训（这是本条最值钱的一句）**：
    **用"环境里有什么文件"代替"这个对象属于哪一类"，就会得到假结论。**
    它与 `Lang::Rust` 变体补上之前那三次"绕道"是**同一类错**——
    上次是"用清单文件的存在性冒充 Rust"，这次是"用 `Cargo.toml` 的存在性冒充 Rust 依赖"。
    **同一个错换了个位置又长了一次。**
  - **回归测试**：`依赖归属由语言决定而不是目录里有什么文件`——造一个"两样清单都在"的混合项目，
    三个断言：① Web 依赖查 `node_modules` ② Rust 依赖仍走 `Cargo.lock`
    ③ **交叉验证**：`vue` 在 Rust 视角下确实是 `No`（那不是误报，是它真不在 `Cargo.lock` 里）。
    **做过负向验证**：退回旧判据 → 红在「Web 依赖要查 node_modules——有 Cargo.toml 不代表它是 Rust 依赖」。
  - **它是怎么被发现的**（这条对"怎么找 bug"有用）：**不是单元测试**，
    而是**拿五个真项目挨个跑 `guide`**。前一个假设（"它在往上找父目录的清单"）
    **当场被推翻**（父目录一个清单文件都没有），推翻之后才看见真正的那一支。
    → 与 §2「拿真东西去问」是同一课，只是这次的"真东西"是**一批真项目横向跑同一命令**。
