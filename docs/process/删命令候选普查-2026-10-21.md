# 删命令候选普查（2026-10-21）

## 我先前的假设是错的

计划里写"真删 `snap` / `clean` / `env`"，理由是"看着没人用"。**grep 一跑就不成立**：

| 命令 | 提到它的文件数 | 说明 |
|---|---|---|
| `env` | **130** | 环境检测是核心概念，不可能删 |
| `clean` | **33** | 清理是"能删什么"的一整条线，文档/规则里到处都是 |
| `snapshot` | **26** | 快照概念在多处复用（扫描缓存、环境快照…） |
| `snap` | **8** | 与 `snapshot` 语义重叠，删它要连概念一起理 |

## 结论（修正计划）

1. **"按感觉挑三个删"是错的**——`env` 根本不是候选，`clean` 是一条线不是一个命令。
2. 真正该删的判据应该是：**只有它自己、没有别的命令/文档依赖的概念**。按这个口径，候选要重新挑。
3. 更稳的路：**先量使用，再删**。但仓库现在**没有命令调用日志**（`limits.mjs` 统计的是 pro 咨询，`rounds/decisions` 都是 0）。
   → 所以第一步不是删，是**加一行调用记录**（`~/.jingwei/usage.jsonl`：时间 + 命令名 + 退出码），跑一周后再按真实调用数删。

## 下一步（替换原计划）

| 原计划 | 改成 |
|---|---|
| 删 `snap` / `clean` / `env` | **先加 usage 记录**（`~/.jingwei/usage.jsonl`），一周后按真实调用数删 |
| —— | 同时：把 `env` 从"候选"里永久划掉（130 处依赖，是核心不是尾巴） |

**判据**：一周后，`usage.jsonl` 里调用次数为 0 的命令才是删除候选；仍要 grep 引用确认无测试/文档依赖。
