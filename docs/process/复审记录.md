# 设计复审记录（十遍章程）

> 这是地基层，所以按章程反复过。**关键不是"过十遍"，是每遍换一个视角**——
> 用同一个视角看十遍，只会看到同一个东西十次。
>
> 每一遍的范围都是**全量**：`设计.md` + `数据层设计.md` + `crates/model` + 现有代码。
> 每遍必须产出三样：**发现（带证据）· 改动（增/删/改）· 门禁结果**。

---

## 0. 十个视角（每遍一个）

| 遍 | 视角 | 这一遍只问一个问题 |
|---|---|---|
| **P1** | **事实核验** | 文档里每个数字/命令/引用，**出处是哪、能不能复现**？ |
| **P2** | **一致性交叉** | 同一件事在几处出现时，**说的是不是同一句话**？ |
| P3 | 正确性与不变量 | 边界、退化、误报：**出错时它会不会安静地错**？ |
| P4 | 承载力与性能 | 实测数字、预算、增长模型：**到多大会崩，怎么知道**？ |
| P5 | 安全与隐私 | 权限、路径、注入、敏感数据：**最坏能坏到哪**？ |
| P6 | 可用性与信息架构 | 场景清单 → 每屏职责：**第一次用的人会不会迷路**？ |
| P7 | 可维护性与发布 | 依赖、lint、测试、迁移、发布：**半年后还能改吗**？ |
| P8 | 生态与集成 | 外部工具 / LSP / 各语言：**别人的约束吃透了吗**？ |
| P9 | 外部借鉴的吸收与裁剪 | IDEA / MC UI / HPC / 游戏引擎 / 数据库内核：**抄来的对不对路**？ |
| P10 | 反脆弱与极端场景 | 断电、并发、磁盘满、超长路径、超大项目、恶意输入：**会怎么死**？ |

## P1 · 事实核验（第一遍）

### 1.1 方法

把两份设计稿里**所有可核验的断言**逐条抓出来（数字、命令、外部事实），
按来源分三级：**实测**（本机可复现）· **引用**（外部来源，未在本机复现）· **估算**（写明算法）。

### 1.2 结果：数字的来源分级（这是本遍的主要产出）

| 断言 | 级别 | 出处 / 复现方式 |
|---|---|---|
| SQLite 3.53.4 / FTS5 可用 | **实测** | 本机 Python `sqlite3`；`pragma compile_options` |
| 1.21M 行灌注 12.25s、库 77.3MB | **实测** | `数据层设计.md` §0 的探针（已删脚本，语句保留可重跑） |
| 点查/1 跳/FTS 0.00–0.03ms | **实测** | 同上 |
| `(file_path,kind)` 24.27ms → 0.03ms | **实测** | 同上（改索引前后各测一次） |
| 8 跳稠密图 9,841 行 / 2.8ms | **实测** | 同上 |
| FK 级联 / integrity_check / FTS 同步 | **实测** | 同上 |
| `wal_checkpoint(TRUNCATE)` 8ms | **实测** | 同上 |
| 打字路径 126ms → 0.57ms | **实测** | 项目内实测（改前改后各一次） |
| 打包体量 2.5MB / 项目 26.2MB | **实测** | `dist/*.zip`、目录统计 |
| tree-sitter 增量 65µs / 1600 行 8× / 16k 行 14× | **引用** | 来自对话中引用的第三方基准（lattice / perl-lsp-swarm），**未在本机复现** |
| SQLite 点查比 PostgreSQL 快 30–60× | **引用** | 同上（knowledge-graph-rdbms 基准） |
| Tauri IPC ~0.5ms/次；tauri-wire 28×/33×/−44% | **引用** | 同上（tauri-wire 基准） |
| LSP 冷启动 60–120s；rust-analyzer 单实例 22–39GB | **引用** | 同上（社区报告），**与本机无关** |
| 打包体量估算 10–22MB（全量 25–50MB） | **估算** | 按各组件单独体积相加；未做完整打包验证 |
| 容量模型"每 1000 文件 ≈ 8MB" | **估算** | 由 1.21M 行 77MB 按行数比例外推 |

### 1.3 本遍改动（增）

**给 `数据层设计.md` 增加"数字来源分级"要求**：凡出现数字，必须能回答"哪一级、怎么复现"。
**理由**：这份设计的核心承诺之一是"每条结论都要能自己验证"——设计稿自己先得做到。
**具体落点**：`数据层设计.md` §16（新增）。

### 1.4 本遍遗留

- 全部**引用级**数字，等 M3/M7 真正接上 tree-sitter / LSP 时在本机复测一遍；
  复测前，文档里它们**只能当参考，不能当预算**。
- `估算级`的容量模型需要用一次真实全量索引校准（M4 做）。

找"同一件事在多处出现"的地方，逐一比对：**文档之间**、**文档与代码之间**、**清单与 DDL 之间**。

## P3 · 正确性与不变量（第三遍）

**这一遍只问**：出错时它会不会**安静地错**？

### 3.1 发现（六条，全部带证据）

| # | 发现 | 证据 | 严重度 |
|---|---|---|---|
| **A** | **三态被压成布尔**：`deps_status: BTreeMap<String,bool>` 被三处消费——`src-tauri/main.rs:155`（**发给前端**）、`crates/engine/rules.rs:699`（**规则判断**）、`snapshot.rs:209`（变更比对）。C++ 项目里"查不到"的包，到这两处就变成 `false` = **缺失**；规则会照着"缺失"报，界面会照着"未安装"显示 | `rg deps_status` 三处命中 | **高**（这正是本系统最不能犯的错） |
| **B** | **结论可以绕过校验**：`Conclusion` 的字段全是 `pub`，任何人都能直接塞一个 `level: Error` 进去——"估的不许报 Error"**只靠自觉**，等于没写 | `rg "pub level" crates/model/src/lib.rs` → 命中 | **高**（一条核心纪律落空） |
| **C** | **截断不告知**：多跳查询有 10 跳上限，超出的关系看不到，但返回值里没有"被截断"的标记 → 用户会把"看不到"读成"不存在" | 设计 §7 只写了上限 | 中 |
| **D** | **失效边可能被读到**：设计只说"查询时过滤 `expires_at`"，没规定用视图。第一个写 store 的人漏一次，就会读出幽灵边 | `rg "FROM edges"` → 0 命中（store 尚未存在，属前瞻风险） | 中 |
| **E** | **`checksum` 语义未定义**：设计要它服务抽样校验，但没说算"单节点指纹"还是"文件节点集合指纹" → 实现时各写各的 | `数据层设计.md` §3.2 只有列名 | 中 |
| **F** | **静默忽略的规模未知**：`let _ =` 在 engine 里有 40+ 处，抽样看到的都是测试清理（无害），但没有机制保证生产路径不混进去 | `rg "let _ = "` | 低（但会累积） |

### 3.2 本遍立即修掉的

| # | 改动 | 落点 |
|---|---|---|
| B | **`Conclusion` 字段私有化，只留 `Conclusion::new` 一个入口**（里面就是 `error_checked` 那三道闸）+ getter + `with_boundary/with_next/suppressed` 链式设置 | `crates/model/src/lib.rs`；15 项测试改走受检入口后仍全过 |
| F | **workspace lints 打开 `clippy::let_underscore_must_use`**：以后所有"忽略 Result"的点会被列出来逐个判定，而不是靠人记得 | `Cargo.toml` |
| A | **给 `deps_status` 加废弃告警注释**（标明"会丢三态，禁止新代码使用"，指向 `deps_detail`），并写清清理计划与触发点（M2 接 store 时一并改） | `crates/engine/src/facts.rs` |

### 3.3 本遍记为待办（带 DoD，不许无期限挂着）

| # | 待办 | DoD（做到什么算完） | 触发点 |
|---|---|---|---|
| A | 规则引擎与 Tauri 输出改走三态 `deps_detail`，删掉 `deps_status` | `rg deps_status` 在 crates/ 与 src-tauri/ 里 **0 命中**；且有测试断言"unknown 不进缺失计数" | **M2** |
| C | 多跳查询返回 `truncated: bool`，界面能显示"还有更深的关系未展开" | 有一个环状深图的测试，断言 `truncated == true` 且界面出现提示 | M2 |
| D | 建 `live_edges` 视图，**只许查视图** | 视图存在；`rg "FROM edges"` 只允许出现在视图定义与迁移脚本里 | M2 |
| E | 定义两种指纹：`nodes.checksum` = 单节点指纹（kind\|name\|file_path\|line\|data 规范化）；文件级集合指纹存 `files.nodes_sha` | 文档写明算法；抽样校验测试通过 | M2 |

### 3.4 这一遍的方法论收获

**"不误报"这条纪律，只写在文档里就一定会漏。** 它必须被三次上锁：

1. **类型层**：三态是类型（`Verdict`）、置信度是类型（`Confidence`）——已做
2. **构造层**：结论只能过受检入口（`Conclusion::new`）——**本遍补上**
3. **查询层**：只许查 `live_edges` 视图，不查基表——**待 M2 补**

三层任意缺一层，纪律就退化成"希望大家记得"。

## P4 · 承载力与性能（第四遍）

**这一遍只问**：到多大会崩，我怎么知道？

### 4.1 做法：把数字变成可复跑的脚本

新增 **`tools/db_probe.py`**：用系统自带 Python + 标准库 sqlite3 建出与设计
**一字不差**的库（DDL 与 §3 同步），灌数据、量体积、跑查询计划、验不变量。
**从此设计里的每个数据库数字都可以就地复跑**——这是 P1 那条"数字必须有出处"的落地。

### 4.2 实测（两个规模点）

| 规模 | 行数 | 库体积 | 字节/行 | 点查 | 1 跳 | 3 跳 | FTS |
|---|---|---|---|---|---|---|---|
| 10k 文件 / 20 符号 | 410,000 | 74.6 MB | 182 | 0.01ms | 0.00ms | 0.02ms | 0.02ms |
| 20k 文件 / 20 符号 | 820,000 | 153.2 MB | 187 | 0.00ms | 0.00ms | 0.02ms | 0.03ms |

**体积组成**（820k 那次）：nodes 46% · edges 22% · 索引 19% · FTS 12%。

### 4.3 发现（三条，一条是硬错）

| # | 发现 | 证据 | 处理 |
|---|---|---|---|
| **A** | **容量模型是错的**：文档写"50 万节点 ≈ 30–40 MB"，实测比例是 **≈185 字节/行**，50 万节点 + 200 万边 ≈ **460 MB**——**差了 4–10 倍** | 两个规模点线性外推 | 已改：容量模型改为"行数 × 185B"，并附换算表与"50 万节点时该重审什么" |
| **B** | **写入吞吐有两个数，容易误读**：批量 UPSERT ≈10 万行/秒；逐条 UPSERT ≈1.5 万行/秒（**那是脚本瓶颈，不是 SQLite**） | `db_probe.py` 逐条执行；早先探针用 executemany | 已改：§11 把两个数并排列出并各自标注瓶颈归属 |
| **C** | **查询延迟不随规模退化**（两个点都是 0.00–0.03ms），体积线性——**所以瓶颈确认不在数据量**，而在 CTE 深度 / 索引选错 / 长事务 | 上表 | 已在 §11 写明，并有两点支撑 |

### 4.4 本遍新增的纪律

> **脚本与设计同源**：`db_probe.py` 的 DDL 与设计 §3 必须一致；
> 改设计就要同步改脚本，否则数字与设计会各走各的（这和 P2 那条"同一事实只允许一个可编辑副本"是同一类问题，
> 属于它的镜像：**可执行副本也必须跟得上**）。

### 4.5 本遍记下的待办（带 DoD）

| # | 待办 | DoD | 触发点 |
|---|---|---|---|
| 1 | 把 §6.3 的六项预算各配一条**可执行的基准**（现在只有数字，没有命令） | 每项预算都有对应命令与阈值，能一条条跑 | M2（store 落地后改用 criterion） |
| 2 | 校准"首次全量索引 <120s"这条 | 用 `db_probe.py --files 20000` 的灌注时间作参考上界（56.7s 是脚本瓶颈上界） | M4 |
| 3 | 引用级数字（tree-sitter / LSP）本机复测前**不得当预算** | 文档里这些数字旁都标注「引用，未复现」 | M3 / M7 |

## P5 · 安全与隐私（第五遍）

**这一遍只问**：最坏能坏到哪？

### 5.1 发现

| # | 发现 | 证据 | 严重度 |
|---|---|---|---|
| **A** | **打开陌生项目会自动执行它里面的命令**：`afterAuto` 在 `SET.trial`（**默认 true**）下自动 `launch_project`，而启动命令来自项目里的契约文件。**一个 clone 下来的项目 = 一次自动的任意程序执行** | `ui/app.js:48` `trial: true`；`main.rs:627 launch_project` | **严重** |
| **B** | **敏感文件原来是被"放行"的**：可编辑白名单里写着 `env`，还专门 `base.starts_with(".env")` → `.env` 会被列进文件树并读进内存。`id_rsa` / `*.pem` / `*.key` / `.npmrc` / `.git-credentials` 同样没有任何拦截 | `crates/engine/src/workcopy.rs` 旧白名单 | **高** |
| **C** | 契约命令本身是**用户可编辑的字符串**（这是设计要的），但它随项目走 → 与 A 叠加就是"项目文件决定执行什么" | 设计 §1.2 与 `contract.rs` | 中（由 A 的机制兜住） |
| **D** | **日志可能带绝对路径**（含用户名） | 待核：`dlog` 的记录点 | 中 |

**同时确认**两条**已经守住**的（复审不只是找问题）：

- **Tauri 权限最小**：`capabilities/default.json` 只有 `core:default` + `dialog:default`，
  **没有文件系统 / shell / 剪贴板插件权限** → 前端无法直接读写文件或起进程（文件与进程都在自研 command 里）。
- **没有任何网络依赖**：`rg reqwest|ureq|hyper|surf` 在全部 `Cargo.toml` 里 **0 命中** → 结构上不存在"偷偷把代码传出去"的可能。

### 5.2 本遍已修

| # | 修法 | 落点 |
|---|---|---|
| **B** | 从白名单**移除 `env`**、删掉 `.env*` 放行；新增**敏感文件拒绝清单**（`.env*` / `id_rsa*` / `.npmrc` / `.pypirc` / `.git-credentials` / `.netrc` / `credentials` / `.htpasswd` / `keystore` / `.tfstate` + 扩展名 `pem/key/p12/pfx/jks/ppk/kdbx`），命中就**不列、不读**。附测试：8 个敏感文件一个都不许出现在可编辑列表里，同时普通源码与 `.gitignore` 照常列出 | `crates/engine/src/workcopy.rs`（142→143 项测试） |

### 5.3 本遍记为待办（带 DoD）

| # | 待办 | DoD | 触发点 |
|---|---|---|---|
| **A** | **给"自动执行"加信任机制**：① 自动试运行**默认关闭**；② 对某个项目首次自动执行前，界面必须显示**原样命令**并要求确认一次，决定记进 `.drydock/trust.json`；③ 未确认的项目，自动流程只允许**只读**动作（扫描/检查/构建产物分析），不跑 `run` | 有一个陌生项目（比如从压缩包解开、无 trust 记录）被打开时**不会执行任何命令**的测试；界面上能看到"将执行：<命令>" | **M4**（与一条龙接线时） |
| C | 契约命令在 UI 上**永远原样显示**，任何位置都不做字符串拼接后再执行 | `rg "format!.*run" 执行路径` 为空；有测试断言带 `&&`/`|` 的命令被原样展示 | M4 |
| D | 日志只记**相对路径 + 短码**，不记文件内容、不记绝对路径 | 抽查一份日志：无绝对路径、无文件正文、无令牌样式字符串 | M5 |

### 5.4 这一遍的方法论收获

**"安全"在文档里写"不读取密钥"是零成本的一句话，落到代码里是"白名单里别写 env"。**
本轮抓到的问题不在设计条文，在**实现细节把设计意图反过来做了**（"可编辑文件"的名单
顺手收进了 `.env`，于是密钥文件从"被保护"变成"被打开"）。

→ 所以每一遍复审都必须同时看**文档**与**实现**，光对文档是查不出来的。

## P6 · 可用性与信息架构（第六遍）

**这一遍只问**：第一次用的人会不会迷路？

### 6.1 十个核心场景（从"第一次打开"到"长期使用"）

| # | 场景 | 用户此刻想知道 | 界面必须给的 | 绝不该出现的 |
|---|---|---|---|---|
| 1 | 第一次打开 | 这是什么、我该干嘛 | **一句话定位 + 一个明确的第一步** | 满屏并列控件（现在欢迎页有 4 类控件：父目录/深度/扫描/选目录 + 打开已有 + 新建） |
| 2 | 扫出项目流 | 这些项目是什么状态 | 整行横幅 + 关键词小字（类型/最近改动/契约/待处理/卫生） | 空白表格、只堆名字 |
| 3 | 看一个项目缺什么 | 卡在哪、先修哪个 | 概览的结论卡（按排查层排序）+ 每条四要素 | 平铺 50 条不排序 |
| 4 | 跑起来 | 正在干什么、跑到哪了 | 阶段流面板（每步一块，关键行 ≤3，原始输出折叠） | 一块糊满字、跑完就消失 |
| 5 | 跑失败了 | 根因是什么、下一步点哪 | 症结 + 受影响面 + "去看终端最后几行" | 只丢一个退出码 |
| 6 | 改代码 | 我改了会影响什么 | 编辑器（画布）+ 应用前留版本 + 变更检测卡片 | 改了不告诉我影响了什么 |
| 7 | 看依赖 | 声明和实际对不对得上 | 声明 → 实际 两列 + 三态 + 传递树 | 只给"装了/没装"两个状态 |
| 8 | 清理空间 | 哪些能删、删了会怎样 | 三区（能删/要权限/别碰）+ 每项后果 | 一个"一键全清" |
| 9 | 看机器 | 这台机器有什么、哪里不对 | 快读摘要 + 深入才展开 | 首屏堆 200 行 |
| 10 | 做记录 | 我今天干了什么、学到什么 | 项目卡片流 + 记录/笔记 + 运行日志可引用 | 空白笔记框 |

### 6.2 发现（五条）

| # | 发现 | 为什么是问题 | 处理 |
|---|---|---|---|
| **A** | **欢迎页没有"顺序"**：扫目录、选目录、打开已有、从模板新建四类动作并列，新用户不知道先点哪个 | 第一屏决定他会不会继续用 | **已写进设计 §2**：空状态只给**一条主路径**（选目录扫描），其余降为次要按钮；并加三步小标（① 选目录 → ② 看它缺什么 → ③ 跑起来） |
| **B** | **"抑制下位"可能是永久沉默**：如果上层根因一直没修（例如用户暂时不想装工具链），下位结论**永远不出卡**，用户会以为"这工具什么都不说" | 过滤是本系统的核心价值，过滤过头 = 价值归零 | **已写进设计 §8.3**：不仅规定"隐藏必须可查"，还规定**入口形态**——问题栏底部固定一行「另有 N 条被上层挡住 · 查看」，点开按原因分组列出 |
| **C** | **失败时的"出路"没有清单**：路径不存在、无权限、磁盘满、文件被占用、检查器未装——这五种各有不同的正确说法与下一步，现在没有统一规定 | 失败态是新手最容易放弃的地方 | **已写进设计 §10.5**：给出**失败出路表**（症状 → 界面说什么 → 用户能点什么） |
| **D** | **跑完之后没有"然后呢"**：一条龙跑通后，怎么停、怎么复跑、怎么看这次留了什么，没有显式引导 | "跑通"是成就感最强的一刻，此处断链最可惜 | **已写进设计 §9.4**：跑完后在阶段流末尾固定给三件事——① 怎么停 ② 怎么复跑 ③ 这次留下了哪条记录（可点） |
| **E** | 窄窗口下状态栏/工具窗的取舍未定 | 低优先 | 记为待办（P10 一起看） |

### 6.3 本遍的方法论收获

**"信息过滤"这个词本身有陷阱**：它听起来是"砍掉多余的"，但真正难的是**砍掉之后怎么让人相信没丢东西**。
所以过滤系统必须自带两个出口：

1. **时间出口**：被压下的东西，根因解决后要**自动浮回来**（不是"永远不再提"）。
2. **位置出口**：任何被隐藏的，都要能在一个**固定位置**查到（不是"我们自己知道它被过滤了"）。

这一遍把这两个出口都写成了设计要求，而不只是原则。

### 7.2 五条发现

**A. lint 只在一个 crate 里生效，等于没有。**
P3 记下的"已修：打开 `let_underscore_must_use`"**只对 `jingwei-model` 生效**——
workspace lints 需要各 crate 显式写 `[lints] workspace = true`，而只有 model 写了。
engine 里 22 处吞 Result，一处都没被拦。**这是最阴的一类失效：文档上写着规矩，门禁上什么都没发生。**

→ 已修：四个 crate 全部继承；22 处逐条处理——有信息量的转成日志（新开 9002–9006 五个码），
无信息量的写一句理由后显式豁免。

**B. 42 处 `unsafe`，一个 `// SAFETY:` 都没有。**
unsafe 是这套代码里唯一能弄出内存不安全的地方，而 42 个块里没有一处写"凭什么安全"。
补注释的过程里挖出两件必须记下来的事：

- `Process32FirstW` 要求 `dwSize` 在**第一次**调用之前就填好。代码手写 `Default` 正是为了
  这个——而"为什么手写"的理由原来没写。谁把它改成 `derive`，得到的结果是**一个进程都数不到**，
  界面看起来像"机器上什么都没跑"，不报任何错。
- `clean.rs` 的占用探测靠"改个名试试"，改完**必须改回来**。原来失败是静默的——
  静默的后果是用户的目录顶着 `.jingwei-probe` 这个名字留在原地，而界面上什么都不说。
  这不是清理时的边角，这是**改了用户的东西**。

→ 已修：开 `undocumented_unsafe_blocks`，42 处逐一补齐。

**C. 改名不是替换字符串，是引入兼容面。**
四处"改了就会静默坏事"的地方（详见设计 §1.4）。最典型的是忽略文件的标记：
只认新标记 `# added by jingwei` 的话，老项目里盖着 `# added by drydock` 的文件会被**再盖一遍**，
用户文件里平白多一行。

**D. "同一事实只允许一个副本"这条规矩，被自己破了两次。**
1. 设计.md §5 里留着一份完整的旧 DDL——实测把三处设计改掉后，这份副本没跟着改，
   于是同一份表结构有了两个互相矛盾的版本，读到哪份全凭运气。（已删，只留"为什么这么设计"）
2. 版本号 6 处副本。（已收敛：Cargo 三处用 `version.workspace = true`，
   并由 `tools/gate.mjs` 校验与 `tauri.conf.json` 一致）

**E. 门禁靠人记得跑，就总有一天不跑。**
→ 已加 CI（`.github/workflows/gate.yml`），并把两条"编译器管不了"的规矩写进 `tools/gate.mjs`。

### 7.3 一个取舍：规矩怎么长牙，又不一次把人压垮

单文件 1000 行这条规矩，实测 5 个 Rust 文件超限（最大的 2128 行）。只有两条路可选：

- 立刻全部拆完 → 一次伤筋动骨的大重构，而且要和 M2 抢时间；
- 把上限调高 → 这条规矩从此是橡皮筋，下次还会再调。

选了第三条：**登记在案，只许降不许升**。
超限的**新**文件直接失败；已经超限的写进 `gate.mjs` 的 `KNOWN_LONG` 表，
一旦比登记值更大就失败，变小了就提示把登记值改小。

这不是放水——是把一次性还不起的债，转成**不能继续恶化**的债，而且账是公开的（门禁脚本里看得见）。

### 7.4 这一遍的方法论收获

**发布视角能查出别的视角查不出的东西**，因为问法不同：它不问"对不对"，问"**换个人来接，接得住吗**"。

这一遍里，凡是"只有作者本人知道"的地方全都暴露了：没有 CI、根目录没有 README、
里程碑指向一个不存在的 crate、lint 只写在文档里而没写进 `Cargo.toml`、改名留下的兼容缺口。
**这些在功能视角下全都不是问题**——功能视角只会看到"能跑"。

## P8 · 生态与集成（第八遍）

**这一遍只问**：接进来的每一个外部系统，我们**问对地方了吗**？

### 8.1 先立判据

**"装了"是用户的事，"我们找到了"是我们的事。**
少列一个来源，就是一次误报——而误报是这个项目最不许犯的错。
所以每种工具链都得能回答"用户可能把它装在哪"，而且这份清单要能**逐条核对**。

### 8.2 逐条实测

| 工具链 | 现在的来源 | 判定 |
|---|---|---|
| **Python** | 环境变量（新旧名双读）、契约绑定、项目内 venv、PATH（**刻意不排除 `WindowsApps`**，理由写在代码里）、`LOCALAPPDATA` 下三个位置、`C:\Python3xx`、**`py -0p`**、scoop、conda（两处）、`.local/bin`、便携目录 | **标杆**。`py -0p` 那条尤其对：问的是"系统登记过的解释器"，比任何目录猜测都权威 |
| **Java** | `JAVA_HOME`、PATH、六个发行版安装目录、便携目录、`.java-version`、`~/.m2/toolchains.xml`（Maven 官方的多 JDK 机制） | 好，但缺 4 处 |
| **C / C++** | PATH、`SDK`/`tools`/`msys64`/`LLVM\bin` 等便携目录；分 gnu / llvm / msvc 三家族；`cl.exe` 不给 `--version`（它打印横幅） | 中，**缺最要紧的一条** |
| **Web / Node** | 只读 `package.json` 与 `node_modules` | **缺口**：根本没探测 node / npm / pnpm |

### 8.3 补掉的四处（共同点：装了却说没装）

1. **Java：`%USERPROFILE%\.jdks`** —— IDEA 自己下载的 JDK 放这儿，**既不写 `JAVA_HOME` 也不进 PATH**。用 IDEA 的人（正是本工具的目标用户）最容易撞上。
2. **Java：Microsoft / Semeru / GraalVM / `.sdkman`** —— 三个发行版 + 一个版本管理器，同理。
3. **Python：`.pyenv/pyenv-win/versions`** —— pyenv 的版本**故意不进 PATH**（那正是它的用法）。不认这条线，等于把 pyenv 用户判成"没装 Python"。
4. **C/C++：`vswhere.exe`** —— 这条最要紧。Visual Studio 装的 MSVC **不在 PATH 上**，要它出现在命令行里必须先跑 `vcvarsall.bat`。微软官方为此提供了 `vswhere.exe`（位置固定，随 VS Installer 装）。补上它之前，"装了 VS 但工具说没有 C++ 编译器"是**必然**会发生的误报。

### 8.4 一个"路径写对了、但问法不对"的例子

**uv 的 Python 装在哪？** 代码里硬编码了 `%LOCALAPPDATA%\uv\python`。

查官方文档（`docs.astral.sh/uv/reference/storage/`）拿到的原话是：Python 版本默认放在
persistent data directory 的 `python/` 子目录，而且**可以用 `UV_PYTHON_INSTALL_DIR` 覆盖**，
官方还专门给了 `uv python dir` 这条命令来回答"到底放在哪"。

所以正确做法是：**uv 在 PATH 上时问 `uv python dir`，拿不到再退硬编码路径**。
这正是这一遍要抓的东西——**硬编码是猜；官方给了查询命令的，就该去问**。
（`py -0p` 已经是这个做法，uv 还没跟上。）
→ 记为待办（带 DoD），因为它要新增一次进程调用，属于探测策略的改动，不混进这次的小修里。

### 8.5 tree-sitter："按需加载语法包"的前提，比写着的严

设计里写着"语法包按需加载，缓存在 `.jingwei/grammar/`"。查实际（官方仓库与 docs.rs）后：

- 动态加载确实是官方支持的路：`tree-sitter-loader` 用 `libloading` 加载 .dll/.so/.dylib；
  但它**同时依赖 `cc`**——也就是说"在用户机器上现场编译"是一条真实存在的路径。
- 语法包有 **ABI 窗口**：`TREE_SITTER_LANGUAGE_VERSION = 15`、
  `TREE_SITTER_MIN_COMPATIBLE_LANGUAGE_VERSION = 13`。core 与 grammar 的版本必须落在窗口里。

**结论（已写进设计 §6.1）**：目标机器上**没有 C 编译器**（这一条正好被 8.3 的第 4 点说明）。
所以"按需编译"走不通，实际只剩一条路：**预编译的 .dll 随发行版分发，运行时按需加载**。
"按需"的真正含义因此是**按需加载与按需解析**，不是按需编译。代价两条：发行包变大；
升级 tree-sitter core 时要重新编译全部语法包。

### 8.6 判据实测：加一门语言要改几个地方

设计 §1.2 原本写着："加语言时**不需要改 engine**（这是抽象是否合格的判据）"。

实测：`Lang` 是硬编码的五值枚举（Python / Java / Cpp / Web / Unknown），`Lang::` 出现在
**6 个文件**里，其中 **8 处是真分支**（`match lang` / `match opts.lang`）。
也就是说——**这条判据现在是假的**。加一门 Go 或 Rust，要动 `lang.rs`、`deps.rs`、
`scaffold.rs`、`probe.rs`、`rules.rs`、`projects.rs`。

**改法**：判据本身要留住，但它得先能判定。已改写为：

> **加一门语言，只允许改 `lang.rs` 一处；改到第二个文件，就说明抽象漏了。**

这个形式人工就能核对（加语言时数一下动了几个文件），也给出了明确的改进方向。
（数据化的完整方案要等 M2 之后——现在改，会和数据层抢时间。）

### 8.7 这一遍的方法论收获

**"集成"这个词掩盖了一件事：接进来的每个系统，都有一份它自己定的规矩。**
这一遍查出来的四个缺口（`.jdks`、pyenv、vswhere、`uv python dir`），
没有一个是"代码写错了"——全都是**我们对别人的生态了解得不够**。

所以这一条要写下来：**凡是要接一个新工具，先查它的官方文档"东西装在哪、怎么问"**，
不要凭 Windows 的常识去推。`C:\Program Files` 那套常识，在这四个例子里全是错的。

## P9 · 外部借鉴的吸收与裁剪（第九遍）

**这一遍只问**：每一条"抄来的"，**对不对路、代价是什么**。

### 9.1 抄对了的（逐条给证据）

| 抄自 | 落成什么 | 证据 |
|---|---|---|
| **IDEA** 的语法配色 | 6 类色值 × 两套主题 | `--sy-kw:#0033b3`（Light）/ `#cc7832`（Darcula）、`--sy-str:#067d17`/`#6a8759`、`--sy-com:#8c8c8c`/`#808080`……与 IDEA 默认一致，`[data-theme="dark"]` 另起一份 |
| **IDEA** 的信息组织 | 编辑器用画布（不是卡片）、依赖窗按 Maven 读法、问题栏在下方 | 结构与设计 §10.1/§10.2 对得上 |
| **MC 整合包**的按压反馈 | `:active{transform:scale(.99)}` / `.985` | 点下去有回弹，不靠音效也有"收到了"的手感 |
| **0 体积音效** | Web Audio 现算，不放音频文件 | `new AudioContext()`，且有开关（`SET.sound`）|
| **PCL2** 的窄导航条 | 图标 + 悬停提示，横向空间全留给内容 | `.side` / `--rail-w` |
| **Reese's Sodium Options** 的"只标改动项" | 设置页只在偏离默认时显示标记与还原 | 有测试：`设置：改动后出现标记与还原` |

### 9.2 抄歪了的（两条，都是实测出来的）

**A. "只动 `transform` 与 `opacity`"这条规矩写得太窄，等于逼着人天天违反它。**
实测：CSS 里有 30 多处 `background` / `color` / `border-color` / `box-shadow` 的过渡。
这些**只触发重绘、不触发 layout**，代价可以忽略；全删掉界面会变僵。
真正的禁忌是**会触发 layout 的属性**。规矩已改成按这条判（细节见设计 §10.4）。
顺手修掉两处真违反：

- `.progress .fill` 的 `transition: width` → 改 `transform: scaleX(var(--p))`。
  进度条每秒要更新好几次，动 width 就是反复触发布局。
- `.feed` 的 `transition: right` **保留**，但把理由写在代码里了：通知栏跟着侧栏开合做
  一次性位移，换成 transform 得反推侧栏宽度差，不划算。**例外的理由要写下来，否则它就成了橡皮筋。**

**B. 设置项是死的——动效档位从来没生效过。**
`applyLook()` 里设的是 `--dur` / `--dur-fast` / `--dur-slow`，
而 `style.css` 里 63 处用的是 `--t` / `--t-fast` / `--t-slow`。
**两批变量根本不是同一批**：切"快/标准/慢"什么都不变。
（"关"侥幸生效，因为它是靠 `[data-motion="off"]` 那条 `!important` 规则兜的。）

这类 bug 的坏处不在动画本身——**在于它让"设置"这件事变得不可信**，而这个工具的全部价值就是"说的和实际一致"。
→ 已修（JS 改设 `--t*`），并给 uitest 加了一条断言：切到快档后 `--t-fast` 必须真的变成 60ms。
**没有断言的设置项，等于没有设置项。**

### 9.3 该抄没抄的

**`prefers-reduced-motion`。** 工具自己有"关动效"，但从不读系统的同一个开关——
Windows 里那个开关是给前庭功能障碍（晕动症）的人用的，不是审美偏好。
→ 已补：系统设了"减少动效"时**首次运行**默认关；用户自己挑过档位之后不覆盖他的选择。

### 9.4 这一遍最重要的发现：P5 的信任机制，一行代码都没落地

查 `trial` 与 `trust`：

- `trust` **全仓库零命中**——`trust.json` 不存在，没有任何信任逻辑。
- `trial` 的默认值**还是 `true`**（`SET` 与 `SET_DEFAULTS` 两处）。
- `app.js` 里 `if (SET.trial) { await invoke('launch_project', …) }`——**直接执行，没有任何检查**。

也就是说：**P5 认定"最危险"的那件事，此刻仍然成立**——打开一个别人发来的项目（压缩包解开、
无任何历史记录），工具会自动跑它契约文件里写的启动命令。

P5 当时的记录是"**已写进设计 §1.3**"。而 P9 来查的是**代码里有没有**。

**而且设计本身还写错了一处**：信任记录原本规定存在**项目内** `.jingwei/trust.json`。
那等于"别人发来的压缩包只要自带一份 trust.json，就绕过了这道闸"——正好把要防的东西请了进来。
**安全机制存错地方比没有它更糟，因为它看起来是有的。**

→ 已修（三处）：

1. `trial` 默认 `false`；
2. 只有**手动在「运行」页跑过一次**才把这个项目记进信任（提示里**原样列出将执行的命令**）；
3. 信任记录改存**这台机器上**（localStorage 的 `jingwei.trust`，按项目路径），不跟项目走。

### 9.5 方法论收获（这条要写进迭代规矩）

**"写进设计"不等于"做到了"。**
P3 也犯过同一形态的错（lint 只写在一个 crate 里），P5 犯得更重（安全机制只写在文档里）。
两次都是**同一种失效：决定记在了文档上，而门禁上什么都没发生**。

所以加一条硬规矩（已写进 §13）：

> **每一条安全类与正确性类决定，必须同时留下一个"能失败的东西"**——
> 一条测试、一条 lint、或一条门禁脚本里的断言。
> 做不到，就说明这条决定**还没做**，只是被记下来了。

## P10 · 反脆弱与极端场景（第十遍）

**这一遍只问**：正常路径之外，它会**怎么坏**。

### 10.1 清单与实测

| 场景 | 现状 | 判定 |
|---|---|---|
| 断电 / 崩溃时写文件 | 原子写：先写 `.tmp` 再 `rename` | **成立**，而且那个 `rename` 就是 `MoveFileExW`（见 10.3） |
| 磁盘满 | P7 处理过：日志写不进 → stderr；变更基线 / 运行记录失败 → 新码 9002 / 9006 | 成立 |
| **文件被瞬时锁住**（杀毒、索引器、编辑器） | **没有任何重试** | **缺** |
| 超长路径（>260） | `should_skip` 拦下并给出原因；扫描里另外记「最长路径」 | 成立，**但闸门原来只装在外层** |
| 符号链接 / 联接点 | `file_type().is_dir()` 对链接返回 false → 不递归进去 | 成立（默认就是安全的） |
| 网络盘断线 | `should_skip` 会拦 | **同上：原来只装在外层** |
| 超大项目 | `MAX_DEPTH=4` + `FILE_BUDGET=6000`；超限置 `truncated` 并生成一条 finding | 成立（P3 抓的"截断不告知"已修） |
| 畸形输入 | 契约不是合法 JSON、认不出的编码，各有明确说法 | 成立 |
| **并发：两个窗口开同一项目** | **没有单实例保护**；`watch.json` 互相覆盖 → 变更基线错乱 → 会误报"变了" | **缺** |
| 递归爆栈 | 有深度上限 | 成立 |

### 10.2 补掉的一处：闸门只装在外层

`should_skip`（拦网络盘 / 链接 / 超长路径 / 越界）原来**只在"扫项目列表"那一步**
（`projects.rs`）被调用；进了项目内部，`project.rs` 的 `walk` 自己管自己，那道闸就不存在了。
而 junction 在 `node_modules` 里遍地都是，网络盘断线会让扫描直接挂住。

→ 已在 `walk` 里补上同一道检查。

### 10.3 一条"把语言已经保证的事又写了一遍"的规矩

设计 §11 的平台特例第 1 条写着："`std::fs::rename` 不是原子操作 →
一律走 `MoveFileExW(..., MOVEFILE_REPLACE_EXISTING)`"。

查官方文档（`doc.rust-lang.org/std/fs/fn.rename.html`）原文：

> This function currently corresponds to the `rename` function on Unix,
> and **`MoveFileExW` with a fallback to `SetFileInformationByHandle` on Windows**.

**标准库已经就是那个调用**，还多了一条 fallback（Win10 1607+ 且文件系统支持时，
行为与 Unix 一致，也就是真正的原子替换）。原来的写法会让人以为要自己写一遍 FFI——
**定规矩之前先查清"语言是不是已经做了"**，否则这条规矩本身就是个坑。

### 10.4 剩下的两条（带触发条件，不无条件挂着）

1. **写前重试**。触发条件：有真实用户报"保存失败 / 落盘失败"。
   到那时才拿得到真实的重试次数分布，现在拍一个数只是猜。
2. **单实例保护**。触发条件：有人同时开两个窗口。
   形式也定了：`.jingwei/lock` + 启动时检测，**只提示不强制**——
   强制退出会让"我想开两个窗口看不同项目"变得难受，那不是我们该管的。

### 10.5 这一遍的方法论收获

**极端场景的价值不在于"都处理掉"，而在于知道"坏了会是什么样"。**

这一遍查出来的是两类：一类是**看起来像问题、其实语言已经解决**（rename）；
另一类是**闸门装在了一层、另一层裸奔**（`should_skip`）。
后者是这个项目最容易犯的错：**同一个判断在多条路径上各写一遍，改的时候只改了一处**。
它和 §3.2「判断只有一份」是同一个病，只是换了个地方发作。

→ 已加进设计 §3.2 的说明：**同一道检查，要么只写一次，要么在每条路径上都验一遍。**

# 第二轮 · 从"决策书"到"施工图"

第一轮十遍问的是：**已经做的，对不对。**
第二轮问的是：**拿着它，能不能开工。**

这两件事不一样。第一轮把设计里**错的和虚的**挑出来了；第二轮要补的是**空的和粗的**——
错的东西会让人返工，**空的东西会让人卡在原地**，而卡住的地方连报错都没有。

## Q1 · 可开工性诊断

### 1.1 什么算"能开工"（判据）

一条设计要算施工图，得让人**不需要再做决定**就能写代码。四条判据：

1. **没有"待定"**——二选一的地方都定死了
2. **DDL 可执行**——能直接粘进 SQLite 跑
3. **接口有签名**——函数、类型、错误，到符号级
4. **有施工顺序**——先写哪个文件、每步怎么验

### 1.2 逐条核对（现状）

| 判据 | 现状 | 证据 |
|---|---|---|
| 没有待定 | **破** | 《数据层设计》§13 标题就是「**待定**：Rust 侧的 SQLite 绑定」 |
| DDL 可执行 | **破** | 两份设计文档里 `CREATE TABLE` **零命中**。唯一的 DDL 在 `tools/db_probe.py`，而且是压测用的**简化版**（没有 `CHECK`、没有三张支持表、没有 FTS5 触发器）|
| 接口有签名 | **破** | 两份文档里 `fn … -> …` **零命中**；`pub fn` / `struct` 只出现在散文里 |
| 施工顺序 | **部分** | §14 有里程碑与 DoD，但没有"先写哪个文件"的粒度 |
| 模块分层 | **破** | 设计写依赖方向 `cli / src-tauri → adapters → engine → model`，而 **`adapters` 这个 crate 根本不存在**；engine 内部 **32 个模块**没有任何层次说明 |
| 外壳契约 | **破** | `src-tauri` 已经有 **38 个 Tauri 命令**，但设计里没有这份清单——前端能调什么、返回什么，只写在代码里 |

结论：**六条判据里四条是破的**。这就是"跑不起来一个完整项目"和"能开工"之间的距离。

**把"我以为它在那儿"当成了"它在那儿"**。

## Q3 · 物理模型落地（DDL 从文档搬进文件）

### 3.1 新增 `tools/schema.sql`：唯一真源

DDL 不再贴在文档里，理由只有一条：**贴着的 SQL 没法被执行，也没法被校验**。
搬进文件之后：

```

   --- tools/db_probe.py   读它建库压测（数字因此可复跑）
   --- crates/engine       将来 include_str! 同一份做建库与迁移
   --- 《数据层设计》§3      引用它，只解释"为什么"，不贴副本
```

内容按《数据层设计》§3–§10 收全：7 条 PRAGMA、`meta`、`nodes`、`edges`、
三张支持表（`files` / `index_runs` / `query_cache`）、3 条索引、FTS5 外部内容表 + 三触发器、
`live_edges` 视图、版本戳。`kind` 与 `source` 的取值用 `CHECK` 写死——
**写错一个立刻失败，而不是留下一条"幽灵关系"**。

### 3.2 实测：十项全过

```
1 建库 OK                     2 版本 1
3 FTS 命中 [('main.rs',)]     4 CHECK 拦住非法 kind
5 CHECK 拦住非法关系           6 edges 2 条 / live_edges 1 条（失效边被过滤）

```

### 3.3 把探针接到同一份 DDL——于是它立刻抓到了两个错

`db_probe.py` 里原来内嵌着一份 DDL，而且**已经和 schema.sql 对不上**：
少了三张支持表、触发器名也不一样。改成读文件之后，两件事马上暴露：

1. **CHECK 拒绝执行**：探针往 `line` 里塞了 `i % 400`，正好会落到 **0**，
   而 `CHECK (line IS NULL OR line > 0)` 不允许。
   ——这就是这条约束存在的意义：**脏数据在写入的那一刻就被拦住，而不是等它进库之后**
   再让某个人对着"第 0 行"发懵。已改成 `(i % 400) + 1`。
2. **旧索引名**：体积分解那段还在 `DROP INDEX idx_edges_dst`，而索引已经改名成
   `idx_edges_dst_kind`。改动漏在了脚本里——**同一事实两处副本的又一次现形**。

### 3.4 数字复跑（证明探针与 DDL 真的合上了）

```
规模 10,000 文件 / 20 符号 / 4 边  →  410,000 行，21.15s，主库 79.7 MB
点查 by id 0.01ms · 列某文件符号 0.04ms（走 idx_nodes_file_kind）
1 跳正向 0.00ms · 1 跳反向 0.00ms（走 idx_edges_dst_kind）
3 跳 0.02ms · FTS 0.02ms
体积拆解：全部 74.6 / 去 FTS 65.2 / 再去索引 51.2 / 只剩 nodes 34.4
不变量：integrity_check ok · foreign_key_check 0 · FTS 行数差 0
```

**两条规矩因此变得可执行**：
§12.3 门禁之外，数据层多了一条 —— **改表结构 → 改 `schema.sql` → 跑探针**，三步固定。

## Q4 · 领域层接口（`model` 侧）

### 4.1 `model` 已经提供了什么

这一层是最完整的（15 条测试，无 IO、无依赖），把它当成施工参照物：

| 类型 | 管什么 | 关键方法 |
|---|---|---|
| `NodeKind`（13）/ `EdgeKind`（15） | 世界上有什么、怎么连 | `as_str()`、`ALL`、`EdgeKind::allows(src,dst)`（**构造期**拒绝非法组合） |
| `Source`（5） | 这条事实哪来的 | `as_str()`、`is_authoritative()` |
| `Confidence`（3 档） | 有多确定 | `value()` / `from_value()` |
| `Verdict<T>`（三态） | 是 / 不是 / **查不了** | `is_yes()` / `is_missing()` / `ok()` |
| `Node` / `Edge` | 图谱的两种元素 | `new()`（强制带来源）· `Edge::from_row()` · `is_live()` |
| `Conclusion` + `Level` + `SuppressReason` | 给用户看的那一条 | **字段私有**，只能过 `new()`（内含 `error_checked` 三道闸）|
| `node_id()` / `normalize_path()` | 稳定标识 | 分隔符与大小写规范化 |

### 4.2 两处"描述了一个不存在的机制"

**A. `model` 的测试注释写着**："DDL 的 CHECK 子句由 `ALL` 生成"。
——**那个机制不存在**，DDL 是手写在 `schema.sql` 里的。
注释描述不存在的机制比没有注释更糟：读的人会以为"改 `ALL` 就够了"。已改写。

**B. `Source` 没有 `ALL`**（`NodeKind` / `EdgeKind` 都有）。
结果是"有哪几个来源合法"这件事**只有手写副本**——CHECK 里写一套、`as_str` 里写一套。
已补上 `Source::ALL`。

### 4.3 最重要的发现：**engine 根本没有依赖 model**

设计 §3.1 写着依赖方向 `cli / src-tauri → adapters → engine → model`。
而 `crates/engine/Cargo.toml` 里**没有 model 这条边**——我要写 store 时才撞上这堵墙。

也就是说：**`model` 是个孤岛**——15 条测试全过，零个消费者，存在于仓库里但不在链路上。

> **依赖方向写在文档里不算数，得让 `Cargo.toml` 说话。**

已接上。这条同时也是"图谱内核还没开工"最直接的证据：**领域模型做完了，但没有任何人用它。**

### 4.4 新增 `crates/engine/src/store.rs`：把 DDL 与领域模型焊在一起

```
pub const SCHEMA_SQL: &str = include_str!("../../../tools/schema.sql");  // 编译期嵌入
pub const SCHEMA_VERSION: i64 = 1;
```

**为什么要把 DDL 嵌进二进制**：嵌进去之后，"设计"与"实际建的表"不可能再分家——
改错一边，测试立刻红；而不是等到某台机器上第一次写库才炸。

四条测试，全部守"两个副本不许漂"：

| 测试 | 守什么 |
|---|---|
| `ddl_kind_lists_match_the_domain_enums` | DDL 里两处 `kind` 的取值 == `NodeKind::ALL` / `EdgeKind::ALL`（**含顺序**）|
| `ddl_source_lists_match_the_source_enum` | `source` 的取值 == `Source::ALL` |
| `ddl_version_stamp_matches_the_constant` | DDL 末尾写进 `meta` 的版本号 == `SCHEMA_VERSION` |
| `ddl_executes_and_live_edges_filters_expired` | DDL 真能建库；失效边被 `live_edges` 挡掉；非法 `kind` 写不进去 |

### 4.5 这四条测试，**第一次跑就抓到了东西**

```
edges.kind 的 CHECK 与 EdgeKind::ALL 不一致
  left:  [depends_on, calls, references, defines, contains, …]   ← 我手写 DDL 时的顺序
  right: [contains, defines, implements, calls, references, …]    ← EdgeKind::ALL 的顺序
```

**内容一样、顺序不同**——这就是"两个副本"漂移最典型的形态：**肉眼看不出来**。
（`CHECK` 里的顺序其实不影响约束行为，所以它永远也不会以 bug 的形式暴露。）

已以 `ALL` 为准统一，并把顺序的语义写进 DDL 的注释：
**先结构类（包含/定义/实现）→ 再引用类（调用/引用/依赖）→ 最后记录类（诊断/因果/时间）**。

## Q5 · 数据层接口（读写真的跑起来了）

### 5.1 API 定案

`crates/engine/src/store.rs`：

| 方法 | 干什么 | 为什么是这个名字 |
|---|---|---|
| `Store::open(path)` | 打开（必要时新建）。**建库与迁移是同一段 SQL**——DDL 里全是 `IF NOT EXISTS`，所以不存在"第一次要跑另一个脚本" | |
| `Store::open_readonly(path)` | 只读连接 | 查询用这条、写用 `open`：**索引在写的时候，界面查询不被长事务卡住** |
| `schema_version()` | 读版本戳 | 迁移脚本靠它决定跑哪几步 |
| `upsert(&[Node], &[Edge]) -> WriteReport` | 一个事务里写一批 | 返回的是**数字**（写了多少 / 失效多少），不是"操作成功"——数字要能报到界面上 |
| `expire_edge(src,dst,kind,at) -> bool` | 失效一条边 | 返回"真的改了没有"，让调用方能区分"失效成功"和"本来就没了" |
| `neighbors(id, kind, Dir) -> Vec<String>` | 1 跳邻居 | `Dir::Out` / `Dir::In`（反查同样常用：谁引用了这个符号） |
| `counts() -> (i64,i64)` | 节点数 / **有效**边数 | 界面上"索引了多少东西" |
| `node(id) -> Option<Node>` | 读一个节点 | 读路径**不做校验**：历史数据要能原样读回来 |

### 5.2 四条设计规矩，落成了代码

1. **全在一个事务里**——半批写进去比全没写更糟（图谱会自相矛盾）。
2. **UPSERT，且 `created_at` 不覆盖**。这条值得单说：`updated_at` 每次刷新，
   但 `created_at` 是"第一次看到这个东西的时间"——**每轮重扫都刷它，等于把历史擦掉**。
   有测试守着（`upsert_is_idempotent_and_keeps_created_at`）。
3. **失效只标记不删；重新发现会复活**（`ON CONFLICT … SET expires_at=NULL`）。
   只失效不复活的话，"我改回去它就好了"这种事永远不会被反映出来。
4. **查询只走 `live_edges` 视图**——失效边在语法上就查不到，
   不需要每个调用点记得写 `WHERE expires_at IS NULL`。

### 5.3 新冒出来的两个缺口

1. **`Node` 没有 `checksum` 字段**，而 DDL 里有 `checksum TEXT`。
   设计里"`checksum` 语义未定义"这条待办，现在有了更具体的形状：**连字段都没进领域模型**。
2. **DDL 的 `edges.source` 允许 NULL，而 Rust 的 `Edge.source` 是必填**——
   DDL 松于 Rust。这是**有意的**（历史数据要能读回来），但之前没写下来。已在读路径注明。


原因有两层：**杀毒软件（卡巴斯基）拦编译产物**，以及**我自己把 `cargo test` 和
`cargo clippy` 并行发了**——clippy 正在写那个测试 exe，test 要执行它，Windows 直接拒绝。

**结论：门禁必须串行跑。**（CI 里已经是串行 step；本地手跑时别并行。）

## Q6 · 引擎分层与数据流

### 6.1 实测：32 个模块、75 条依赖边、**3 对真循环**

把 `crate::xxx` 的引用扫一遍，得到模块依赖图：

**被依赖最多（也就是最底层）**：

```
contract 23 · dlog 20 · lang 19 · facts 17 · probe 15 · project 12 · textfile 11 · mem 7
```

**双向依赖（真正的循环）——设计说"依赖方向单向"，实测有三对**：

| 循环 | 具体是什么 |
|---|---|
| `probe ↔ ccpp` | ccpp 用 probe 的 `run_cmd` / `which`；probe 用 ccpp 的 `probe_cc(root)` |
| `probe ↔ jvm` | 同上 |
| `project ↔ rules` | rules 用 project 的 `HYGIENE_IDS`（常量）；project 用 rules 的 `Finding` / `Severity`（类型）|

### 6.2 根因：**工具与类型，混在了编排文件里**

三对循环看着吓人，拆开看**每一处都只有一两个符号**：

- `probe.rs` 同时干两件事：提供 `which` / `run_cmd`（**纯工具**），
  和做语言探测编排（**业务**，那 3 行 `match lang` 才需要 ccpp/jvm）。
- `rules.rs` 同时干两件事：定义 `Finding` / `Severity`（**类型**），和写规则（**业务**）。

**拆法（三步，都不大，但必须在 store 接进来之前做）**：

1. `which` / `run_cmd` 从 `probe` 下沉到 `winutil`（它已经是底层，谁都能用）——
   拆完 `ccpp → probe` 与 `jvm → probe` 两条边直接消失。
2. `Finding` / `Severity` 从 `rules` 上移到 `model`——
   它们本来就是领域概念（"给用户看的那一条"），和 `Conclusion` 是邻居。
   拆完 `project → rules` 消失。
3. `HYGIENE_IDS` 留在 `rules`（它本来就是规则的清单，不是项目的属性）。

**为什么必须先拆**：`store` 要接在图谱与探测之间。图里有循环的时候，
它插在哪儿都说得通——**那就等于没有分层**。

### 6.3 分层建议（按实测入度 + 语义，不按文件夹顺序）

```
L0  纯工具（无业务概念）  winutil · dlog · textfile · parallel · scan · jobobj
L1  机器与系统           machine · mem · native
L2  探测（拿事实）        probe · jvm · ccpp · deps · editors · envsetup · profiles · lang
L3  项目理解（出结论）     project · projects · contract · rules · diag · fix
L4  图谱（存与查）        store            ← 这一层现在只有骨架
L5  项目状态（可回滚）     changes · snapshot · workcopy · runs · notes · scaffold
L6  编排（一条龙）        launch
```

规矩：**箭头只能从下层指向上层之外**，也就是 `L(n)` 可以引用 `L(n-1)` 及更低，
反向引用一律视为设计缺陷。上面三对循环拆完之后，这张图才是真的。

### 6.4 一次调用的完整数据流（`inspect`，前端最常走的那条）

```
前端 invoke('inspect', { root })
  -- src-tauri::inspect
       -- notes::migrate_legacy(root)      旧 jsonl 记录搬成笔记（不搬的话老项目显示"一篇都没有"——那是假象）
       -- snapshot::load_latest(root)      上一次的快照（用来做"变了什么"）
       -- probe::make_facts(root, None)    采事实（内含 lang 探测 → jvm / ccpp 探测）
       -- deps::rust_tree(root)            传递依赖树（只读一份 lock，很便宜）
       -- rules::run_all(&facts, prev)     出结论（三态 + 抑制 + 聚合都在这里）
     → 组装 JSON 回前端
```

**这条链上，`store` 现在缺席**——它应该插在 `probe::make_facts` 之后
（把事实写进图谱）与 `rules::run_all` 之前（结论也从图谱查一次做交叉核对）。
接法写在 Q10 的施工顺序里。

### 7.3 最要紧的问题：**错误契约不统一，12 个命令根本没有"查不了"的通道**

```
26 个命令： Result<Value, String>     ← 有错误通道，但错误被压成一个字符串
12 个命令： Value / Vec<Value> / Option<String> / Vec<App>   ← 没有错误通道
```

无错误通道的那 12 个里，有好几个**恰恰是最容易查不到的东西**：

`profiles_list` · `openers`（找编辑器）。

它们出错时只能返回空对象或空数组——于是前端看到的是 **"没有显卡"**，
而真相是 **"没查到显卡"**。**这正是这套系统从第一天就要消灭的那种错。**

### 7.4 定案：统一信封（把三态贯彻到前端）

所有命令的返回统一成：

```json
{ "state": "yes" | "no" | "unknown",
  "reason": "为什么是这个状态（unknown 必填）",
  "data": { … } }
```

与 `model::Verdict` 的三态**同构**。前端只按 `state` 分三支：

| state | 界面说什么 |
|---|---|
| `yes` | 用 `data` 正常显示 |
| `no` | 显示"没有"，并给出依据（哪几处都看过了）|
| `unknown` | 显示"**查不了** + `reason`"——**绝不显示成"没有"** |

**错误（`Err`）与 `unknown` 是两件事**，与 §11.1 那两条对齐：

| 情形 | 走哪条 | 前端表现 |
|---|---|---|
| 整件事没做成（目录不存在、权限不够） | `Err` | 红条 + 下一步（对应 P6 的失败出路表）|
| 做成了，但某项查不出来 | `unknown` | 灰条 +"为什么查不了" |

**这条定案是从 Q7 才开始有的**——之前"查不了 vs 没有"只活在 `model` 的三态里，
到了外壳这一层就被 `Value` 抹平了。**一条原则只守在后端，等于没守。**

## Q8 · 解析管线（tree-sitter 的真实约束）

M3 的全部前提都在这一遍。三个问题：**版本能不能配、符号抽不抽得出来、体积多少**。

### 8.1 版本矩阵（实测兼容）

| crate | 最新版 | 实测 |
|---|---|---|
| `tree-sitter` | 0.27.1 | |
| `tree-sitter-rust` | 0.24.2 | ✅ 与 core 0.27 配得上 |
| `tree-sitter-python` | 0.25.0 | ✅ 解析出根节点 `module` |
| `tree-sitter-java` | 0.23.5 | ✅ 根节点 `program` |
| `tree-sitter-cpp` | 0.23.4 | ✅ 根节点 `translation_unit` |
| `tree-sitter-javascript` | 0.25.0 | ✅ 根节点 `program` |

加载方式（0.25+ 的写法）：`tree_sitter_rust::LANGUAGE` 是常量，`&LANGUAGE.into()` 得到 `Language`。
**五个语法用同一个 `Parser` 轮流 `set_language` 没问题**——不需要每种语言一个解析器实例。

### 8.2 符号抽取：可行，API 就是那两个

```
root.child_by_field_name("name")      → 函数名
child.kind() == "function_item"       → 节点类型
node.utf8_text(src.as_bytes())        → 取原文
```

实测从一段 Rust 里抽出了 `["add", "broken"]`。

### 8.3 **错误门控不是理论，是必须做的**——这一遍实测的直接证据

故意在那段源码里放了一个写坏的函数：

```rust
fn broken( { }
```

结果：`has_error = true`，错误子树数 = **1**，
而抽取函数名时——**`broken` 照样被抽出来了**。

也就是说：**不检查错误，坏代码里的符号会照样进图谱**，
然后"这个函数在哪定义"会给出一个根本不存在的答案。
设计 §12.2 里那条"tree-sitter 遇 `ERROR` 子树 → 不建调用关系"
**必须落在代码里**，判据就是 `node.has_error()`（递归到子树）。

### 8.4 体积：实测（**引用数字第一次被验证**）

```
core + 1 个语法（rust）        1307.5 KB
core + 5 个语法（+py/java/cpp/js）  5873.5 KB
增量 4 个语法                  ≈ 4.5 MB   →  平均每个 ≈ 1.14 MB
```

设计里写的"10+ 语言静态链接会 +5–15MB"——**按实测比例，10 个语言 ≈ 11.4 MB，落在区间里**。
这条从"引用级"升成"实测级"。

**一个附带发现**：如果只是声明 grammar 常量而不真的调用 `set_language`，
链接器会把它们**整个裁掉**（第一次测出来增量是 0 KB）。
但代码里只要有一处 `match lang { Rust => …, Python => … }` 的全语言分发，
链接器就裁不掉了。所以**静态链接的成本最终还是要付**——
这条也反过来说明：动态加载 DLL 那条路的价值在于**不把体积压在安装包上**，
而不是"省内存"。

# 第三轮 · 设计可靠性通审（R1）

**范围**：《设计.md》26 个决策点 + 《数据层设计》23 节，逐节读，只问两件事——
**这条前提成立吗？有没有反例？**

**结论：整体可靠，9 处漏洞/错误，全部已整改。**

### R1.1 两处真漏洞（会造成实际后果）

**① `checksum` 的语义被混成了一个字段——抽样校验因此做不了。**

《数据层设计》§8 写的判据是"`files.content_sha` 与磁盘一致，**且该文件的节点数一致**"，
紧接着说"新增 `nodes.checksum` 就是为了比对'节点集合'"。

问题是：**`nodes.checksum` 是逐行的**，而"节点集合"是**文件级**的概念。
一行里存"整个集合的哈希"是说不通的——于是这条校验根本落不了地。

→ 已拆成两个东西，各归各位：

| 字段 | 层级 | 管什么 |
|---|---|---|
| `files.nodes_count`（**新增列**）| 文件级 | 这个文件解析出几个节点；`NULL` = 还没解析过（不是 0）|
| `nodes.checksum` | 行级 | 这个节点自身内容的指纹 |

DDL、`Node` 结构体、写入与读取、文档全部跟着改了。

**② 路径小写化的前提没写。**

`id = "<kind>:<规范化 key>"` 的规范化里有"小写"，理由是"Windows 大小写不敏感"。
但**没有任何地方写"本工具只支持 Windows"**。换到 Linux/macOS，`Foo.rs` 与 `foo.rs`
是两个不同的文件，小写化会让它们**撞成同一个 id**——而"同一个东西只有一个节点"
这条特性会把这件事变成**静默的数据丢失**（后者覆盖前者），不报错。

→ 已把前提写进 §2，并注明：要支持跨平台，这里必须先按平台决定是否小写。

### R1.2 五处"描述与事实不符"

| # | 写的是什么 | 事实 | 整改 |
|---|---|---|---|
| ③ | 设计 §7："复合索引 `(depends_on_id, kind)`" | **那个列不存在**（我们的边表是 `edges(src,dst,kind)`），是从别处的图数据库设计带过来的残留 | 改成实际的 `(dst, kind) WHERE expires_at IS NULL` |
| ④ | 设计 §6.1："+5–15MB **未实测**" | Q8 已经实测了：每语言 ≈1.14MB | 换成实测值 |
| ⑤ | 数据层 §11："与 §11 的结论一致" | 在 §11 里引 §11，**自引用** | 改成指向 §4 与 §7 |
| ⑥ | 数据层 §11："建库语句与本文 §3 一致" | §3 从 Q3 起就不放 SQL 了 | 改成"读的是 `tools/schema.sql`" |
| ⑦ | `Node` 结构体没有 `checksum` 字段 | DDL 里有 `checksum TEXT` | 已补上 |

### R1.3 两处实现缺口（已补 / 已定）

**⑧ 过期清理从来没实现，而且它的"例外"是个不报错的坑。**

§6 说"每次索引结束后删一次过期超过 30 天的边"，并规定 `noted_at` 与 `changed_at`
**永不清理**。但 `store` 里只有 `expire_edge`，没有清理；而且那条 `NOT IN` 例外
如果漏写，用户会**安静地丢掉笔记和提交记录**，等到某天想翻旧账才发现。

→ 已实现 `Store::purge_expired(older_than)` + 一条专门的测试
（`purge_never_touches_notes_or_commits`：三条边全过期，清理只允许删掉派生那条）。

**⑨ 迁移里最危险的一步没有可照做的写法。**

§9 只写了一句"改 CHECK 取值范围必须重建表：新建 → 迁数据 → 删旧 → 改名"。
照着这句话做不出来，而且里面藏着一个**不报错的坑**：`nodes` 一重建，
`nodes_fts` 的外部内容指向就断了（`content_rowid` 还指着老 rowid），
搜索会返回旧的、或者干脆搜不到——**但什么错都不报**。

→ 已补完整的 SQL 模式，并把"最后那句 `rebuild` 不是收尾动作、是必需的一步"写死在旁边。

### R1.4 顺带把保留策略的数字对齐了

原文的表格里写着"环境快照 保留最近 30 条"，而**代码里没有对应物**——
实际存在的是"文件快照 20 版（`snapshot.rs`）"和"运行记录 60 条（`runs.rs`）"。
已把真实数字与实现状态（✅/⬜）逐行标进表格，并说明：

> **没有归属的保留策略 = 没有策略。**
> `runs.jsonl` 不在 SQLite 里，所以它的保留策略谁都不管——这次把它登记进来就是为了这个。

### R1.5 横着看这 9 处

| 类型 | 处数 | 例子 |
|---|---|---|
| **描述与事实不符** | 5 | 列名不存在、数字对不上、状态过时、字段缺失 |
| **真漏洞** | 2 | `checksum` 混层；小写化的前提没写 |
| **实现缺口** | 2 | 清理没写；迁移模式没有可照做的写法 |

**五处"描述与事实不符"里没有一处是想错了**——全都是在**写完之后的某个时刻，事实变了而文档没跟上**
（Q3 改了 DDL、Q8 测了体积、§3 搬了家、Q5 发现字段缺失）。

两份文档加起来 1100 多行，靠人通读来核对是不现实的。
所以这一轮的收尾动作是：**能自动核对的，一律变成测试**——
DDL 与枚举一致、版本戳一致、清理的例外、`live_edges` 的过滤，现在都有测试守着。
剩下那些**没法自动核对的**（比如"这个列名到底存不存在"），
唯一的办法是**写的时候就从代码里抄，而不是从记忆里抄**。

### R4.1 一条龙认语言了

**背景**：六个阶段里前四个锁死在 Python 上，拿它去开一个 Vue 项目，
用户看到的第一句话是「没有可用的 Python，无法启动」。**答非所问比不回答更糟**——

**建成**：前四阶段按语言分家（`launch/python.rs` · `node.rs` · `java.rs`），
后两阶段（拉起进程、等待就绪）三种语言共用一处实现；用途从「一个布尔量」改成四种
（`Run` / `Task` / `Build` / `Install`）。

**实测**（真夹具，不是想出来的）：

| 场景 | 结果 |
|---|---|
| 没有契约的 Node 项目 `jingwei run` | 6 阶段全过，就绪 251ms，依据「端口 5173 已监听（输出里出现过 localhost:5173）」 |
| 同一项目 `jingwei test`（没有 test 脚本） | 「package.json 里没有 test 脚本：它有的是 dev / build」 |
| 同一项目 `jingwei env install` | 走 `npm install`，按退出码 0 判完成 |
| Spring Boot 的 pom + 自带 wrapper | 第 4 阶段：`…mvnw.cmd spring-boot:run`（凭据：pom 里有 spring-boot-maven-plugin） |

### R4.2 修掉的三处真误报 / 真缺口

1. **Node 依赖「未安装」误报**：原来只判 `node_modules/<名字>` 在不在。
   yarn PnP 项目**压根没有 `node_modules`**、monorepo 的依赖装在**仓库根**——
   这两种情况会把装好的依赖报成未安装。现在：PnP 返回「确认不了」（三态里的 unknown），
   `node_modules` 往上找，版本就地读 `node_modules/<名字>/package.json`。
2. **「补装依赖」会去跑测试**：`install` 原来被当成「跑个脚本」，Node 项目上会落到 test 脚本上。
   已按用途分开（见上）。
3. **图谱里「自己的漏接」伪装成「外部符号」**：`use` 没接上的引用被算进 `external`，
   而那个数字没法判断图是不是真的全。现在分成两类独立出口
   （`unmapped_imports` / `namespace_mismatch`）。建完立刻见效：自己索引自己时报出 6 处，
   全是真问题（`super::` 3 处、裸路径 1 处、crate 名路径 2 处）；补上相对路径解析之后
   **6 → 0**，连上 18 → 24。

### R4.3 又一处「决定写在文档上、门禁上什么都没发生」

《设计》§12.3 写着「这四条跑在 CI 上（`.github/workflows/gate.yml`）」，
而仓库里**根本没有 `.github`**——这是同一个病的第五次发作（P3 / P5 / P9 / P10 各一次）。

同一轮还带出两处**同形态**的东西：

1. **文档测试从来没有进过任何一道门禁**。`envelope.rs` 的模块文档里那段 JSON 示例
   被 rustdoc 当成 Rust 编译，doctest 一直是红的——而原来的门禁只跑 `--all-targets`，
   它不含 doctest。现在那段标成 ```text，文档测试进门禁（新增第四道）。
2. **一次提交是不完整的，而提交信息说它完整**：`git add crates/engine/src/launch`
   只加上了 `launch/` 目录，`launch.rs` 本体没进去——于是 `mod java;` 不在，
   `launch/java.rs` 根本没被编译，而信息里写着「实测 6 阶段全过」。
   这是**「看起来对、其实没生效」**那一类坏数据，比「错的」更难发现。
   规矩已补进《设计》§11.0.1：动 git 之前先看 `git status`；只 `git add` 目录时，
   记得同名的 `.rs` 文件不在里面。
