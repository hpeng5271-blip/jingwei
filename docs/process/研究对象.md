## 五、这轮实测撞出来的两个真结论

### 5.1 Node / Java：**判得出、画不出**——这是边界，不是 bug

`index` 目前只解析 `.rs` / `.py`。vite（940 个 .js、586 个 .ts、26 个 .vue）与
petclinic（50 个 .java）的结论是**诚实的三态**：

> `扫到 0 个文件——这个目录里没有我们能解析的源码（目前只支持 .rs / .py）`
> `它有：940 个 .js、586 个 .ts…` → **不是你没有源码，是我们还没支持这门语言。**

**能做的部分照做**：`guide` / `doctor` 仍然工作（读 `package.json` / `pom.xml`，
给出能不能跑、缺什么）。**所以要写清**：这两类项目我们**给结论、不给图谱**。

### 5.2 Python 的「还没连上」为什么这么多——**是口径，不是解析**（2026-10-18，结论已纠正）

**我一开始判错了**：看到 flask 里 102 处 `from .x import`、`config.py` 0 入 0 出，
就断定"相对导入没解析"。**用一个最小夹具验证之后，旧代码就能连上**：

```
pkg/core.py: from .util import helper / return helper()
pkg/util.py: def helper()
→ 图谱：core.py out=1 · util.py in=1   （旧代码、未改任何东西）
```

所以相对导入**是通的**。真正的原因是**口径**：
`graph roles` 只算 `calls`（跨文件**调用**），而 Python 里大量跨文件使用是
`import` + **属性访问 / 类实例化 / 常量引用**——它们不产生 `calls`，于是那些文件
看起来"没人用"。flask 的 18 个 isolated 里，`typing.py`（只有类型别名）、
`signals.py`（只有信号对象）、`views.py`（只有类定义）就是这种：**它们本来就没有跨文件调用**。

**这条纠正值得记**：我差一点为了一个不存在的 bug 去改解析器——
**先拿最小夹具验证"旧代码到底行不行"，再动手**（`框架.md` §9.2 量具先坏）。
**仍然成立的欠账**：Python 的"使用"（属性访问/实例化）没有进图谱，
所以角色对 Python 只是**线索**，不是结论。这条留在 `docs/reference/债表.md`。

## 六、大对象的一条硬事实：**大项目能把索引打挂**（2026-10-18，未修，已如实记账）

拿 `tauri`（真仓库，331 个 .rs、26 个 Cargo.toml）试索引，**第一次就失败**：

```
cd D:\research\jingwei-objects\tauri\crates\tauri-utils
jingwei index
→ 索引失败：写关系失败：<src> -calls-> <dst>（底层：FOREIGN KEY constraint failed）
```

**是什么**：一条 `calls` 边指向了一个**没被落库的符号**（两头在同一个文件里）。
FK 违约 → **整个项目索引失败**，用户什么都拿不到。

**我试过的两版（都撤回了，不留在代码里）**

| 尝试 | 做法 | 为什么撤回 |
|---|---|---|
| ① | 插边遇到 FK 违约就**跳过并计数** | **违背一条已声明的不变量**：`a_bad_row_rolls_back_the_whole_batch` 明确要求"坏边必须整批回滚"；而且两条写路径都得改，口径一散就是新的坑 |
| ② | 往错误信息里补底层原因 | 它本身是改进，但跟 ① 绑在一次提交里，单独立不住；分开做 |

**下一步（写清，不靠记性）**

**已经定位到了（2026-10-18 深夜，只读诊断 + 一个调试开关）**：

- 把那个文件单独拎出来就能复现（`%TEMP%\jw-tauri-min`：一个 Cargo.toml + `src/acl/schema.rs`）；
- 加一个临时开关把解析出的符号打出来：**22 个符号里没有 `gen_possible_permission_schemas`**；
- 它是 **`pub trait PermissionSchemaGenerator` 的默认方法**（`schema.rs:33` 的 trait 里，87 行的 `fn`）。
  同一个 trait 的名字本身进了符号表，**它的默认方法没有**。
- 而一条 `calls` 边却指向这个不存在的 id → 外键违约 → 整个项目索引失败。

**注意**：调试开关与"错误信息带 dst"那版都撤了（`git checkout`）——
后者虽然有用（正是它把 dst 与底层原因打出来的），但**撞上 `store.rs` 1000 行上限**，
为它拆文件不值得——先记着，等 0.5 一起做（那时顺手把错误句柄抽出去）。

1. **下一步的定位**（还没做）：那条边是谁产的——trait 默认方法没进符号表，
   `resolve` 却拿到了这个 id，说明符号表的来源不止"解析出的符号"。
   先查 `SymbolTable` 的构造（`by_name`/`by_path` 都从哪儿灌进去的）；
   查法：插边前把本次 `nodes` 的 id 集合打出来，看缺哪个、为什么缺
   （多行签名的 `fn`？宏里生成的 `impl`？被 `#[cfg]` 过滤？）；
2. **在产出点修**：解析/合并阶段就不产出指向未知节点的边（不是写入时兜底）；
3. **判据**：`tauri-utils` 索引成功，且 `a_bad_row_rolls_back_the_whole_batch` **仍然绿**。

**为什么先不修**：它触到"数据正确优先"那条线。改错了会让整张图谱**悄悄少边**——
那比"索引失败"更坏。**宁可留着失败，也不留一条我看不懂的规则。**

### ✅ 已修（2026-10-19，第 100 轮）

**根因**：`trait_item` 只收了 trait 自己的名字，**body 从来没走过** → trait 的默认方法缺席；
而一条 `calls` 边指向它 → 外键违约 → 整个项目索引失败。
顺带发现：trait 里**没有 body 的方法声明**在语法树里是 `function_signature_item`（不是 `function_item`），
所以那些也全都没有位置。

**修法**（`parse.rs`，两趟都补）：
1. 收符号那趟：`trait_item` 的 body 用 **trait 名当容器**递归（`Gen::describe`）；
2. 收调用那趟：同样按容器走，**不再 push scope**（两样都写会拼成 `Gen::Gen::describe`，测试当场抓到）；
3. `function_signature_item` 也算符号（trait 的方法声明）。

**证据**：

| 对象 | 修之前 | 修之后 |
|---|---|---|
| 单文件最小复现 | **索引失败**（FK） | ✓ 24 符号 / 4 调用 |
| `tauri/crates/tauri-utils` | **索引失败** | ✓ 27 文件 / 832 符号 / 133 调用（161ms） |
| **整个 `tauri`** | 从来没跑通过 | ✓ **329 文件 / 5,916 符号 / 849 调用 / 3.2 秒** |

**测试**：`trait_的默认方法也要算符号`（三件事：声明有位置、默认方法在、默认方法体里的调用源正确）。
**不变量没让路**：`a_bad_row_rolls_back_the_whole_batch` 仍然绿（347 条单测全过）。
