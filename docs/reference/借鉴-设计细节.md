## 1. salsa / rust-analyzer：用 revision 判断"能不能复用"，而不是重哈希

**问题**：二次启动/增量时，怎么不重算、不逐字节比对，就知道某文件的解析结果可复用。

**设计**

1. 每个输入是 tracked struct，字段一变全局 revision +1（单调整数，非哈希）；
2. 查询结果 memoize，并记下"这次读过的输入字段"（依赖集）；
3. 回答时只比依赖字段的 revision，没变→直接返回缓存，O(1) 不碰内容；
4. durability：几乎不变的输入（解析器版本/配置）标低变更频度，比较时跳过；
5. 变更只沿依赖图向下传播，无关文件完全不检查。

**我们的落法（可直接做）**

- `store::file_results` 现在只有 `result_sha`（内容哈希逐字节比）；
- 加一列 `file_rev INTEGER`（单调递增，每次写该文件 +1）+ 保留 `EXTRACTOR_VERSION`；
- 二次启动：先比 `(file_rev, extractor_version)`，不变就**跳过、不重哈希内容**；
- rev 变才重解析 + 重算 `result_sha`；哈希只作为"内容真变了"的第二道确认。

**出处**

- https://github.com/salsa-rs/salsa
- https://github.com/rust-lang/rust-analyzer/blob/master/docs/dev/architecture.md

## 2. tree-sitter：增量解析——只重解析改动的区间

**问题**：只改几行也整文件重解析，浪费；也让"内容变但结果没变"的早期截断失去粒度。

**设计**
1. `ts_parser_parse` 接受旧 `Tree` + 一个 `TSInputEdit`（`start_byte`/`old_end_byte`/`new_end_byte`），只重解析受影响区间；
2. 未变子树被复用（节点指针不变），改动祖先从下往上重建；
3. `ts_parser_set_included_ranges` 限定范围，只解析值得解析的 range；
4. 用 **byte 偏移**（不是行号/字符数）定位编辑，避开 CRLF/UTF-16 歧义；
5. 按"节点是否复用"决定重抽符号——复用子树直接沿用符号。

**我们的落法（有前提，别急着写）**
- 落点：`graph/parse.rs` 现在每文件从头 `parse`；改成保留上次 `Tree` + 内容快照，diff 出 `TSInputEdit` 喂回；
- **前提**：`Tree` 只能活在**长驻进程**里（CLI 跑完就退出，拿不到收益）；
- 所以先在 **GUI 的 watch/重索引路径**做，CLI 不动；没有基准证明收益前不合并。

**出处**：https://tree-sitter.github.io/tree-sitter/using-parsers（Incremental parsing / `TSInputEdit`）

## 3. LSP 的位置不是"列号"：byte offset 入库，UTF-16 只在边界换算

**问题**：重命名/跳转要指出"第几个字符"，但两个坐标系是错位的：
tree-sitter 给的是**字节偏移**，LSP `Position.character` 要的是 **UTF-16 code unit**。
混用最明显的症状：含中文/emoji 的行，光标与编辑位置整体偏移。

**设计**

1. tree-sitter 节点自带 `start_byte/end_byte` 与 `Point{row, column}`（column 按字节）；
2. LSP 的 `Position` 是 UTF-16 code unit、行列都 0 起——**直接混用必错**；
3. 库内只存一种真值：**byte offset + 行号**，列号不入库；
4. 同名定位：看目标 offset 落在哪个符号的 `[start_byte, end_byte)` 区间，**唯一命中**，不扫文本；
5. 出 LSP 时再换算：从行首 byte 数到目标 byte，按 UTF-16 数 code unit 得列。

**我们的落法**

- `parse.rs` / `parse_python.rs` 存 `start_byte/end_byte`（tree-sitter 免费给）；
- `edge_sites` 补一列 `byte`，rename 用它精确替换，替掉现在的“行内找名字”；
- `lsp/mod.rs` 加一层 `byte → UTF-16 column` 转换（只在这一层换算）。

**出处**

- LSP Position（UTF-16）：https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#position
- rust-analyzer 的 `line-index`：https://github.com/rust-lang/rust-analyzer/blob/master/crates/line-index/src/lib.rs

## 4. 冷启动"哪些目录不必再递归"：Everything 的 MFT/USN 与不提权的 RDCW

**问题**：整盘扫冷缓存 98.7s、热 5.6s。差别全在"要不要碰每个目录的元数据"。
能不能**不碰没变的目录**？——需要一份"变过什么"的事实，而这在 Windows 上不免费。

**设计**

1. Everything 的瞬时索引 = 读 NTFS 的 **MFT + USN Journal**；要开卷句柄 `\\.\C:`，
   `FSCTL_READ_USN_JOURNAL`——**需要管理员**，违反本项目的"绿色免安装、不提权"边界。
2. **不提权的裁剪**：`ReadDirectoryChangesW`，对根开 `FILE_LIST_DIRECTORY` +
   `FILE_FLAG_BACKUP_SEMANTICS`，`bWatchSubtree=TRUE`，拿变更事件（路径 + 动作 + 序号）。
3. 事件落**持久 journal**（`%LOCALAPPDATA%\jingwei\watch.jsonl`）；
   下次启动只重扫 journal 里出现的目录。
4. **坑**：NTFS 里改深层文件**不会**改祖先目录的 mtime——
   "目录 mtime 没变 = 子树没变"是**伪判据**（这条我们早就在代码注释里记过一次）。
5. 冷基线仍要 walk 一次；之后靠 journal 保温：成本从 98.7s 降到"只扫变更目录"。

**我们的落法（债表 0.27，未实现）**

- `scan.rs` 加持久 watch 后端：进程常驻时用 RDCW 收事件写 journal；
- `discover` 先读 journal：只扫变更目录；journal 不存在才整盘 walk；
- **三态口径**：RDCW 没在跑（进程未常驻）→ 明说"增量查不了"，退回全量，
  **不许把"没记录"说成"没变化"**。

**出处**

- ReadDirectoryChangesW：https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-readdirectorychangesw
- Everything 的索引（MFT/USN）：https://www.voidtools.com/support/everything/indexes/
- USN 变更日志：https://learn.microsoft.com/en-us/windows/win32/fileio/change-journals
