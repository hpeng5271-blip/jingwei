# SOP · 工作流程（给 Agent 用的）

> **这份是操作手册，不是介绍。** 主语是"我怎么想、我怎么动手"。
> 每一次开工前读一遍；写新东西之前问一遍。**它不是文档，是判据。**
>
> **它的来源有两处**：① 用户自己的思维方式（§一，他几天内靠这套方法把方向找对、
> 避免了我浪费掉的资源）；② 我踩过的坑（§二、§七的 S1–S14，每条都有实测证据）。
>
> 维护规矩：**这份超过 350 行就说明它在空谈。** 宁可短，不可虚。

## 〇、开工流程（按顺序，不许跳）

> **这一节是这份 SOP 的正文。** 下面各节是它的材料与理由。

### 第 0 步 · **先读那个"会说真话的最小文件"**

- **判据**：在动手查任何东西之前，先问一句
  **「哪一份文件/哪一条命令，最可能直接回答我这个疑问？」** 然后**只读那一个**。
- **为什么**：**这是我最大的一类空转。** 实测：我追了整整一轮
  （查 `graph_dump` → 查 `graph_db_path` → 查 `data_dir` → 挪库做干净实验 → 分步追踪文件消失），
  而答案在 `crates/engine/examples/export_graph.rs` **第 30 行**：
  它用临时库、跑完就删。**我一开始就没读那个最可能给出答案的 121 行文件。**
- **不适用**：疑问本身还没有明确的对象时（那时该做的是**先把疑问说清**，而不是读文件）。
- **自查**：动手前能不能一句话说出"我要读的是哪个文件、为什么是它"？
  说不出 → 我还在真空里试探。

### 第 1 步 · 一句话说清这轮交什么

- **判据**：先写一句"**这轮交什么**"，再动手。写不出 → 这轮不该开始。
- **为什么**：用户明确要求过（"每轮先用一句话说清「这轮交什么」，再动手"）。
  而我实测最容易犯的错就是**没有交付物就开始查**——查到哪里算哪里，最后什么都没交。

### 第 2 步 · 写任务卡（任务 / 验收 / 停止条件 / 不做什么）

- 四样缺一样就不算任务卡。**"不做什么"这一栏最容易省，也最容易省出事故**
  （我在呈现层改了很多轮，正是因为"不做什么"里没写"不许再动呈现层"）。

### 第 3 步 · 写假设（我预期看到什么）

- **判据**：动手前写一句"我预期看到什么"；验完对一下。
  **对不上就是我模型错了——那一秒是整轮里最值钱的产出**（见 §七 S5）。
- **不适用**：探索性的一次性查询（"这库里有什么"），那时没有假设可写。

### 第 4 步 · 只动一个方向，改完立刻量

- 一次只动一个方向（见 §七 S1）。**量出来的指标要能推翻方向**（S13）——
  如果指标"永远会通过"，那它是成绩单，不是判据。
- **不许给自己搭脚手架**：要验的是**产品行为**，不是我的脚本。
  能用一条命令验的，不写脚本；能看输出的，不解析文本。

### 第 5 步 · 收尾必须给三样

1. **门禁/测试的结尾**（不是"我跑过了"）
2. **改动范围**（`git diff --stat`）
3. **改之前它确实坏过的证据**

**缺任一项，就是没做。**

### 第 6 步 · 失败 2 次就停

同一件事失败 **2 次**就停下，如实报「未完成，卡在哪」。不"再试一次"。
**反复试探是最贵的浪费**（用户实测 + 我的账）。

### 全程 · 三件不许做的事

- **不许用建文档代替交付**（本文件就是我自己犯这毛病的证据）。
- **不许把指标当目标**（门禁全绿而界面是坏的——这是实测，不是比喻）。
- **不许在"元层面"过夜**：整理文档、加门禁、写账本，只在**它拦住了真交付**时才做。

## 三、开工前的四个问题（缺一个就别动手）

1. **终极形态**：这个东西最终该长成什么样？**这一步往那个方向走了吗？**
2. **该不该有**：它让哪一句话更**可信 / 更准时 / 更好懂**？答不上来 → 不做。
3. **学与发明**：这一处学的是**谁**、学它**哪一点**、它**哪里不够**、**我们自己的那一手是什么**？
4. **怎么算完**：验收标准（可判定）· 停止条件（几次失败就停）· **不做什么**。

## 四、动手时的规矩

- **重建优先于修补**：改一个地方超过 2 处、或要绕过既有结构 → 停下来，重建那一块。
- **失败 2 次就停**：不"再试一次"。如实报"未完成，卡在哪"。
- **最短验证路径**：要验的是**产品行为**，不是我的脚本。
  能用一条命令验的，不写脚本；能看输出的，不解析文本。
- **先修坏的**：用户看得见的坏东西，优先级高于任何新功能。
- **改动要小、要能回退**：一次只动一个方向，让"哪一步弄坏的"永远可定位。

## 五、关于 skill / 蒸馏（用户问的）

**结论：不建 skill 体系，先建"方法"。** 理由：

- skill 是**把已经稳定的流程固化**；而现在**流程本身还在错**（见 §二）。
  固化一个错的流程，只会让它错得更快、更一致。
- 真正该"蒸馏"的是**用户的思维**（§一），而它已经写成这份文件了——
  **它比任何 skill 都短、都硬**（因为是判据，不是步骤）。
- **什么时候才需要 skill**：当某件事我**第二次**做、而且第一次的判据已经被验证正确时。
  现在的候选只有两个（真窗口取证、门禁收口的读法），**还不够格**。

**这条决定本身就是一个例子**：用户在问"是不是该学网上的蒸馏、做 skill"，
而正确答案是"**现在不该**"——因为该学的不是"别人怎么做 skill"，
而是"**我们现在的瓶颈在哪**"。这正是他 §一 里"思想先推到终极"的用法。

> **2026-10-16 修正**：上面这条"不建 skill"**已经被用户推翻了一半**。
> 他说"先写着，慢慢完善"——也就是**边用边长**，而不是等它稳定。
> 而且他点明了 skill 该是什么形状：**"链式就是 skill"**——
> **复用的不是结论，是那条推理路径**。所以下面 §六 就是第一版 skill：
> **只写判据，不写步骤；每条都带"什么时候它不适用"。**

## 六、skill 第一版：三条判据 + 一条我自己的

> **格式要求（用户定的形状，2026-10-16 追加一条硬约束）**：
> **链式**——存判据与路径，**不存答案**。
> 每条必须有四项：**判据 / 为什么 / 什么时候不适用 / 实测证据**。
>
> **「什么时候不适用」是准入门槛，不是可选项。**
> 理由：用户说的是"**按需的、动态的**"——探针有量程。
> **一条没有适用域的判据就是会误报的判据**，而误报是这个项目最贵的错误
> （四条线里"无自查不报错""三态不压扁"都是为它立的）。
>
> **自查**：新加一条 skill 时，先用 grep 确认第四项真的写了——
> 「我记得写了」不算（这个项目为"我记得"付过太多次账）。

### 六.〇 · 两条评价 skill 本身的轴（**用户 2026-10-16 明确纠正过我的理解**）

> 用户原话："横向要宽可以提升**方法论高度和适用范围**"，
> "纵向收束（要精准正确可验证可重建等最起码的）"。

**这两条是正交的两个维度，不是一个东西的两头。** 我第一版理解成
"产品功能铺得宽"，被当场纠正——**那是把"方法的宽"读成了"产品的宽"。**

| | **横向：方法论的宽度** | **纵向：单次执行的收束** |
|---|---|---|
| 说的是 | **方法本身**——适用范围、跨域可用、高度 | **方法的每一次应用** |
| 判据 | 它**解决过几个不同场景**的问题？换个领域还成立吗？ | 结论**可验证**？过程**可重建**？ |
| 反例 | 只在"改这个文件"时管用的偏方 | "我觉得应该对" |
| 好例子 | 「先写假设再动手」能用在调试 / 设计 / 沟通 / 排查 | 这一次假设写清了、验了、对不上就**改模型** |

**为什么这条最要紧**：产品再宽，方法窄，就是**偏科**。
而用户一直在推我补的是**横向**——他把"伴侣出轨"的多角度分析
推到"信息该挂多视角标签"，把"经典物理可动可静"推到"判据按需动态"——
**那全是在把方法搬到新域**，而不是在加功能。

**自查**（每加一条 skill 都要过）：
- **横向**：这条判据换成另一个领域还成立吗？如果只在写 Rust 时管用，那它是**实现技巧**，
  不是 skill——该进代码注释，不该进这里。
- **纵向**：这条判据**怎么验**？验不了就不是判据（见下面 §七 S6–S11 的实测证据栏）。

### S1 · 重建优先于修补

- **判据**：改一个地方要动 **2 处以上**、或**要绕过既有结构** → 停下，重建那一块。
- **为什么**：修补要求先彻底理解旧结构（比重建还贵），而且每层补丁都要在下一层被绕过。
  用户实测："通过不断重建避免了很多资源浪费"。
- **不适用**：只动一处、且不绕过任何结构的小修（那种情况重建反而是浪费）。
- **我的实测证据**：门禁修 3 轮、图谱布局改 2 版——全是修补；正确答案都是重建。

### S2 · 反推出来的结论不许报"错误"

- **判据**：从**观察**反推出"是哪一个"的结论 → **最多警告级**，并标"未验证"。
  只有经过验证（或用户自己确认）才升到错误级。
- **为什么**：**从原理推向"所有可能"很容易（推演）；从观察反推"是哪一个"很难。**
  用户的原话是把推演做在**前置处理**上（闸门 + 缓冲），而不是拿观察去猜。
- **不适用**：纯逻辑必然（三态不许压扁那类）——那不是反推，是定义。
- **我的实测证据**：假 Error 全是反推（"依赖没装"、"这是 Python 项目"），而且都没验证。

### S3 · 判据要有适用域，出了域必须沉默

- **判据**：每条规则写明**适用的项目类型 / 语言 / 环境**；出了域**不做弱判断，直接沉默**。
- **为什么**：用户说的"按需、动态"——探针有量程，出了量程不该调参数硬用。
- **不适用**：跨语言的**形式**判据（例如"路径里的 `:` 要归一化"），那些与语言无关。
- **我的实测证据**：Python 规则跑进纯 Rust 项目 → 报假错。

### S4 · 可信度是用出来的，不是标出来的

- **判据**：来源权威**只是入场券**。要报错误级，还需要
  **"它在这个项目上被验证过、且没错过"** 的记录；没有记录 → 降级并标"未经验证"。
- **为什么**：用户说"可用的会随着使用增加可信度、完善程度"。
  来源权威 ≠ **在你这台机器、你这个项目上**成立。
- **不适用**：一次性事实（"这个文件存在吗"）——那种当场可验，不需要积累。
- **改动**：这一条**推翻**了 `设计哲学.md` §三.2 原来那张"静态分档"表，
  要改成"分档 + 验证记录"两栏。**这是一处待改的架构，记在账上。**

### S5（我自己的）· 先把假设写下来，再动手

- **判据**：动手前在回答里写一句"**我预期看到什么**"；验完对一下。
  **对不上，就是我模型错了——那一秒是整轮里最值钱的产出。**
- **为什么**：我最贵的浪费不是"想错"，是**推理出的结论没落到任何地方，于是又推一遍**
  （1642 次工具调用 / 73 次对话就是这么来的）。
- **不适用**：探索性的一次性查询（"这库里有什么"），那时没有假设可写。

### 关于"沉淀"（用户第三条，目前只是方向，还不能当判据）

用户说的：**混沌的就让它混沌；没有沉淀物，本身就是一种沉淀出的信息。**

**为什么现在还不能写成判据**：它与"一屏 1 结论 / 极致表达"直接冲突，
而冲突的解法我们还没想清（我提过"用拆分代替妥协"：该藏的折叠 + 混沌单列一层，但没验证）。
**先记着，不动手。** 这符合用户"慢慢完善"的意思。

## 七、skill 第二版：从实战里长出来的（2026-10-16 追加）

> **准入条件**（用户定的形状 + 我加的约束）：
> 一条能进来，必须**已经被一次真实失败验证过**——不是"我觉得对"。
> 每条仍然要有：**判据 / 为什么 / 什么时候不适用 / 实测证据**。

### S6 · 验证工具本身要先被验证：**第一条断言必须是"有数据"**

- **判据**：任何"拿真环境取证"的工具，**第一条断言查"我验的对象里有没有东西"**，
  而不是查"它的属性对不对"。
- **为什么**：我在**一个空图谱**上量出了"画布 96%×90%，✓ 修好了"——
  布局、着色、骨架**从来没被验过**。
  **验一个空容器然后说验过了，比不验更糟**：它会让人**停止怀疑**。
- **不适用**：验"空本身就是结论"的东西（例如"没有依赖"是正确结果时）——
  那时要显式写"我期望它是空的"。
- **实测证据**：整个"图谱布局"阶段的验证全是空跑；
  改成第一条断言查节点数之后，第一次跑就抓出真相。

### S7 · 判据必须确定：**"跑两次过一次"不是判据**

- **判据**：同一条命令连跑 3 次必须结果一致。出现间歇性，**先修取证工具，再谈产品**。
- **为什么**：我修了三轮门禁，而失败是**取证脚本的固定 1500ms 太短**——
  报告只写一次，那一刻没画完就**永久**留下"正在读取…"。
  **症状长得像产品坏了，于是查错了方向。**
- **不适用**：本身就在测随机/并发的判据——那种要写成"分布断言"（例如"至少 99% 通过"），
  并且**显式说明它是概率性的**。
- **实测证据**：修前 1/3 失败、修后 3/3 通过。

### S8 · 名字要有信息量：**用"最强的那一个"，不用"公共前缀"**

- **判据**：要给一组东西取名字时，取**它里面最有代表性的那一个**（出现最多 / 度数最高），
  不要取"所有成员的公共前缀"。
- **为什么**：公共前缀会被**最浅的那个成员压平**——一个团横跨 `src/` 时，
  `lib.rs` 把名字压成 `crates/engine/src`，于是**三个团同名**。
  而"读代码的人认的是文件，不是路径的公共前缀"。
- **不适用**：一组东西**天然同质**时（都在同一个目录），公共前缀就是那个目录，那时它是对的。
- **实测证据**：改前三个最大的团都叫 `crates/engine/src`；改后
  `crates/engine/src/lib.rs`(56) / `src-tauri/src/main.rs`(52) / `…/understand/project.rs`(45)，
  而且 **277 个家族 0 个算不出名字**。

### S9 · 每个通道只表达一件事

- **判据**：视觉/信息通道（颜色、形状、大小、位置）**一个通道一件语义**，
  不要把两件挤进一个通道。
- **为什么**：我把"类型（文件/符号/项目）"从颜色里挤掉、换成"社区"，
  于是用户看到"一堆有颜色的点"**分不出哪个是文件**。
  **合成通道是后退，不是进化。**
- **不适用**：通道不够用时（例如只有黑白打印）——那时要显式说明降级了什么。
- **实测证据**：用户一句话点出来（"不同形式的点做基础区分"），我才发现自己丢了这一层。

### S10 · 验证脚本崩了，等于没验

- **判据**：验证脚本**必须跑到底**；中途抛异常时，那一轮**结论作废**，不许"看了一半就报过"。
- **为什么**：我的团名验证脚本在第 66 行崩了（把对象当字符串用），
  而我看着前 8 行的输出就判断"算得对"——**实际上我看到的正是错的那部分**（三个团同名）。
- **不适用**：脚本设计成"提前退出即结论"时（例如第一条断言失败就该停）——
  那种要显式 return，而不是抛异常。
- **实测证据**：就是这一轮。

### S11 · 学外界要落到"它哪里不够"

- **判据**：学一样东西之后，必须写出一句「**它哪里不够 / 我们这里为什么不能照抄**」；
  写不出来说明还没学到能用。
- **为什么**：用户要求的"学与发明两条都要"。**只学 = 永远排后面。**
- **不适用**：纯粹的形式规范（例如文件命名约定）——那种照抄就是对的。
- **实测证据**：GraphRAG 那一条学到了两样能用的（层次社区、按度数排序），
  并找到了它缺的一样：**它没有"团与团之间怎么连"**——而代码图上那才是"改了影响谁"的答案。
  **这一条缺口直接变成了我们的下一手（团桥）。**

### S12 · 上游缺的东西，下游再努力也画不出来

- **判据**：一层做不好时，**先往上问一层**"它有没有我要的东西"，
  再决定是不是在这一层修。**换层比堆功夫便宜一个数量级。**
- **为什么**：我在 ④呈现层改了**很多轮**（画布尺寸、力导向、骨架、团名、团卡片、抽象层级），
  每轮都"通过验收"，而**用户一直说图没用**。最后拿真数据一量：
  **跨文件依赖在库里基本不存在**——呈现层画不出没有的东西。
  一条真数据（`calls` 边里跨文件只有 80 条）**当场终结了整条错误的努力方向**。
- **不适用**：确实确定问题在本层时（例如"这个函数算错了"）——
  那时往上问就是拖延。
- **实测证据**：修 `resolve` 一处（限定名没拆 `::`）→
  跨文件调用 **80 → 265**（3.3×）、有依赖的文件 **42 → 73**、
  枢纽从"文件+它的符号的假中心"变成 `mem.rs`(入21)/`probe.rs`/`dlog.rs`/`main.rs`/`launch.rs`
  ——**那才是"哪些块在互相用"**。
  **5 行改动 > 前面所有呈现层的功夫。**

### S13 · 量出来的指标要能推翻你的方向

- **判据**：每做一个方向，**先定一个能被量、且可能否证它的指标**。
  指标出来发现方向错了 → **立刻换方向，不要"再优化一下看看"**。
- **为什么**：我在呈现层"优化"了很多轮，因为**我用的指标是"这一层对不对"**
  （画布尺寸、节点数、布局收敛），它们**永远会通过**，永远推翻不了方向。
  而 `跨文件调用数` 这个指标**一次就把方向推翻了**。
- **不适用**：纯探索期（还不知道该量什么）——那时该做的是**先找到那个指标**，
  而不是先做功能。
- **实测证据**：见 S12。判据是"`main.rs` 这类入口的出入度必须显著高于其它，
  否则说明解析没通"——修前它 出5/入5（和其它文件没差别），修后 出6/入5 且
  枢纽换成了真正的核心模块。

### S14 · 动态/静态灵活切换（用户 2026-10-16 明确要求）

- **判据**：**先用"静态最小改动 + 既有规则兜底"验证方向**；
  方向被证实有用之后，再上"动态/精确"的重版本。**不要一上来就做重的那个。**
- **为什么**：用户原话"动态调整和静态适用的灵活切换"。
  重的版本（真路径解析）代价大，而且**它解决的问题可能只占剩余的一小部分**——
  在不知道收益的情况下先做重的，就是拿大钱赌小收益。
- **不适用**：**安全性由轻版本兜不住**时（例如轻版本会连出错边）——
  那时必须直接上重版本，因为错的边比没有边糟得多。
