# 道理不在代码里，在写代码的人的脑子里【让编程再次伟大#20】

<!-- 来源：https://www.bilibili.com/video/BV1GAyZYAEwA · 本地 whisper-small 转写 · 有错字，引用需回视频核对 -->

大家好,这是袁智能
自从我去年开始直播写代码
就有很多粉丝想让我把代码分享给他们
当然不是为了窃取什么商业机密
而是想要通过学习我的代码来提升自己的编程水平
也有一些粉丝想要我推荐一些好的开源软件
但也不是为了想要用这种软件
而是想要把代码下载下来
阅读学习
每次读我都会劝他们
说世界上有一万种学习方法
读代码是最没有价值的一种
但是简单的几句劝说
估计没有几个人听进去
所以本期视频我想深入探讨一下这个道理
首先我们要正确的认识到代码的价值
或者说代码在一个软件中的角色
有些粉丝都说过
想要做一个项目写一个软件
但找不到一个好的起步方式
所以就算是看这边的代码
照帽画虎
好歹也有一个出发点
这个想法的问题根源在于
软件的出发点从来都不是代码
任何一个软件项目都是从一个问题开始的
它可以是一个商业问题
一个科学问题
对人问题
甚至可以是虚空打靶的问题
为了应对这个问题
首先要形成一个解决方案
这个解决方案会包括很多的维度
比如某些特定的流程
某些内部制定的规则
某些角色能力的设计
某些任务的分配方式
最后为了实现这个解决方案
有些部分我们需要接触软件的能力
这里才会开始写代码
所以代码也是相当中后细的分支里的内容
如果你对一个软件项目一无所知
或者是大概了解了皮毛
那么直接打开人家的原代码
就像是空间道中间一个节点
想要通过阅读这里的内容来获得一个起步的方向
自然就是蛮人摸像的行为
另一个常见误区
是觉得名气大的项目管理肯定比较规范
所以代码质量肯定很高
看着他们来学怎么写代码指定没错
这个误区的核心在于代码质量的定义
我们常说的QC quality control
从本质上来说只是在表面上坚度了代码质量
从QC常见的五大范围就可以看得出来
reliable 可靠性
extendable 可拓展性
testable 可测试性
portable 可移植性
reuseable 可重用性
这些都是典型的非空冷静需求
用大白话来说
只要它能跑 改起来方便
写够了测试
可以被重复利用
那就是高质量的代码
这种质量标准不关心你这个代码是干嘛的
也不关心它是不是解决某个问题的最好做法
甚至不关心它是不是一个正确的做法
比如这些年最著名的安全漏洞事件
Java 的老4J
老4J 作为 Apache 项目
QC 管理自然也是到位的
老4J 漏洞的核心问题不是哪一段代码
而是直接用外部传入的文本来执行命令这个做法
就算代码总对这个外部文本进行了严格的检查过滤
把执行命令这种高权现行为暴露给不可控的外部环境
总任何一个角度来说都是一个非常糟糕的做法
那么基于这种错误的做法
写出来的符合QC 要求的代码
被你学过去了
也只会造成更多的老4J事件
那么如果我们想要从一个优秀的软件里学到一些东西
它只有价值的知识点在哪
不是怎么把它写出来
而是为什么这么写
著名程序而他们Energy说过
The secret of a good software is not kept inside is know how but know why
我以前在北京信任的时候
都会先问他们在业务方面的支持背景
比如当年我有一个项目是在视频网站上运行的基于AI的外语学习
虽然开发组人只要求编程技术和NLP相关的技术
但我还是会逐一确认大家有没有对在线视频行业
和在线教育行业的市场状况有所了解
如果他们没有相关的经验
我会建议他们不要急着开始看文档看架构
而是先补充业务知识
有些人就会疑惑我是个程序员
又不是做推广或者做销售了
为什么要关心市场背景呢
道理很简单
你就算现在一口气把所有文档都看完了
你也只会对我们这个系统有一个很模糊的认知
比如有一个小侧功能
你最多只能看懂了他用了某某技术
生成了某种规格的题目
然后以某种程式呈现给了用户
但你理解不了他为什么这么做
他为什么选择这种NLP技术而不是另外的那些技术
为什么他用这种形式来呈现这个题目
毕竟学外有100种方法
这些设计上的角色
从红光的技术路线到具体的每一个交互的画面和按钮
都是基于我们视频平台的现有业务
我们想要开拓的互动式学习
以及所有竞争对手的情况综合考虑所做出来的
有了业务知识的背景
你才能充分理解我们所积累下来的所有的技术角色
才能真的看懂我们的代码
这种从业务投资到技术的诺外知识
可以说是连接着业务需求和技术实现的桥梁
也是我认为的最有价值的知识
但也是最难传播的知识
一是需要投入的能力成本太大
二是这种内容的写作门槛有点高
因为只有决策者能够写下他们的思路
而且思路比结果难写太多了
所以你会发现很少有项目会留下解释诺外的知识
大多都是解释诺号的
某种程度上这也造成了业界的一个共识
重新写一个比在现有代码上做修改更容易
因为新的开发组接受一个项目是
只有诺号没有诺外
在思路上就很难和钱同步
也就很难维持项目的一致性
很多开发组最后都会选择绕开现在的部分
在旁边按照自己的思路写新的
然后逐步把它替换掉
久而久之那些原本的代码
就会变成无闻之小无闻大理的legacy code
值得欣慰的是逐渐有更多的项目
主意识到了把角色过程记录下来的重要性
不管是会议笔录
视频博客文章还是任何的其他形式
只要能够留下来一些能够让后人知其然
同时知其所一样的线索就是一个巨大的进步了
那些希望通过读代码提升自身素养的程序员
我觉得他们误解的编程是一门艺术这个口号
就像作家会看很多别人写的书
音乐家会听很多别人做的音乐
导演会看很多别人拍的电影
以此来拓掌自己的知识面
陶野心智提供灵感
是艺术创作的不可豁去的一环
我们程序员确实也有这样不可豁去的一环
只不过我们应该被熏掏的不是最终的代码
而是解释思路
所以大家以后看到别人的代码
记着给我问外
对方嫌你烦的话
你就说是原子人教你这么问的
有事找他
下期再见拜拜
