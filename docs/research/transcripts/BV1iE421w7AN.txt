# 最心疼前端程序员的架构【让编程再次伟大#13】

大家好,这次元子能上期视频我们讨论了一个应对后端复杂对的架构设计
本期我们把目光转移到前后端连接的部分,也就是API的架构设计
API架构会直接影响前端程序员和后端程序员的工作内容
比如说在什么情况下需要修改一个API
API的调用有没有限制谁定规则
返回的数据机构有没有标准谁定标准
诸如此类的工程问题重要程度都不亚于技术问题
今天我分享了这个API架构和目前主流的RESTAPI架构相比
试着从更红光的角度去解决技术问题的工程问题
我们可以把它称为统一接口架构
顾名思义就是把所有的接口统一起来
整一个系统的前后端只用一个API交流
在解释它的设计原理之前
我们要先回顾一下RESTAPI的一些缺陷
举个简单的例子
一个电商平台上面商品页会有很多信息
按照RESTAPI的设计理念
我们要给每一种信息配一个接口
不同接口之间有时候会有相互的依赖
比如说我们这里要先通过商品的API去获取
本商品所在店铺的ID
然后才能够通过热销API获得本店的热销商品
于是当这个页面的内容复杂度增加
这种依赖也会加深
除了在速度上会有显著的影响
更大的风险来自于故障处理
这里有点像上期提到的重步执行
容易造成连锁故障的情况
而且会更糟糕
因为前端一般都不会有自动回滚
或者重视的机制
而是会将错就错
除非你用户F5刷新
但是比起这个技术问题
它更重要的是有严重的工程影响
比如说热销商品的接口
原本只返回商品ID名字和缩列图
那么如果有一天你接到了产品经理的要求
要在上面给热销商品显示价格
那你只能够向后端提交声
请求他们修改接口返回价格
有时候后端因为任务繁忙
让你等一等
结果三年之后又三年
这些小改动还是没法上线
你在产品经理的催促之下
只能够自己动手解决问题
I个调用商品API
把热销商品的所有信息都拉下来
只是为了获得它所在的那个价格
这种丑陋的打补定的方式
在软件项目里面其实很常见
因为前端的变动往往是频繁的锁碎的
而由此会波及到后端的部分
就很容易形成任务进度上的瓶颈
我们的统一接口架构
就一次性解决了这些问题
首先在这个架构设计里面
每一个页面需要的信息
都可以在一个HTB请求里面传达清楚
这里使用了Post请求的消息主体作为一个容器
比如说我需要商品的信息
我就可以在主体里面列出来
具体需要什么就列什么
比如说图片名字价格介绍
我需要这个商品的评价
但是我只要分数和留言
我不需要这个评论者的名字头像之类的
那接下来我要这个商品
所在店铺的logo和名字
最后是这个店铺的热销商品
以及每个商品的缩略图名字和价格
这样子通过一个HTB请求
就把所有的需求都交代清楚
可以说是在时间上和空间上
都做到了最优化的状态
那么当前端需要调整获取的信息
那只需要调整这个请求的主体内容
对于后段来说
他们的唯一任务就是看懂这个主体
然后返回相对应的数据
那么要看懂这个主体
自然就要先在代码层面上给它进行定义
这里的做法就有点像OP
我们首先确定的是
从整一个系统的层面来说
有什么数据是存在的
是可以被读取被修改的
然后这些数据之间有什么关系
它有什么参数
什么类型之类的一些信息
这里整体就构成了
我们统一接口架构的数据结构模型
一些结构的定义
就是统一前后端交流的语言
这样不管前端发送什么样的请求
后端都可以实时解读请求的主体
然后找到对应的数据
比如说前端需要上评信息
然后恰好相比信息都在主数据库
那后端就可以把这个请求翻译成为SQL语言
发送到主数据库
如果评论的信息在另一个数据库
那后端就可以把这部分的请求
转发到另一个数据库的地址
有时候有一些数据是来自于其他部门的Res API
比如说这个热销API
可能它只返回商品ID和排名
那么我们就要根据这些ID
再走一遍主数据库去把对应的商品数据拉回来
你会发现这里后端系统就是一个翻译器
不管数据语言在哪里用什么接口
有什么数据
经过翻译器的转换之后
它都会统一变成我们的结构模型
它有点类似于编程语言里面的编译器
它能够让使用者不需要关心底层的
基统差异或者是硬件的区别
只需要注重自己的业务逻辑的表达
自从2012年Veron发布了TypeScript
它迅速的成为前端开发的主流语言
因为它弥补了前端开发最大的缺陷之一
信息类型的缺失
从而导致代码间的沟通无法保证质量
尤其是JarScript这个语言天生的容错能力太强了
就算你写错了
它也能装作没发现
然后在关键时刻再给你统一刀子
但TypeScript不是完美的
因为它只能管得了前端本身的东西
从后端返回的东西
它没法保证它的类型的格式
理论上来说你是可以在前端写个类型
然后把它套在某一个Res API的返回数据上
但是它返回的是不是就是这个类型
你没法保证
传统的Res API就是一个黑盒子
没打开之前你都不知道里面是什么
有一些靠谱的后端程序员会手写文档
聪明一些的会用Swagger之类的工具自动生成文档
但文档终究是文字
它不保证
也没有办法结合到代码里面
在编译或者是测试的时候进行检验
我们的统一接口架构就把最后的这个漏洞给补上了
因为前端后端都用了是统一套的数据结构模型
前端在调用API的时候
对于它请求主体里面列出来的东西
每一个都有准确的类型信息
这些类型信息是光通整个系统的
一些比较规范的数据员
比如说数据库
它本身就有精确的数据结构和类型信息
后端在定义接口的时候
就可以直接继承它们
而对于那些没有类型信息的数据员
比如说前面例子里面的那个热销Res API
我们也能根据对方的文档这些资料
在接口层面自定义
我们想要的数据结构和类型
总而在前端后端都完全统一代码和数据的类型信息
大大的提升代码质量
看到这里有些后端程序员
可能会对这个架构皱眉头
因为数据结构的定义和翻译器的编写
这些工作听起来就比单独的写一个具体的 API 要复杂很多
感觉有点像是在给后端增加100倍的工作量
只是为了讨好钱
都让它们的工作轻松一点点
首先这个问题其实不必要担忧
因为通常来说
一个软件系统可以提供的数据
大部分都是直接从数据库来的
这也是为什么后端程序员喜欢称自己为西亚U立工程师
也正因为如此
现在市面上有很多成熟的自动化宽价
能够让你直接从数据库的 schema
生成接口的所有的数据结构和翻译器
一行代码都不用写
那你实际上只需要把精力放在那个帐笔很小的自定义接口上
这样看来是不是工作任务就轻松了很多
我们这个架构设计它不仅仅解决了工作量的问题
更重要的是把前端和后端程序员的工作任务进行的解偶
因为传统的LS API架构
实际上就是把前端的一部分任务分配给了后端
画面上需要呈现什么数据
本来是前端的工作
但因为能获取什么数据这件事情的权限是在后端的手上
所以不管界面上做什么调整
前端都需要后端的帮忙
后端也一直需要待机
这种依赖不仅影响工作效率
而且很容易影响情绪
因为前端的本质工作是界面
然后会被后端所约束自己的进度自己无法做主
而后端的本质工作是系统
然后会被前端打断
经常要当当工具员的角色
大家都不高兴
最后一起骂产品经理
所以我们常说优秀的软件设计需要解偶
同样的在软件项目里面程序员之间也需要解偶
我们的架构设计就是通过
把后端程序员排除在前端的工作范围内
让前端可以自主的去处理前端的设计和开发
解偶本身不代表这两边就没有瓜葛了
而是让他们的交流更清晰
更客观
减少主观因素对于项目的影响
有些人会说这种截然不同的做法就是在舔坑的同时挖新的坑
比如说抛弃RESAPI就是抛弃了几十年
互联网基础设施所提供的强大的缓存能力
又比如说合并所有的接口
会让全线管理和限速限量等功能的开发难度都大大提升
先不说这些技术问题其实都有解决方案
我觉得更重要的问题是
我们在探索新的设计新的架构的时候
我们追求的是什么

才是有影响力的优化这个概念

能比代码层面在技术细节上带来更强的提升能力
本期的统一接口架构带来的提升
则是突破了技术层面
上升到了团队合作和项目管理的层面
这些工程问题往往会随着时间的增加投入人力的增加
软件复杂度的增加会变得越来越让人头疼
再多的规章制度和流程规范也没法消除它
所以我们能够用一个架构设计
把无解的工程问题转化为有解的技术问题
在我看来就是一个大跨步的提升
这也是探索新做法的最大意义
