# 我为什么把业务逻辑都写进数据库【让编程再次伟大#14】

<!-- 来源：https://www.bilibili.com/video/BV1si421a7aE · 本地 whisper-small 转写 · 有错字，引用需回视频核对 -->

大家好,这是袁智能
今天我们换个方向来讨论一个超级无敌简单的设计思路
前面两期视频我们都在聊很复杂的架构设计
长这评论区有不少人在抱怨
有的时候我是没有困难也要制造困难
有的时候我的设计理念不切实际忽略了很多情况
我觉得他们的理解误区在于总是想着有一个万能的解决方案
就是英语里面说的One Size Fix All Solution
但现实不是这样运作的
复杂的问题就是要用复杂的设计
而且不同的复杂问题还是要用不同的复杂设计
比如你的业务逻辑分之多
那么它最大的风险就在于会出错
所以要选择优化流程管理的设计
如果你的前端变化很多
那么最受影响的就是你的开发周期的管理
所以要考虑是在架构上结偶前后端的程序员
但是如果你的软件就那么几个简单明了的功能
99%是CRUD
几个人就能够开发完成
最后用户也只不过几百人的话
那你就用不上也没必要用任何复杂的架构
这种情况下我给你一个推荐
就是直接把业务逻辑写进数据库里面就得了
把业务逻辑写进数据库并不是什么新鲜主义
甚至可以说这才是最早的软件的写法
在1966年IBM发布了Information Management System
它可以说是现代数据库的B组
其中最核心的发明
就是让用户可以直接在数据库里面存储和执行业务层面的应用逻辑
这个做法的一大优点就是快
因为数据和应用逻辑在同一个地方
就可以进行本地图取本地运算本地返回
减少了传输的成本
毕竟在没有关切没有高速网络的当年
数据传输是一个很大的瓶颈
而除了快之外
这种做法更重要的价值在于
保证了数据的完整性和一致性
IMF系统发明了Trigger和Transaction等一系列现代数据库的默认机制
被后人总结为ACID特性
直到今天
它也还是最值得信赖的数据保障机构
而再厉害的程序员也不敢说自己在应用程
走写的代码逻辑能够保证有ACID
它的另一个核心价值则是数据的安全性
数据库作为数据的源头
把业务逻辑放进去
我们就能够在源头控制数据的读写权限
让外界可以接触到的数据保持在最低程度
这是理论上能够达到了最高级别的安全性
原本这个IMS系统只是印NASA的要求
为了给阿波罗计划管理材料库存和开发的
但它实在是太优秀了
它的速度、稳定性和安全性
在银行业里就是旧事主义版的存在
所以在70年代开始
IMS在金融行业被迅速接纳广泛应用
即使到今天它也还是最主流的交易系统之一
随后电信行业、制造业、零售行业也纷纷入场
使用IMS进行产业升级
从此,信息技术革命正式拉开帷幕
所以可以毫不夸张地说
今天我们讨论的这种做法
就是人类历史上最伟大最重要的软件架构设计
当然,今天我们不是为了要研究
怎么协助下一个金融系统或者是充训系统
从一个简单的软件的角度来说
省事才是它最大的优点
把业务逻辑都塞进数据库这种行为
可以称作为中信化
而中信化这个词在互联网时代
真的是一个人人喊打的过界老鼠
它就像是大数据分布式集群
微服、高口用信等等
互联网名词的反义词
它代表了互联网所反对的一切东西
但我想问的是
你开发的软件真的需要这些互联网时代的标签吗
我大胆的猜测
在看这个视频的绝大部分观众
在职业生涯的绝大部分时间里
都不是在忙着开发DAU在百万级倍以上的软件
就以我个人距离
我在某个用户规模一万级的公司待了很多年
它也开发了很多软件
有给员工用的
有给合作伙伴用的
有给商家用的
这些软件的使用者加起来也不到百万级
和直接面向一页消费者的代码
只占我这么多年写过的代码中很少很少的一部分
所以在绝大份情况下
你开发的那个软件它不需要大数据
因为它这辈子会装得下的数据都塞不满你的手机
它也不需要分布式集群
因为它总共可能就只有几千几万个用户
你撑死了也倒不了1000QPS
一台服务器都用不完
它更不需要什么微服架构
因为你的业务逻辑很简单
没有什么需要模组化需要结偶才能够应付的麻烦问题
所以它也不怕什么单点故障
因为你总共就没有几个点
真有了故障了你也躲不过
拷开那些关键量力的名词
你会发现把一切塞进数据库的中心化方案
已经能够解决你几乎所有需求
一直有看让编程再次伟大这个系列的视频的观众
你会发现我在很多系统视频里面都有介绍到
我在数据库上的各种玩法
无论是上一期将数据库的CRUD
直接映射到API上的GraphQL架构
还是在上一期用数据库再造事件驱动机制的异部架构
异货是第八期里面提到过的Postgres强大的全线管理功能
这些都是懒人的最爱
因为你只需要花很少的时间
就能够解决大多数软件的功能需求
除此之外你的代码逻辑也能剩下不少的功夫
比如在一个方式里面直接调用锁定
修改各种数据你也不需要有任何的顾虑
如果中途出了问题
整个Transaction你能保证绝对干净的回滚
如果你要在应用程序做这些工作
你需要摆弄各种的Mutax和Locking的逻辑
又比如你可以通过Trigger来控制一些前置和后置的步骤
比起在应用程首写这些调用的规则
它也更省事也更稳妥
甚至如果你不喜欢写SQL
数据库也允许你用自己喜欢的变成语言
连PHP都可以支持
当然这些都不是空谈
我用这种做法造了一个完整的电商平台
也就是第一期视频里面提到的那个
去年的这个时间
我还在逼让直播来加班写这个的全过程
老粉是可以证明的
我天天在那写SQL
从业务逻辑的复杂度来说
我觉得电商平台其实是一个非常简单的软件
比如开店 上架 商品 下单 结算等等这些核心的步骤
其实都是很直观的
所以整个电商平台的后端部分
我只用了大约8000行的SQL
其中包含了101个table 228个function
310个Trigger 404个policy和600个index
这里面已经基本上航盖了
能够想到过的电商功能
从立项到发布
算上前端的开发时间也不足12个人越
而且保守估计前端的部分至少占了4分之3
因为当时是第一次写小程序
每天都在踩坑
在发布后的将近两年里
后端系统经历了237次的升级和大布丁
和传统的那种升级的
还要把服务上线下线
还要考虑Dumb Time的这种做法相比
一函Other命令就能够完成无缝症症的感觉
真的是无法使用的爽
对比起我之前开发的软件
这次的体验总结来说
就是需要的人力更少
代码更少
数张更少
生产环境更简单
运为更轻松
绝对无形好评

数据库作为大部分软件的核心
可以说是程序员最熟悉的陌生人
尤其是在一些大公司里面
数据库是被盐房死守的
除了DBA之外
谁也不能够碰
以至于不少程序员在工作了很多年之后
对数据库的印象只有一个很模糊的感觉
我希望大家能够更多的去了解和尝试
把数据库更多的应用在你的软件中
去发挥它更大的价值
去make database great again
