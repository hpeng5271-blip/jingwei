## 一、去哪学（学习路径）

1. **先补"为什么"，再读"怎么做"**（#20）：
   > "如果我们想要从一个优秀的软件里学到一些东西，它有价值的知识点在哪——**不是怎么把它写出来，而是为什么这么写**。"
   > "The secret of a good software is not know-how but **know-why**."
   > "**读代码是最没有价值的一种**（学习方法）"——因为软件的出发点从来不是代码，而是问题与解决方案。
2. **业务知识是桥**（#20）：他招人先问业务背景；没有业务背景，"你只能看懂用了某某技术，
   但理解不了他为什么选这个技术、为什么这样呈现"。
3. **经典当历史书读**（阅读#1）：
   > "把它看作历史书，而不是工具书"；要了解时代背景（人月神话写 60 年代 IBM OS/360）；
   > "不要只读和自己有关的部分"——软件工程是网状结构，每个角色互相影响。
4. **让新技术沉淀 3 年再上手**（#1）：等它进主流、形成稳定生态；顺带避开早期大改
   （React 的 class→hooks 就是例子）。
5. **经验只能靠实战攒**（#1）：
   > "你不需要样样精通，但必须要有实战的经验。从别人那里看来的、听来的、书上看到的理论知识，在没有实际上手之前，其实都是空谈。"
6. **运维是最容易被忽略的技能**（#1）：很多架构师交付就收工；"设计只是开始而不是结束"，
   要对系统到下线负责。
7. **跨角色学**（#1 六边形战士 / 阅读#1）：懂业务、懂沟通、懂运维；不要只盯着自己那一格。

## 二、架构的精髓（取舍）

| 主张 | 依据（转写） |
|---|---|
| **架构 = 取舍，且不只在技术层** | #1："这些利弊和决策，其实不仅仅停留在技术的层面……开发难度、项目周期、费用成本、长期维护复杂度，都会左右你的设计决定。" |
| **选型要考虑"被绑定"** | #1：用阿里云 OSS 的 RAM 账号分发——技术上没问题，但"把系统和阿里云绑定了"；他改用 MinIO（S3 兼容）做抽象层。 |
| **先搞清项目关心什么** | #1：线上广告分发要百万 QPS → Kafka；线下物联网要安全/准确 → 另一种选择；"从来就没有标准答案"。 |
| **预判扩展边界（多对多）** | #1：线下广告"多屏同播 + 政府监管"→ 一开始就设计成多对多，"之后不需要重构，只是新增表达"。 |
| **简单优先，但允许复杂解** | #2："大道至简"；#17：Unix 的 Do One Thing 适合当年，但 GUI 时代问题变复杂，"复杂问题那就复杂了"（systemd 缝合但缝得好）。 |
| **技术栈越小越好** | #2：终端设备上为消息队列背 Redis+Node.js 两个栈不值得；Pinterest 从 7 种数据库减到 3 种反而撑住 2000 万访问；他用一张 Excel 替掉 CMS。 |
| **别过度开发** | #2：给只做中国市场的产品上完整 i18n；每小时 1000 万条（不到 10GB）却上 Hadoop 集群。 |
| **规则要自动化，不要靠吵** | #2：format 进 CI、API 规范统一；"规则整合到 CI/CD，就没有冲突可以发生了"。 |
| **代码是工具，不是抽象艺术** | #2：反对 clean code 教条；"代码真正的目的"是让人**更容易写、更容易看、更容易用、更容易合作**。 |
| **别造轮子** | #2：通用工具做出来就要养一辈子；"技术栈越小越好"，"技术栈与技术债成正比"（转写大意）。 |
| **知识会衰减** | TRAE：项目积累的业务逻辑与决策考量散落在会议/邮件/聊天/PR，随时间与人员流动被遗忘；分工越细，宏观知识与微观细节越隔阂。 |

## 三、工程经验（协作与交接）

1. **四类对话对象**（#1）：项目官方负责人 / 公司技术负责人 / 客户方负责人 / 真正的使用者；
   "汇报级别越高，时间越少，内容就越得浓缩"——架构师要会**提炼重点、少废话**，
   还要把技术内容**转译**给非技术听众。
2. **交接的载体是"决策记录"**（#20）：
   > "很少有项目会留下解释 know-why 的知识，大多都是解释 know-how 的。"
   > 结果就是"重写比改更容易"——新团队只有 know-how，没有 know-why，只能绕开旧代码另写一套，
   > 旧代码变成 legacy。
3. **知识库贴着代码放**（TRAE）：每个组件一份知识库：流程图 / 架构与选型对照 / 完整修改历史 /
   待办 / 面向 AI 的文字版端到端测试案例；放在组件目录旁（AI 会逐层向上找资料）。
4. **AI 协作要"填补信息孤岛"**（TRAE）：AI 不会主动问 10 万个为什么，只会在 review 时暴露误解；
   每个新对话都相当于一次代码交接 → **改代码必须同步更新知识文档**。
5. **简单任务自己做，难任务交 Agent**（TRAE）：避免"深度思考"拖慢小事。
6. **语音是效率杀手**（#23，按标题与分章）：语音"死无对证"、异步会议更可靠——文字留痕。
7. **老油条六条**（#2 分章）：过度开发 / 立规矩 / 工具不是艺术 / 技术栈越小越好 / 别造轮子 / 最朴素的最好。

## 四、明显是 ASR 错、不要引用的地方

- 人名/产品名一律不可信（"袁智能"=原子能、"核读"=Hadoop、"Mexico"=MySQL、"Pentress"=Pinterest、
  "诺外/诺号"=know-why/know-how、"ISL"≈Excel、"SystemD"=systemd）。
- 数字（"1000 万条/10 个 G"、"7 种数据库减到 3 种"、"2000 万访问"）可能被转写吞掉单位，
  **要用就得回视频核对**。
- 结论性的话（如"技术栈与技术债成正比"）我只听到大意，**不是逐字**。

## 五、和经纬的接口（待 pro 判）

- "know-why 缺失 → 重写比改容易" ↔ 我们做的"理解层/交接页"正是 know-why 的载体；
- "知识库贴着代码放" ↔ 我们的图谱/事实是否该支持"组件级知识卡"；
- "技术栈越小越好" ↔ 已落成依赖基线闸；
- "先搞清项目关心什么" ↔ `handover` 的"是什么/能不能跑/热点"；
- 冲突：systemd 式"缝合"与我们"最小化"的边界，需要 pro 给判据。
