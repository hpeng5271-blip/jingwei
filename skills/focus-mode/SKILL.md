# 资源调度：先量，再停，最后才换通道

## 已知数字（2026-10-22 实测，release）

| 动作 | 耗时 |
|---|---|
| `jingwei index`（本仓库） | ~548 ms |
| `handover --json` | ~537 ms |
| `doctor --json` | ~382 ms |
| `next --json` | ~83 ms |
| `jingwei file`（单文件） | ~42 ms |
| GUI 常驻 | 31 MB 工作集 / 8 MB 私有 / 28 线程 |

**根因不是内存，是"每次取数 spawn 一次 CLI"**（500 ms 级）。数量具：`node tools/perf.mjs`（只报不阻断，
写 `%LOCALAPPDATA%\jingwei\perf.jsonl`）。

## 聚焦模式（默认档 = 只停轮询与对账）

- 开着：停任务角标 3 秒轮询、停允许表对账；按钮写「聚焦中 · 后台 0 项」；
- **中/重两档是手动的**，不默认（索引/扫描是用户自己发起的，不该替他停）；
- 「按了要真停」：断言 `聚焦模式：按钮在、开着时后台停、关掉恢复` 守着。

## 处理"慢"的顺序（别跳步）

1. **量**：`node tools/perf.mjs`，拿到数字再说话；
2. **停**：聚焦模式、窗口失焦不轮询、设置页关掉不刷允许表；
3. **合并**：同类请求单飞 + 500 ms 去抖；
4. **换通道**（最后）：常驻 sidecar / 批量取数——`债 0.42`，pro 定的下一重点。

## 别做的

- 不要为"快"加缓存层/换存储引擎（当前不是瓶颈，是复杂度）；
- 不要把预算做成门禁阻断（pro Q7-B：只报不阻断，现在"能跑优先"）；
- 不要在没有量具的情况下动优化——说不清值不值。
