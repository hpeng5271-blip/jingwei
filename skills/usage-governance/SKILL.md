# 使用数据：契约先定，再谈采集

## 存哪（唯一位置）

`%LOCALAPPDATA%\jingwei\`（C 盘、用户私有、**不放 TEMP**——系统清理会整目录删）。
界面设置页有一行“数据目录：… [打开]”，一键跳到资源管理器。

现有文件（2026-10-22 实测合计 ~162 KB）：

| 文件 | 作用 | 坏了怎么办 |
|---|---|---|
| `tasks.json` | 任务日志（最近一条 = “刚才”） | 可删，重建 |
| `perf.jsonl` | 性能量具记录 | 可删，重建 |
| `fp-cache.json` / `scan-cache.json` | 指纹 / 扫描缓存（**投影**） | 直接丢弃重算 |
| `verify-last.json`、`watch.jsonl`、`llm-ledger.jsonl` | 校验/监视/记账 | 可删 |

## 记什么（动态层，5 条事件）

`open`（同文件 5 分钟内只记一次）· `edit`（保存后行数变化，**不记内容**）· `check`（该文件 error/warn、变绿/变红）· `revisit`（间隔 >30 分钟再回）· `abandon`（打开未改就离开）。

## **绝不记**（硬边界，pro 给定）

`-h/-V` 之类帮助调用 · 纯滚动/悬停 · 后台内部查询 · 自动对账事件 · **GUI spawn 的取数**
（否则 GUI 每取一次数就污染事件流）· 键鼠/停留时长/光标/窗口标题/剪贴板 · 任何文件**内容**。

理由：记录越全越像监控；一旦感觉被观察，行为会为了记录而变。

## 保留（pro Q4）

事件流是**源**，其余都是**投影**：90 天详情 + 长期只留计数；投影坏了直接丢弃重算，不留修复路径。

## 治理现状（先量后合）

六处数据各记各的（`tasks` / `perf` / `runs` / `usage` / `drafts` / `notes`）——**先观测写入次数与日增量**（债 0.46），一周后再决定是否统一事件流。别现在就合：那要迁移 + 全部断言红一遍。

## 别做的

- 不要把数据搬到 `%TEMP%`（会被清理工具删）；
- 不要在没有 schema 的情况下新增采集字段；
- 不要在未量化的前提下“统一事件流”。
