## 1. 它是什么

**终端与 IDE 之间的"理解层"。** 它不替你写代码，也不替你装环境；
它把「这个项目现在到底是什么状态」讲清楚，并且**在你需要的时候才讲**。

| 卡住的地方 | 谁回答 | 落点 |
|---|---|---|
| 这台机器上装了什么，够不够跑这个项目 | **经纬** | §8 环境探测（14 条 Python 来源 / 11 条 Java 来源）|
| 报错一屏，**先修哪一个** | **经纬** | §6 信息管线（过滤七步 + 抑制下位）|
| 改了代码，说不清改了什么、影响了什么 | **经纬** | §5 增量 + 变更基线 |
| 环境越装越乱，磁盘越来越满，不敢删 | **经纬** | §8 清理（三区 + 回收站）|
| 忙了两天，说不清自己做了什么 | **经纬** | §8 记录（笔记 + 运行记录 + 变更）|
| 编辑器内核、补全、调试 | **不做**（IDEA 十几年磨的）| §7 只管"够用的窗口 + 外跳"|

### 1.1 四条不许破的线

写在代码里（类型、构造入口、断言），不是写在文档里靠自觉：

| 线 | 实现里的抓手 | 守它的测试 |
|---|---|---|
| **数据正确优先**（先于速度、延迟、首屏）| `store::apply_file_update` 的四步事务 | `a_bad_row_rolls_back_the_whole_batch` |
| **不生成修复命令** | `fix.rs` 只做"补一行忽略规则"这种答案唯一且可逆的事 | `fix` 6 条 |
| **无自查不报错** | `Conclusion` **字段私有** + 唯一构造入口（内含三道闸）| `an_error_without_a_self_check_is_downgraded` |
| **关系必有来源** | `Edge::new` 的 `source` 是必填参数——没来源的关系**造不出来** | `illegal_node_pairs_cannot_be_constructed` |

### 1.2 三态：最核心的一条线

`Verdict<T>` 分 **是 / 不是 / 查不了**。它不是"体验优化"，是**事实表述的准确度**：

> 「没找到 Python」和「机器上没装 Python」不是一句话。
> 前者是**我们的结论**，后者是**对世界的断言**——而后者我们无权给出。

这条线从内到外贯通：`model::Verdict` → `engine::envelope::Envelope`
（`{state: yes|no|unknown, reason, data}`）→ 前端 `unpack()` 按 `state` 分三支。

**判据一句话**：**这是"用户的空白"，还是"我们的失败"？**
用户自己创建的东西（配置档、笔记）空 = 正常（`yes` + 空数组）；
系统里本该存在的东西（Python、编辑器、硬件）空 = 异常（`unknown` + 为什么）。

## 2. 系统全景

### 2.1 依赖方向

```
cli / src-tauri  ──→  engine  ──→  model
                        │
                        └──→  tools/schema.sql（编译期 include_str!，DDL 唯一真源）
```

**判据是可执行的一行**：扫 `crate::xxx` 的引用，**双向依赖必须是 0 对**。
曾经有 3 对，施工第 0 步拆掉了；拆的时候**连调用点一起改**——
留着转发层时，文本扫描看到的还是旧方向，**依赖方向必须是真的，不是看起来像**。

### 2.2 engine 的分层（按实测入度定，不按文件夹顺序）

```
L0  纯工具（不懂业务）    winutil · dlog · textfile · parallel · scan · jobobj
L1  机器与系统           machine · mem · native
L2  探测（拿事实）        probe · jvm · ccpp · deps · editors · envsetup · profiles · lang
L3  项目理解（出结论）     project · projects · contract · rules · diag · fix
L4  图谱（存与查）        store · parse · index · envelope
L5  项目状态（可回滚）     changes · snapshot · workcopy · runs · notes · scaffold
L6  编排（一条龙）        launch
```

**箭头只许从上层指向下层。** `store` 之所以现在能放进来，就是因为第 0 步先把三对循环拆了
——**图里有循环时，插在哪儿都说得通，那就等于没有分层**。

### 2.3 一次调用的完整数据流

前端最常走的那条（`inspect`）：

```
前端 invoke('inspect', { root })
  └─ src-tauri::inspect
       ├─ notes::migrate_legacy    旧 jsonl 搬成笔记（不搬的话老项目显示"一篇都没有"——那是假象）
       ├─ snapshot::load_latest    上一次的快照（用来比"变了什么"）
       ├─ probe::make_facts        采事实（内含 lang 探测 → jvm / ccpp 探测）
       ├─ deps::rust_tree          传递依赖树（只读一份 lock，很便宜）
       └─ rules::run_all           出结论（三态 + 抑制 + 聚合都在这里）
     → 组装 JSON 回前端
```

图谱那条支线（`index::index_rust`）：

```
目录 → collect_rust_files（过 should_skip 那道闸）
     → 三级检测（大小+时间 → 内容哈希）决定重不重解析
     → parse::parse_rust（tree-sitter；错误门控给 complete）
     → store::apply_file_update（一个事务四步：失效旧关系 → 删旧符号 → 写新的 → 记状态）
```

### 2.4 一次运行留下什么

```
record_run(store, root, command, exit_code, diagnostics, now)
  ├─ Run 节点（data 里放命令与退出码）
  ├─ Run --follows--> Contract           这次跑的是哪份契约
  ├─ Run --produced--> Diagnostic        这次跑出了哪些问题
  └─ Diagnostic --diagnosed_at--> File   每一条判在哪个文件上
```

`produced` 那条边是施工第 5 步**补出来的**：设计原文是"`Run` 节点与 `diagnosed_at` 关系"，
而矩阵里 `diagnosed_at` 的两端是 `Diagnostic → File`——
**诊断根本挂不到运行上**，图谱回答不了"上次跑失败是哪些问题"。

## 3. 领域模型

**13 种实体 / 16 种关系**，全部可序列化；两端合法矩阵在**构造期**生效。

| 实体 | 说明 |
|---|---|
| `Project` `File` `Module` `Symbol` | 代码的骨架 |
| `Dependency` `Toolchain` | 依赖与工具链 |
| `Diagnostic` `Rule` | 结论，与产生它的规则 |
| `Contract` | 环境契约（一条龙执行的依据）|
| `Note` `Commit` `Snapshot` `Run` | 记录类 |

| 关系 | 两端 |
|---|---|
| `contains` | Project→File · Module→{Module,File,Symbol} · File→{Symbol,Dependency,Diagnostic} |
| `defines` | File / Module → Symbol |
| `implements` | Symbol → Symbol |
| `calls` / `references` | Symbol → Symbol |
| `depends_on` | Dependency→Dependency · File→Dependency |
| `needs` | Dependency → Toolchain |
| `diagnosed_at` | Diagnostic → {File,Symbol,Module} |
| `reported_by` | Diagnostic → Rule |
| `causes` / `affects` | Diagnostic 相关 |
| `noted_at` | Note → {File,Symbol,Module,Run} |
| `changed_at` / `snapshotted_at` | 变更与快照 |
| **`produced`** | **Run → Diagnostic**（V0 补的）|
| `follows` | Run → Contract |

### 3.1 三条构造规则

1. **`Edge::new` 强制两端合法**：不合法组合**构造不出来**（返回 `IllegalPair`，里面带着是哪三个值）。
2. **`Edge::new` 强制有来源**：`source` 是必填参数。
3. **读路径不校验**：`Edge::from_row` 故意**不做矩阵校验**——历史数据可能写在规则变更之前，
   **读取必须能原样还原**。

### 3.2 标识规则

`id = "<kind>:<规范化 key>"`。

**一条测试当场抓出来的规则**：规范化**只对位置类实体做**（File / Module / Project），
语言自己的标识符**大小写原样保留**。

> 原来是"任何 key 都跑 `normalize_path`"，而它最后一步是全小写——于是 `Ledger::post`
> 变成 `ledger::post`。但 Rust **大小写敏感**，`Ledger` 与 `ledger` 是两个不同的类型；
> 小写化会让它们**静默撞成同一个节点**（后者覆盖前者，不报错）。
>
> 判据：**文件系统大小写不敏感，所以路径小写；语言的标识符大小写敏感，所以原样保留。**

顺带一条：**位置不是身份**。`symbol:src/lib.rs#S::m` 里**不含行号**——
方法往下挪两行还是同一个符号；否则每次编辑都会造出一堆"新符号"，图谱就没法和历史比。

## 4. 数据层

### 4.1 DDL 只有一份，而且是**文件**

```
tools/schema.sql   ← 唯一真源（能跑、能校验、能被 include）
   ├── tools/db_probe.py       读它建库压测（数字因此可复跑）
   ├── crates/engine/src/store.rs   include_str! 同一份（设计表与实际建表不可能再分家）
   └── 《数据层设计》§3          引用它，只解释"为什么"
```

**为什么从文档里搬出来**：贴着的 SQL **没法被执行也没法被校验**。
实测把三处设计改掉之后，文档里那份副本没跟着改，于是同一份表结构有了两个互相矛盾的版本。

**五张表**：`meta` · `nodes` · `edges` · `files` · `index_runs` · `query_cache`
（加上 FTS5 外部内容表 `nodes_fts` 与视图 `live_edges`）。

**`kind` / `source` 的取值用 `CHECK` 写死**——写错一个立刻失败，而不是留下一条"幽灵关系"。

### 4.2 四条守漂移的测试（第一次跑就抓到了东西）

| 测试 | 守什么 |
|---|---|
| `ddl_kind_lists_match_the_domain_enums` | DDL 里两处 `kind` 的取值 == `NodeKind::ALL` / `EdgeKind::ALL`（**含顺序**）|
| `ddl_source_lists_match_the_source_enum` | `source` 的取值 == `Source::ALL` |
| `ddl_version_stamp_matches_the_constant` | DDL 末尾写进 `meta` 的版本号 == `store::SCHEMA_VERSION` |
| `ddl_executes_and_live_edges_filters_expired` | DDL 真能建库；失效边被 `live_edges` 挡掉；非法 `kind` 写不进去 |

**它们第一次跑就抓到了漂移**：`edges` 的 CHECK 顺序与 `EdgeKind::ALL` 不一致。
内容相同、顺序不同——`CHECK` 的行为不受影响，所以**它永远不会以 bug 的形式暴露**。

### 4.3 写入：一个文件的更新是一个事务，四步

`store::apply_file_update`：

```
1. 先把这个文件产生的旧关系标失效（例外：noted_at / changed_at 是历史，不失效）
2. 删掉不再存在的符号（它们带着自己的边一起被外键级联清掉）
3. 写入新的节点与边（UPSERT；命中的旧关系在这一步复活）
4. 记下这次的文件状态（大小、mtime、内容哈希、节点数）
```

**顺序不是随便定的**：

- 少了第 1 步 → "上个月删掉的那次调用"会永远留在图谱里冒充当前状态
  （UPSERT 只复活命中的，**不清理没命中的**）；
- 少了第 2 步 → 改过名的项目会在图谱里越攒越多已经不存在的符号，而界面会如实列出来；
- **四步必须在一个事务里** → 半途失败会让图谱停在"旧关系已失效、新关系还没写"，
  看起来像"这个文件什么都没引用了"，**而且不报错**。

### 4.4 三级变更检测

| 级 | 判据 | 什么时候用 |
|---|---|---|
| 一级 | 大小 + mtime 都一样 | **每次都先用它筛——不读文件** |
| 二级 | 内容哈希 | 一级说"变了"时才花这个钱（`touch` 一下不该触发重解析）|
| 三级 | watcher / 变更日志 | 归外壳（把事件喂进来），引擎只管"给我一个目录，我把图谱对齐" |

**用纳秒级的 mtime**：秒级精度会把"同一秒里改两次"看成没变，而"保存一下又改一下"
正是最常见的编辑节奏。

### 4.5 失效与历史

- **关系不删，只标 `expires_at`**：一条关系"曾经存在过"本身是信息
  （排查"为什么上个月还好的东西现在断了"时有用的证据）。
- **清理必须显式**（否则库一直涨）：每次索引结束后删一次"过期超过 30 天的边"，
  但 `noted_at` / `changed_at` **永不清理**——那是历史，不是派生数据。
  所以清理 SQL 里那条 `NOT IN` **不是可选项**：写成"清掉所有过期的"就等于把笔记和提交记录
  一起删了，**而且不报错**。有测试盯着（`purge_never_touches_notes_or_commits`）。
- **查询只走 `live_edges` 视图**：失效边在**语法上**就查不到，
  不需要每个调用点记得写 `WHERE expires_at IS NULL`。

### 4.6 容量（实测，不是估的）

```
体积 ≈ 行数 × 185 字节（含索引与 FTS），两个规模点线性、无拐点
10k 文件 / 20 符号 → 410,000 行 → 74.6 MB
20k 文件 / 20 符号 → 820,000 行 → 153.2 MB
"50 万节点 + 200 万边" → 约 460 MB
```

**复跑命令**：`python tools/db_probe.py`（默认 10k 文件）、`--files 20000` 更大。
脚本只用系统自带 Python + 标准库，**建库语句读的就是 `tools/schema.sql`**。

**什么时候该重新审**：到 460MB 量级时，要重审的是页缓存、`VACUUM` 代价、
是否把 FTS 拆成独立库——**不是换掉 SQLite**。

## 5. 解析与图谱

### 5.1 解析：tree-sitter，只做一门

**版本**（实测兼容）：`tree-sitter 0.27` + `tree-sitter-rust 0.24`。
五个语法（rust/python/java/cpp/js）可以共用**一个** `Parser` 轮流 `set_language`。

**体积**（实测）：core + 1 个语法 = 1.3 MB，**每增加一个约 1.14 MB**，
10 个语言 ≈ 11.4 MB。（设计里"5–15MB"原本是引用级估算，现在有了实测值。）

**只做 Rust，是故意的**：设计 §1.2 那条判据——"加一门语言只许改 `lang.rs` 一处"——
**要等第二门进来才验得了**。先把一门做通，再拿第二门验抽象。

### 5.2 错误门控：不是理论，是必须做的

实测过：源码里有一个写坏的函数（`fn broken( { }`）时，`has_error = true`、
错误子树 1 个——而**符号抽取照样把 `broken` 抽了出来**。

所以"能不能建关系"**只能看 `complete`，不能看抽到几个符号**。
不这么做的后果很具体：图谱里会出现一个"存在但根本编译不过"的符号，
然后"这个函数在哪定义"给出一个不存在的答案。

### 5.3 符号的身份

```
src/lib.rs#Ledger::post     ← impl 里的方法带容器路径（否则同名方法会撞 id）
src/lib.rs#free_function    ← 顶层符号
```

`checksum` 是**内容指纹**（种类 + 名字 + 容器 + 文件），**故意不含行号**——
方法往下挪两行不算"内容变了"。

> 这里第一版写成了 `node_id(...)`，那等于**把主键再存一遍**，毫无信息量。
> 而 R1 刚把"`checksum` 语义混层"当漏洞修掉——转头自己又犯了一次，
> 所以专门加了一条测试盯着它（`checksum_是内容指纹而不是主键副本`）。

### 5.4 集成测试层（一直缺的那一层）

`crates/engine/tests/index_e2e.rs`——**用真临时目录 + 真 SQLite 文件**跑完整链路，
不是内存库：WAL、文件锁、重复打开这些问题**只在真文件上才出现**。

十条端到端测试，其中四条专盯增量：

| 测试 | 守什么 |
|---|---|
| `没改东西时第二遍全部跳过` | 重跑是核心玩法，每次全量解析的话大项目等不起 |
| `只改了修改时间的不重解析` | **二级检测存在的唯一理由**（编辑器、检出都会动 mtime）|
| `删掉的文件从图谱里撤掉` | 磁盘上没有了，图谱里也得没有 |
| `改名之后旧符号不留痕` | UPSERT 只新增和复活，**不清理没再出现的** |

## 6. 信息管线

**所有对外信息走同一条管子，五步，顺序不可换**：

```
事实(facts) → 规则(rules) → 过滤(七步) → 结论(四要素) → 呈现(分级)
```

### 6.1 过滤七步（每步都有判据，不是感觉）

| 步 | 判据 | 不许发生 |
|---|---|---|
| ①去重 | `rule_id + 参数指纹` 相同只留一条 | 同一件事报三遍 |
| ②抑制下位 | 上层根因未解 → 下位不出卡 | 根因下面挂 20 条连锁 |
| ③聚合 | 同文件 + 同错误码 → 一簇 | 同一个错刷满屏 |
| ④分级 | 红=挡运行 / 黄=不挡路 / 灰=进度 / 白=静默 | 用颜色装饰 |
| ⑤排序 | 层序（8 层）→ 严重度 → 位置 | 按时间倒序（会埋掉根因）|
| ⑥容量 | 一行 ≤6 · 一卡 ≤3 · 一屏 1 结论 | 一屏 20 条 |
| ⑦静默 | <0.1s 的操作不出提示 | 点一下就弹通知 |

**过滤系统必须自带两个出口**（P6 抓出来的）：

1. **时间出口**：被压下的东西，根因解决后要**自动浮回来**（不是"永远不再提"）；
2. **位置出口**：任何被隐藏的，都要能在**一个固定位置**查到——
   问题栏底部固定一行「另有 N 条被上层挡住 · 查看」。

> ⚠️ **设计要求，未实现（2026-10-16 核实）**：抑制机制从来没写（`Level::Silent` 零构造点，已删），
> 所以没有任何东西被压下，这两条出口也就无从谈起。详见《总稿.md》同一处下面的更正。

> 「信息过滤」这个词本身有陷阱：它听起来是"砍掉多余的"，
> 但真正难的是**砍掉之后怎么让人相信没丢东西**。

### 6.2 四要素

每条结论给**四样**：事实（凭什么这么说）· 复核命令（怎么自己验）·
边界（什么情况下这条不适用）· 下一步（该往哪看）。

**第四要素不是修复命令**——这是第 2 条线。

### 6.3 三态在管线里的位置

```
权威来源 + 非推测 + 有自查命令  →  可以报"错误"
否则                            →  降级（哪怕它看起来很像错误）
查不了                          →  "无法确认"，**永远不算缺失**
```

守它的是 `model::Conclusion`：**字段私有，只有一条构造入口**，
里面就是三道闸（权威来源 / 非推测置信度 / 有自查命令）。

> 这条如果只写在文档里就等于没写——任何人都能直接塞一个 `level: Error` 进去。

## 7. 外壳

### 7.1 形态：一屏工作区

**工作区是画布**（结构树与代码区是画布，不是卡片），**卡片只用来浮**——
依赖详情、诊断详情、运行阶段流都是浮在画布上的。没有门户、没有仪表盘首页。

### 7.2 视觉：借信息组织，不借皮

- **暖色治愈底色** + **IDEA 的语法配色**（Light `--sy-kw:#0033b3` /
  Darcula `--sy-kw:#cc7832` 等 6 类色值，两套主题）；
- **MC 整合包的按压反馈**：`:active{transform:scale(.99)}`——点下去有回弹；
- **零体积音效**：Web Audio 现算，不放音频文件（有开关）；
- **三档时长** `100 / 170 / 260ms`，由设置里的"动效"档改写；
- **跟随系统的"减少动效"**（`prefers-reduced-motion`）——这是无障碍要求，不是偏好。

### 7.3 动效与反馈：每条回答"发生了什么"

**不许动会触发 layout 的属性**（`width`/`height`/`top`/`right`/…），位移一律 `transform`；
颜色类（`background`/`color`/`border-color`/`box-shadow`）**允许过渡**——
它们只触发重绘，代价可以忽略。

> 这条原来写的是"只动 `transform` 与 `opacity`"，而实测有 30 多处颜色过渡。
> 原话太窄，等于逼着人天天违反它——**规矩要么改准，要么就是橡皮筋**。

**进度条用 `scaleX` 不用 `width`**：进度每秒更新好几次，动 width 就是反复触发布局。

### 7.4 编辑器：**冻结在"够用的窗口"**

只做「**打开 → 看 → 改 → 存 → 能回滚**」，不再往补全、跳转、重构、调试上投一分钱
——那些是 IDEA 十几年磨出来的东西。**要"成熟"就外跳**（`open_in`）。

判据一句话：**它的功能上限是"让用户不必为了看一眼而开 IDEA"**。

**但不能没有**：看不了文件就断了工作流，用户会被迫在两套工具之间反复横跳，
每横跳一次掉一次上下文。

### 7.5 关系图谱展示

**这一节在 R3 之前根本不存在**——设计里搜"可视化 / 关系图 / 图布局"零命中，
而它是**动机级**的诉求（用户说"近乎炫技的关系图谱展示设想"）。
它掉在缝里：内核章节想的是节点和边，外壳章节想的是卡片和通知。

**六条约束**（大部分是**对图谱提的**，不是对界面提的）：

| 约束 | 为什么 |
|---|---|
| 只画 `live_edges` | 失效边画出来就是假的当前状态 |
| **未知的关系不许画成实线** | 三态那条线在图上也要活着：实线=确定，虚线=推断，不画=查不了 |
| 每条边悬停要能说出"哪来的" | "关系必有来源"在图上不能断 |
| 一屏节点数有上限 | 几千个点全画出来既看不清也画不动 |
| 布局算法有时间预算 | 图布局是 O(n²) 起的东西，超了就退化成"只画 N 跳邻域" |
| 点节点要能跳到源码 | 图不落到源码上就只是装饰 |

**一个判断**：这张图**不该是首页**。信息密度太高，第一次打开的人看不懂——
首页仍然是"这个项目卡在哪"。**图谱是钻进去看的东西。**

## 8. 系统管理

（这一章的五节都是 **R3 补写的**：设计里原来零章节，
而 `machine.rs` 1,298 行、`clean.rs` 1,448 行都在跑。
这是**逆差**——代码比设计多，比反过来更危险：没人知道边界在哪。）

### 8.1 环境探测：写"来源清单"，能问的就不猜

**判据**：**"装了"是用户的事，"我们找到了"是我们的事。**
少列一个来源就是一次误报，而误报是这个项目最不许犯的错。

| 工具链 | 来源 | 状态 |
|---|---|---|
| **Python** | 14 条（环境变量双读 / 契约 / 项目内 venv / PATH / `LOCALAPPDATA` 三个位置 / `C:\Python3xx` / **`py -0p`** / scoop / conda 两处 / pyenv-win / `.local/bin` / 便携目录）| 好 |
| **Java** | 11 条（`JAVA_HOME` / PATH / 六类发行版目录 / `.jdks` / `.sdkman` / 便携目录 / `.java-version` / `~/.m2/toolchains.xml`）| 中 |
| **C / C++** | 3 类（PATH / 便携目录 / **`vswhere`**）| 中 |
| **Web / Node** | **0 条** | **缺**（触发条件：做前端项目时必补）|

**三条规矩**：

1. **有官方查询命令的，一律去问，不许猜路径**：`py -0p`（系统登记过的解释器）、
   `vswhere.exe`（VS 装在哪）、`java -version`。**还没跟上的**：`uv python dir`。
2. **"故意不进 PATH"的安装方式必须单独列**：pyenv-win 的 versions、
   IDEA 的 `.jdks`、VS 的 MSVC、便携版 SDK 目录——**"装了却说没装"的高发区**。
3. **每条来源都要留下"从哪找到的"**；找不到时说"我在这些地方都没找到"，
   **而不是"没装"**。

### 8.2 机器清单：多源印证，**不许挑顺眼的**

一个事实**带来源**；来源对不上时**把分歧摆出来**：

```rust
pub struct Fact { pub key: String, pub value: String, pub sources: Vec<String> }
```

**四条来源纪律**（每条都是真踩出来的）：

| 纪律 | 怎么来的 |
|---|---|
| CPU 型号读**两个来源**（注册表 + CPUID）| 注册表那份是 Windows 抄的，CPUID 是 CPU 自己报的 |
| 内存走 **SMBIOS**，不走 WMI | WMI 在这台机器上要 **20 秒**一次 |
| 硬盘型号走**设备描述符**，不走注册表 `Prod_` | 那是 SCSI 产品标识、**固定 16 字节**：`UMIS RPEYJ1T24MKN2QWY` 被截成 `UMIS RPEYJ1T24MK`。**这种"看起来完全正常"的截断，光靠自己发现不了** |
| 系统设置**只挑影响开发的几项** | 不读 VC++ 运行库（缺了别的程序会自己报错）、不读 Defender 排除项（那是安全决定，不是性能决定）|

> **一条教训**：一个**字段**装不下，不等于**这个来源**装不下。
> 当时为此绕道写了 `DeviceIoControl`，结果在那台机器上被系统拒了（err=5）；
> 而同一棵注册树里就有 `FriendlyName`，21 个字符一个不少。
> **别急着换更重的路子，先看完这棵树。**

**实时采样与清单是两件事**：`spec_report()` 回答"这台机器**是什么**"（读一次可以慢，要准）；
`Sampler` 回答"此刻**在忙什么**"（差分求瞬时值，要快）。
状态栏只显示后者，且**字段刻意少而准**——多一个数字就多一份噪音。

### 8.3 清理：先探后删，**只列不替人决定**

| 区分 | 做法 | 为什么必须 |
|---|---|---|
| **能删 / 要权限 / 别碰** | 三区，界面照这个分组 | 混在一起就是"一键全清"——灾难的入口 |
| **回收站 / 永久** | 默认走回收站（`FOF_ALLOWUNDO`）| 误删可恢复是底线 |
| **建议删 / 只列出来** | 日志、空目录**只列不建议** | **留不留只有项目自己知道** |

**"先探后删"是 Windows 逼出来的**：删一个**正被占用**的东西，Windows 上不是干脆失败，
而是**部分成功**——目录删了一半，剩下的是夹生饭。所以先探一次：**能独占打开就是没人在用**。

> 探测本身还有个坑：不能用 `OpenOptions::new().write(true)` 去试——
> Rust 的 std 打开文件时**默认带 `FILE_SHARE_READ | FILE_SHARE_WRITE`**，
> 于是"再打开一次"永远成功，**探测等于没探**。第一版就是这么写错的，被测试当场抓住。
> 这里要求独占（`dwShareMode = 0`）。

**安全闸**：盘根、系统关键目录、`.git`、`.jingwei`、用户目录本体，一律不放行。
**什么算垃圾**：`*.bak / *.tmp / *.swp` 这些在 **GitHub 官方 .gitignore 模板**里是标配
——普遍到需要被集体屏蔽，说明确实是所有人都在忍着的东西。

**虚拟环境**：能**确定**"没在用"的只有两种（名字带 bak/副本，或契约绑的是另一个），
**其余一律不碰**——猜错一次就是把人的环境删了。

### 8.4 项目生命周期

| 动作 | 做不做 | 关键决定 |
|---|---|---|
| **发现** | ✅ | 一个目录本身是项目就**不再往里翻**（否则 `frontend/` 与 `frontend/legacy/` 会各占一张卡）|
| **创建** | ✅ | 按语言给**整套**（清单/构建/忽略/目录约定/契约三条命令），**不是换个后缀了事** |
| **起草契约** | ✅ | 返回 `(契约, 依据)`——依据是"从哪个文件哪一行看出来的"，**看不懂的推导不去猜** |
| **移动 / 删除目录** | ❌ | **工具不该动你的目录** |

**一处用户诉求与实现判断的分歧，摆出来**：用户要的是"挪动项目位置【挪动后配置一并对齐】"，
而实现判断是"工具不该动你的目录"。**两者不矛盾**——用户真正要的不是"让工具搬文件"，
而是"我搬完之后不用手工修一堆配置"。所以做法是 **工具不搬，但工具认账**：
重扫时重算契约里的绝对路径、变更基线里的路径，刷新卡片位置。

### 8.5 笔记

- **给固定的几类，不给空白框**（新手最缺的不是自由格式，是"我该记什么"的提示）；
- **一篇坏了不许毁掉整本**（读不了的跳过，别的照常）；
- **删除只是搬进 `.trash/`**——自己写的字不该被一次误点抹掉；
- **文件是给人看的**：一篇一个 Markdown、文件名带日期、中文留着。
  代价是跨系统拷贝可能乱码；**换来**能被任何编辑器打开、能用 git 管、能在文件管理器里找到。

1. **同一事实只允许有一个可编辑副本。**
2. **引用级与估算级数字不许当预算**（指标必须带出处）。

> 决定记在文档上，而门禁上什么都没发生。

| 属性 / 性能 / 变异测试三层 | 数据层落地之后 |

### 12.2 那处"元层面的裸奔"

§9.3 的第 3 条元规矩（"每条决定都要留下一个能失败的东西"）**自己还没有被自动检查**。

它现在由 `gate.mjs` 的**动机清单**部分地守着一部分（动机必须有落点），
但"**一条决定有没有对应的测试**"这件事，**没有任何东西在查**。

> 这是整个系统里唯一一处没有名字的缺口。
> **如果只修一件事，修这个。**

## 13. 怎么继续

### 13.1 每轮的固定动作

```
选一个小目标（来自里程碑，不是来自灵感）
  → 写失败的测试（或写清验收命令）
  → 实现
  → 跑门禁（§9.2）
  → 写 ADR（如果做了取舍）
  → 记一条"这一轮留下了什么"（可验证的）
```

### 13.2 改任何东西之前，先问这三句

1. **这条决定有没有对应的"能失败的东西"？**（没有 → 它还没做）
2. **这件事我在几处各写了一份？**（>1 → 先合并）
3. **用户当初为什么要这个？那个东西现在有地方放吗？**（第 3 句是 R3 才加上的）

### 13.3 往下的三个方向（按价值排）

1. **补那处元层面的裸奔**（让"决定 ↔ 测试"可检查）；
2. **Web / Node 探测**（唯一一块 0 来源的工具链，而前端项目是目标场景）；
3. **关系图谱展示**（§7.5 的约束已经写好，图谱也已经有东西可画了）。

## 附录 C · 这个项目自己犯过的错（留着，因为有用）

四轮下来，**同一个失效模式发作了四次**：**决定记在文档上，门禁上什么都没发生**。

另外三处值得一提的：

1. **为消除重复副本，把唯一的副本删了**（R1/P7：删设计 §5 的 DDL 时，
   以为数据层设计里有，而那份里是文字描述）；
2. **R1 刚把"`checksum` 语义混层"当漏洞修掉，转头在 `parse.rs` 里又写成主键副本**；
3. **一个字段装不下，被当成了这个来源装不下**（于是绕道写了 `DeviceIoControl`，
   被系统拒了 err=5）。

共同点：**把"我以为它在那儿"当成了"它在那儿"**。
——这也是为什么这个项目最后留下了三条元规矩，而不是三十条功能清单。
